# 给千问 4 的评审提示词（需求 + 批次计划 + Code Review）

> 用途：让外部模型（千问 4 / 其他长上下文模型）对本项目做独立评审。
> 原则：**不让它知道我们的结论**（否则它只会附和），只给材料和评分标准。
> 一次会话只做一件事：需求+计划一起评，代码按模块分开评。

---

## 0. 投喂方式（先解决「它看不看得到代码」）

按优先级选一种：

1. **上传文件**（最稳）：把 `docs/需求文档-屏幕使用时间App.md`、`docs/实施任务批次计划-v2.md`
   与本次要评的代码目录（如 `app/src/main/java/com/screentrace/app/data/`）打包上传。
2. **给仓库链接**：`https://github.com/Sunbeam-5/ScreenTrace`，但要先确认它能联网抓取；
   抓不到时它会假装读过——所以第一条指令是让它**证明读过**。
3. **贴关键片段**：单次不要超过 2000 行；超出就按模块切。

---

## 1. 需求 + 批次计划评审（一次会话完成）

```text
你是一名资深 Android 应用架构师，兼任需求评审专家。你的强项是从「能不能验收」的角度
挑毛病，而不是夸奖设计。

任务：独立评审一个 Android 开源项目（屏迹 ScreenTrace）的需求文档与实施批次计划。

【材料】
- 需求文档：docs/需求文档-屏幕使用时间App.md（当前版本 v2.6，含 CR-01~CR-04 四次变更登记）
- 批次计划：docs/实施任务批次计划-v2.md（19 个批次）
- 代码仓库：https://github.com/Sunbeam-5/ScreenTrace（Kotlin + Jetpack Compose）
- 各批交付说明：docs/批次*-交付说明.md

【评审原则（必须遵守）】
1. 不要假设文档正确，也不要假设代码与文档一致；以代码/仓库事实为准。
2. 每条结论必须带证据：`文件路径:行号` 或 `文档 §x.y 的原文摘录`。给不出证据的结论不要写。
3. 结论必须分级：P0 阻断 / P1 严重 / P2 一般 / P3 建议。不要把个人偏好写成缺陷。
4. 不要复述文档里已写明的设计取舍（例如「为什么排行按单日口径」），除非该取舍本身有逻辑漏洞。
5. 禁止输出「建议完善文档」「建议补充测试」这类没有具体内容的建议；每条建议都要能直接执行。

【第一部分：需求文档评审】
1) 自洽性：跨章节冲突。重点核对 §5 的 UI 规范与 §7 的验收标准是否对同一行为给出不同要求；
   §4 数据模型/合并策略与 §3 解析口径是否一一对应；CR-01~CR-04 是否推翻或残留了旧条款。
2) 可验收性：§7 逐条检查——是否存在不可判定的表述（"流畅""合理""体验良好"）、
   缺少阈值、缺少数据前提、无法用命令或截图验证的条目。
3) 遗漏：从真实用户场景出发，指出这套功能缺什么（要具体场景，不要"建议增加更多功能"）。
4) 合规与上架风险：隐私、权限声明（如 QUERY_ALL_PACKAGES）、Shizuku 依赖、
   可选云同步与 AI 分析的数据边界，哪些会在 Google Play 或国内应用商店被卡。

【第二部分：批次计划评审】
1) 依赖与顺序：是否存在"后面的批次才建表/建接口，前面的批次却要使用"的硬伤；
   批次执行顺序与依赖声明是否矛盾。
2) 覆盖度：把 §7 全部验收条目逐条映射到批次——有没有孤儿条目（没有批次承接）、
   有没有某个批次承担过多（超过一次可验证的交付）。
3) 出口条件：每个批次的"验证"是否可执行（能跑命令/能看指标），还是只能"肉眼看看"。
4) 风险表：补上漏掉的真正技术风险（不是"可能延期"这种废话）。

【第三部分：文档与计划的不一致】
列出"文档说 A、计划做 B""计划引用了不存在的小节/文件/表"这类不一致，逐条给位置。

【输出格式】
第一段：「我读了什么」——列出你实际读到的文件与关键行号（用于证明没有幻觉）。
第二张表：
| 编号 | 级别 | 位置(文件:行 或 §) | 问题 | 证据 | 建议改法 |
最后：「如果只能改 3 处，改哪三处」并说明理由；以及「我不确定、需要作者确认」的清单。
```

## 2. Code Review（按模块，一次一个范围）

> 不要一次让它评全仓库：上下文会被稀释，结论会变成泛泛而谈。
> 建议顺序：`data/`（解析与入库）→ `ui/`（状态与页面）→ `uikit/`（自绘组件）→ `theme/`。

```text
你是一名资深 Android 工程师，现在做一次严格、克制的 code review。

仓库：https://github.com/Sunbeam-5/ScreenTrace
本次评审范围（只看这个范围，其他模块可引用但不要展开）：
  <示例：app/src/main/java/com/screentrace/app/data/**、app/src/test/java/com/screentrace/app/data/**>

【背景（只用于理解意图，不要复述）】
- 数据源：Shizuku 执行 `dumpsys usagestats`，解析 checkin（CSV）与明文两种格式；
  不同 OEM 的历史窗口与事件缓冲行为不同，事件会过期。
- 屏幕时长口径：亮屏/锁屏会话区间（screen_session 表）跨拉取做扫线并集，日聚合从并集重算。
- 产品语义：「—」= 数据源缺失，`0` = 真实 0 次，两者不可混用。
- 技术栈：Kotlin 1.9.24 / Compose BOM 2024.06 / Room 2.6.1 / WorkManager / DataStore；不使用实验性 API。

【重点检查项】
1. 正确性：跨零点、时区/DST、空数据、单条事件、乱序或重复事件、秒与毫秒混用、
   取整方向、浮点累积误差。
2. 并发与事务：Room 事务边界是否正确、协程作用域与取消、Flow 重入与重复发射、
   状态赋值竞态、主线程 IO。
3. 失败路径：异常被吞掉、失败后状态不一致（例如内存态与库不一致）、重试风暴、
   日志/内存无界增长。
4. 数据迁移：Room `version` 与 entity/DAO 是否一致、缺迁移是否会崩、老数据兼容。
5. Compose：状态提升、`remember` 的 key、副作用放在什么位置、单插槽容器
   （Box / Crossfade / AnimatedContent）里放多个根节点、Intrinsic 与 SubcomposeLayout、
   不必要的整页重组。
6. 性能：大文本解析的内存峰值、每帧分配、Lazy 列表 key、图片/图标解析开销。
7. 测试有效性：现有测试是否可能"假绿"——断言太弱、测试数据形状走不到目标分支、
   断言的是实现细节而非行为。指出具体测试名与修改方法。
8. 安全与隐私：敏感数据是否落盘/进日志/进备份、权限声明是否必要且够用。

【输出格式】
1) 三行以内的总体判断：这段代码最大的风险是什么。
2) 问题表：
| 编号 | 级别(P0/P1/P2/P3) | 位置 file:line | 问题 | 触发条件 | 具体修法 |
3) 「看起来可疑但其实没问题」的 3 个点（说明你核对过，避免误报）。
4) 建议补充的测试：给出输入数据形状 + 期望断言 + 它能抓住哪个 bug。

【禁止】
- 不要提"重构以提升可读性"这类无法验证的建议；
- 不要建议引入新框架/新依赖，除非能证明现有依赖无法完成；
- 不要建议修改 reference/ 下的样本数据文件。
```

## 3. 追问模板（把结论落成可执行任务）

```text
把上面的 P0/P1 问题改写成开发任务，每条包含：
- 触发条件（什么输入/操作会复现）
- 期望行为
- 需要改的文件与函数
- 验证方式（跑哪个测试 / 用什么命令 / 看哪个指标）
按依赖顺序排列，不要合并成一条"大重构"。
```

## 4. 使用建议

- **先让它证明读过**：第一段必须输出文件清单与关键行号。若行号明显对不上或漏了核心文件，
  说明它在猜，这一轮结论直接丢弃。
- **一轮审一处**：需求+计划可以一起（都是文字），代码必须按模块切。
- **交叉验证**：同一份提示词分别投给两个模型（例如千问 4 与 Kimi），只采信**两边都指出**的问题
  或**证据充分**的单边问题；把结果汇总进 `docs/多AI评审汇总表`。
- **不要提前告诉它结论**（例如"6g 缺批次卡""批 8 与批 11 顺序矛盾"）。提前喂结论会让它只做附和，
  失去独立评审的意义；等它自己提出来后，再拿我们的核对结果对比，才知道它是否真的在读。
- **对它的建议做二次核对**：模型的常见失效是"引用不存在的文件/行号"和"把设计取舍当缺陷"。
  凡是 P0/P1，都要先在本地 `grep` 一次确认。
