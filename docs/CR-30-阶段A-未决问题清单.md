#### DR-01 · §3-6 应用时长的「区间归属日」口径

| 字段 | 内容 |
|---|---|
| **位置** | 需求文档 §3 解析算法 · 第 6 条 |
| **现行条文** | 「**应用时长**：不从事件配对算，直接用系统自己的区间聚合（`totalTimeUsed`/`appLaunchCount`），**按区间归属日汇总**；当天用 In-memory 段补上。」 |
| **问题** | 「按区间归属日汇总」没有定义归属日 = 区间的**开始日 / 结束日 / 覆盖日**，实现取的是**结束日**（`UsageDumpParser.kt:385` 的 `endMs - 60_000`）。当系统给出一个**跨自然日**的区间（如 checkin 的 ~24h 窗口），整段时长被记到结束日 → 线 2 的直接成因 |
| **建议条文** | 「……**按区间归属日汇总**（归属日 = 区间的**结束日**；当日 In-memory 段补当天）。**（CR-30-R11 待定稿）** 当系统区间**跨越自然日**时：① 区间时长 ≤ 24h 且可按自然日切分的，按自然日切分后分别归属；② 无法切分、或来源可信度不足的，**保留为窗口级记录**，不进入单日精确口径，也**不得**整段记入结束日。」 |
| **依赖** | D-01（方案甲）、D-05（允许改口径）、D-10（窗口级应用时长去哪） |
| **状态** | **待裁决** |

#### DR-02 · §3-9「应用前台区间并入屏幕会话」的证据定性

| 字段 | 内容 |
|---|---|
| **位置** | 需求文档 §3 解析算法 · 第 9 条 · 「应用前台区间并入屏幕会话（CR-03 修订，2026-11-11）」 |
| **现行条文** | 「应用在前台时屏幕**必然亮着**，所以 `ACTIVITY_RESUMED→PAUSED` 配出的前台区间是屏幕时长的**可靠下界**，**必须**与 `SCREEN_INTERACTIVE` 会话一起做区间并集后再切日/切小时。」 |
| **问题** | ① 「**必然亮着**」在 MIUI 上**不成立** —— 存在「息屏但 Activity 仍可见」（R11 的 F-04），发生率未量化；② 「**可靠下界**」在 Activity 区间与 SCREEN 事件**同源缺失**时失效 —— 长亮屏场景下两条证据一起断（这正是线 1）；③ 并入并集会让「屏幕时长」被「前台时长」**污染**：应用在前台 ≠ 屏幕亮；④ 与 GPT §3.2 的要求直接冲突（Activity 只能作**辅助证据**） |
| **建议条文** | 「应用在前台时屏幕**通常**亮着（MIUI 上存在『息屏但 Activity 仍可见』的情形，实际发生率**未量化** —— 见 R11 的 F-04）。因此 `ACTIVITY_RESUMED→PAUSED` 配出的前台区间**不得**作为屏幕时长的『可靠下界』，也**不得**与 `SCREEN_INTERACTIVE` 会话做区间并集后充当亮屏时长。前台区间只作**辅助证据**：用于标注『该时段有应用在前台』，**不用于生成精确亮屏区间**；**不得用应用时长反推亮屏时长**。**（CR-30-R11 待定稿）**」 |
| **依赖** | F-04（N4 取证）、D-05 |
| **状态** | **待裁决**（取证后定稿） |

> **这一条影响面最大**：它直接决定「亮屏时长」这个 App 最核心的指标怎么算。若删除并集，CR-03 当初为解决「应用合计 13h31 > 屏幕 11h09」而引入的机制就消失了 —— 因此**不能简单删除**，必须同时给出替代路径（窗口级 + 质量标记）。R11 §4.2 的「可联合证明的系统状态清单（待验证）」是候选方向，但**尚未验证**。

#### DR-03 · §3-9「应用时长总量约束」在质量非 OK 时不适用

| 字段 | 内容 |
|---|---|
| **位置** | 需求文档 §3 解析算法 · 第 9 条 · 「应用时长总量约束」 |
| **现行条文** | 「……一旦撑破，判定该天 In-memory 的 `totalTimeUsed` 整体不可信……整天退回事件流推导值——宁可少报，也不给一组『加起来比屏幕还长』的数字。」 |
| **问题** | 该约束的分母是「当天屏幕时长」。长亮屏故障日屏幕时长为 **0** → 约束退化为「应用合计 ≤ 0」，任何非零应用合计都会「撑破」；而「退回事件流推导值」在事件流**同源缺失**时仍然是 0 → **把「未知」当成「可信的 0」**，这正是线 1 的固化机制 |
| **建议条文** | 「……显式传入单日（批 6b 的『今日』语义）时豁免此约束。**（CR-30-R11 待定稿）** 当该日的**屏幕时长本身不可信**（采集状态非 OK，或数据质量为 `ANCHOR_ONLY` / `PARTIAL` / `UNKNOWN`）时，本约束**不适用**：既不得据此判定 In-memory 不可信，也**不得**把事件流推导值当作可信值；该日应整体标记为**采集状态 PARTIAL / 数据质量 UNKNOWN**。」 |
| **依赖** | D-07（元数据随行绑定）、D-09（采集状态独立落库列） |
| **状态** | **待裁决** |
