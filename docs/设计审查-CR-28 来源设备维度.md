## 0. 问题与裁决回顾

### 0.1 问题（已核实）

`MergePolicy`（同日取较大）与 `CrossDeviceMerge`（同日累加）写进**同一张表**：

| 操作 | 手机 A | 手机 B | 库里 |
|---|---|---|---|
| 合并两台 | 2h | 3h | **5h**（累加） |
| A 又用 30 分钟 | **2.5h** | 3h | **仍是 5h**（`mergeDay(5h, 2.5h)` 取大） |

**A 新增的 30 分钟被静默丢掉。** 另外 `screen_session` 走区间并集、`day_summary` 走累加，两张表口径不一致。

**[R2] 根因收敛**：病根不是「取大 vs 累加」选错了一个，而是**跨来源合并发生在写路径**。
R2 把写路径统一为「**同来源取大/覆盖**」，跨来源求和**只发生在读路径**（§4.1），
`CrossDeviceMerge` 的累加写法随之废除——P0 从结构上消失。

### 0.2 三项裁决（首审未改动）

| # | 裁决 |
|---|---|
| 1 | 对外默认显示 **跨来源 SUM（总使用时长）**；「占用时钟时长（会话区间 UNION）」保留为**可选辅助指标**，两者不得混为一谈。**逐指标定口径**，不只改首页。 |
| 2 | 历史混合数据**不清空**：能按原始备份重拆的重拆；找不到的**保留并标为「历史来源未知」**；**禁止归属到当前设备**；与新分量**必须隔离**（防取大/覆盖/重复累加）；**不伪造来源**。 |
| 3 | 备份升 **schema 6**、**保留设备分量**；≤5 继续可导入；无法识别来源 → legacy/unknown；导出/导入/再导出保持分量；重复导入幂等；不同设备重叠会话不互相覆盖；**数据写入与账本同事务**。 |

## 1. Room 新表结构、主键与索引（Room DB **v6 → v7**）

> 注意两套版本号：**Room `version`**（现 6）与**备份 JSON `schemaVersion`**（现 5）。本节是 Room 的 v6→v7。

### 1.1 设计取向（首审认可，沿用 R1）

**把「来源」做成行的维度，不拆表、不改查询层的整体形状。** 理由：
- 现有 DAO/查询大多是「按日期区间取行再聚合」，加一列后只需在**聚合处**分流；
- 拆表会让表数量翻倍、备份/导出/迁移各要一套分支；
- 联合主键天然满足「同一来源同一天一行」与「不同来源互不覆盖」。

**保留值 `sourceDeviceId`**（写死的哨兵，永不与真实 deviceId 冲突）：

| 取值 | 含义 |
|---|---|
| 本机 `deviceId` | 本机采集的数据 |
| 远端设备 ID | 跨设备合并进来的 |
| **`'__legacy__'`** | **历史来源未知**（迁移时的混合总量，禁止归属到任何设备） |

### 1.2 六张表的新结构

**`day_summary`**
```sql
CREATE TABLE `day_summary` (
  `date` TEXT NOT NULL,
  `sourceDeviceId` TEXT NOT NULL,
  `screenMin` INTEGER NOT NULL,
  `screenUnlockMin` INTEGER NOT NULL,
  `unlocks` INTEGER NOT NULL,
  `launches` INTEGER NOT NULL,
  `longestSessionMin` INTEGER NOT NULL,
  `pulledAt` INTEGER NOT NULL,
  PRIMARY KEY(`date`, `sourceDeviceId`)
);
CREATE INDEX `index_day_summary_sourceDeviceId` ON `day_summary` (`sourceDeviceId`);
```

**`app_usage`**
```sql
CREATE TABLE `app_usage` (
  `date` TEXT NOT NULL, `sourceDeviceId` TEXT NOT NULL,
  `pkg` TEXT NOT NULL, `name` TEXT NOT NULL, `minutes` INTEGER NOT NULL,
  `launches` INTEGER NOT NULL, `category` TEXT NOT NULL,
  PRIMARY KEY(`date`, `pkg`, `sourceDeviceId`)
);
CREATE INDEX `index_app_usage_pkg` ON `app_usage` (`pkg`);
CREATE INDEX `index_app_usage_sourceDeviceId` ON `app_usage` (`sourceDeviceId`);
```
> `pkg` 索引给「应用排行」（按 pkg 跨日期/跨来源分组）；`name`/`category` 仍是行级字段（合并时占位名回填逻辑不动）。

**`hour_usage`**
```sql
CREATE TABLE `hour_usage` (
  `date` TEXT NOT NULL, `hour` INTEGER NOT NULL, `sourceDeviceId` TEXT NOT NULL,
  `minutes` INTEGER NOT NULL,
  PRIMARY KEY(`date`, `hour`, `sourceDeviceId`)
);
CREATE INDEX `index_hour_usage_sourceDeviceId` ON `hour_usage` (`sourceDeviceId`);
```

**`screen_session`**
```sql
CREATE TABLE `screen_session` (
  `startMs` INTEGER NOT NULL, `kind` TEXT NOT NULL, `sourceDeviceId` TEXT NOT NULL,
  `endMs` INTEGER NOT NULL,
  PRIMARY KEY(`startMs`, `kind`, `sourceDeviceId`)
);
CREATE INDEX `index_screen_session_endMs` ON `screen_session` (`endMs`);
CREATE INDEX `index_screen_session_sourceDeviceId` ON `screen_session` (`sourceDeviceId`);
```
> PK 加 `sourceDeviceId` 后，**不同设备的完全重叠区间也各存一行、互不覆盖**（裁决 3 的硬要求）。
> **[R2]** 入库扫线并集改为**按来源隔离**（`Entities.kt` 现注释：入库前扫线合并、同 kind 区间互不重叠）：
> 同来源区间照旧合并；**跨来源区间永不合并**（合并会破坏 UNION 的同时性信息）。

**`unlock_event` / `notification_event`** —— **[R2] 主键加确定性 `seq`**（见 §1.3）：
```sql
CREATE TABLE `unlock_event` (
  `occurredAtMs` INTEGER NOT NULL, `sourceDeviceId` TEXT NOT NULL,
  `seq` INTEGER NOT NULL,
  PRIMARY KEY(`occurredAtMs`, `sourceDeviceId`, `seq`)
);

CREATE TABLE `notification_event` (
  `occurredAtMs` INTEGER NOT NULL, `type` TEXT NOT NULL,
  `pkg` TEXT NOT NULL, `sourceDeviceId` TEXT NOT NULL,
  `channelId` TEXT, `seq` INTEGER NOT NULL,
  PRIMARY KEY(`occurredAtMs`, `type`, `pkg`, `sourceDeviceId`, `seq`)
);
-- 原有两个索引（pkg、occurredAtMs）保留
```

**不动的表**：`pull_log`（拉取流水，`source` 是数据通道不是设备，与聚合无关）、`app_limit`（本机用户意图，跨设备不搬运）、`device_merge_ledger`（CR-27 已建，`deviceId` + `date`）。

### 1.3 **[R2]** 事件主键：同毫秒冲突验证（二审问题 4）

**验证结论：同一设备同毫秒确实可能有多条合法事件，现状会丢行。**

| 证据 | 内容 |
|---|---|
| `UsageDumpParser.kt:548` | 「应用级事件保持多重集合，**同秒多条真实通知不丢**（CR-01 红线）」——解析层明确保留 |
| `UsageDumpParser.kt:546` | 「同一 user 的相邻事件不合并（逐条输出语义，**同账户快速重复解锁保留**）」——解锁同毫秒/同秒多条合法 |
| `Entities.kt:65-66` | 自陈：「PK 不含 channelId——**同毫秒同包同类型的两条记录会被 `INSERT OR IGNORE` 吞掉后者**」 |
| `unlock_event` PK = `occurredAtMs` | 同设备同毫秒两条解锁，第二条被吞 |

即**解析层红线与 DB 层主键口径打架**（这正是设计审查要抓的那类问题）。修复：

**`seq` 的确定性规则**（保证「重复拉取仍然幂等」）：
1. `seq` = **来源内**、按 `(occurredAtMs[, type, pkg])` 分组后、**解析器输出顺序**的序号（从 0 起）。
   解析器输出是确定性排序（`sortedBy { it.ms }` 稳定排序，同毫秒保持 dump 内原始相对次序），
   因此**同一份输入 → 同一组 `(主键, seq)`**；
2. 写入一律 **upsert 按完整主键**（含 `sourceDeviceId` 与 `seq`）：
   重复拉取同一窗口 → 同键覆盖，**不增行、不漏行、不重行**（幂等）；
3. 跨设备同毫秒：`sourceDeviceId` 在主键里，互不吞（二审测试「A、B 同一毫秒解锁」）；
4. 同设备同毫秒多条：`seq` 0、1、2… 各占一行，不丢（CR-01 红线补全到 DB 层）。

**已知取舍**：同一设备**不同批次**的 dump、同毫秒同组的两条**不同**事件可能都拿到 `seq = 0`
（各自批次内的第 0 条）→ 后批覆盖前批。概率极低（同设备同毫秒 + 跨批次语义重复），
记入 §8 待确认 2（备选：把 dump **原始行号**并入 `seq`，彻底确定但列宽变大）。

> **`screen_session` 不加 `seq`**：会话入库前按来源扫线合并（同 kind 区间互不重叠），
> 同 `(startMs, kind, sourceDeviceId)` 即真重复，upsert 覆盖即幂等，无需序号。

### 1.4 为什么不把 `'__legacy__'` 拆成独立表（沿用 R1）

独立表更「干净」，但：① 每个聚合查询都要 UNION 两张表；② 备份/导出各要两套分支；③ 未来来源继续增加时会再分裂。**保留字 + 行级隔离**已经满足「隔离」要求（见 §4.3），且查询形状不变。

## 2. schema 5 → 6 的迁移规则（Room `MIGRATION_6_7`）

### 2.1 迁移中做（纯 SQL，不读 DataStore）

SQLite 不能 `ALTER TABLE` 改主键，走「建新表 + 搬行 + 换名」：

1. 建 `*_v7` 新表（含 `sourceDeviceId`、新 PK、新索引）；
2. `INSERT INTO *_v7 SELECT ..., '' FROM *;` —— 先把 `sourceDeviceId` 全置 **`''`（未归档）**；
3. `DROP TABLE *; ALTER TABLE *_v7 RENAME TO *;` 并重建索引；
4. **不删任何旧数据**（铁律）。

### 2.2 来源归档（迁移后**首次启动**做，因为它要读 DataStore 的 deviceId 与账本）

```
mergedDates = Room.device_merge_ledger ∪ 旧 DataStore 账本   // CR-27 已有的并集
localDeviceId = DataStore.device_id
for 每个 sourceDeviceId = '' 的行:
    date = 该行的日期（事件/会话按本地时区归属）
    if date ∈ mergedDates:
        该行 sourceDeviceId = '__legacy__'      // 历史来源未知
    else:
        该行 sourceDeviceId = localDeviceId      // 纯本机日（可靠归属，见 §3）
```

**为什么在首次启动而不是迁移里**：`MIGRATION_6_7` 是纯 SQL、跑在 SQLite 层，读不到 DataStore 的 `device_id`；把归档做成**幂等的启动步骤**（只处理 `sourceDeviceId = ''` 的行，处理完就没有这种行了）比塞进迁移安全。

### 2.3 历史混合数据的保留（裁决 2）

- **不删、不清空、不伪造来源**：混合总量原样保留在 `'__legacy__'` 行里。
- **禁止归属到当前设备**：`'__legacy__'` ≠ `localDeviceId`，从结构上堵死。
- **与新分量隔离**：见 §4.3「legacy 只读保护」。
- **能重拆的重拆**：见 §2.4「重建历史来源」。

### 2.4 **[R2 重做]**「重建历史来源」修复工具（可选、显式触发、**必须可回滚**）

> R1 的「本机分量 = 混合总量 − Σ已知来源分量」**废除**：残差归本机就是按当前设备
> 猜测历史来源，二审问题 5 明令禁止。R2 只写**有原始备份直接证明**的分量。

**流程（快照 → 重建 → 核对 → 回滚，四件套缺一不可）**：

1. **重建前快照**：把受影响日期的**全部行**（含 `'__legacy__'` 与各来源行）原样快照到
   本地 JSON（`rebuild_snapshot_<时间戳>.json`）；
2. **记录重建范围**：日期范围、涉及来源、使用的备份文件清单 → `rebuild_log`（§8 待确认 1）；
3. **重建**：对每个含 `'__legacy__'` 的日期，从各设备原始备份（`screentrace-dev-<id>.db`
   或其 JSON 备份）逐来源提取该日分量，写 `sourceDeviceId = 备份 device.id` 的行；
4. **`'__legacy__'` 行只保留「无法由备份解释的剩余」**：
   `剩余 = 拆分前总量 − Σ各来源备份分量`；`剩余 = 0` 才删除该 legacy 行，
   `剩余 > 0` 留着（来源仍不可考），`剩余 < 0` 说明备份与总量对不上 → **该日不重建**；
5. **重建后核对**：逐日断言 `SUM(各来源 + 剩余 legacy) == 拆分前 SUM`、
   `MAX`、`UNION` 三项均核对，结果写 `rebuild_log`；
6. **回滚**：核对不过或中途任何失败 → 按第 1 步快照**整日恢复原始数据**，
   `rebuild_log.rolled_back = true`，绝不留半套状态。

**约束**：
- **不能可靠拆分的日期必须继续保留 `'__legacy__'` 原值**（缺备份 / 备份不全 / 对不上），
  **绝不丢数据**；
- **禁止根据当前设备 ID 猜测历史来源**（`localDeviceId` 只用于 §2.2 归档的
  「纯本机日」判定，那是账本可证的，不是猜）；
- 界面：云同步页「重建历史来源」入口 + 逐日结果（已重拆 N 天 / M 天因缺备份或核对不过保留未知）。

## 3. 现有本机数据的归属与不可靠部分

| 数据 | 能否可靠归属 | 归到哪 |
|---|---|---|
| **迁移前、且该日不在合并账本里** | ✅ 可靠 | 本机 `deviceId` |
| **迁移前、且该日在合并账本里**（合并过外来数据） | ❌ 不可靠（混合总量） | `'__legacy__'` |
| 迁移后本机拉取 | ✅ 可靠 | 本机 `deviceId` |
| 迁移后跨设备合并 | ✅ 可靠 | 来源设备 ID |
| `pull_log` / `app_limit` | — | 不动（与来源无关） |

**不可靠部分的唯一出路**是 §2.4 的重建工具；重建不了就一直挂着 `'__legacy__'`，**宁可「来源不可追溯」也不编造**（裁决 2 明令）。

## 4. 逐指标聚合口径（裁决 1：默认 SUM，辅助 UNION）

### 4.1 口径表（首审确认，沿用 R1）

| 指标 | 表 | **聚合** | 理由 |
|---|---|---|---|
| **总使用时长**（`screenMin` / `screenUnlockMin`） | `day_summary` | **跨来源 SUM** | 裁决 1：统计的是设备使用行为，不是用户独占的现实时间。两台同用 1h = 2h |
| **解锁次数** `unlocks` | `day_summary` | **跨来源 SUM**（= 跨来源 COUNT 事件） | 每台设备各解各的 |
| **启动次数** `launches` | `day_summary` | **跨来源 SUM** | 同上 |
| **最长连续** `longestSessionMin` | `day_summary` | **跨来源 MAX**（**不是** SUM，首审已确认） | 「最长连续」是时长的**最值**，相加无意义；两台各 1h 不重叠 = 最长 1h |
| **应用排行** `minutes` / `launches` | `app_usage` | **跨来源 SUM**（按 `pkg`） | 同一应用在两台设备各用 1h = 2h |
| **小时分布** `minutes` | `hour_usage` | **跨来源 SUM**（按 `(date, hour)`） | 直方图口径，不做区间并集 |
| **通知打扰 / 已查看** | `notification_event` | **跨来源 COUNT** | 主键含来源与 seq 后互不吞 |
| **解锁事件条数** | `unlock_event` | **跨来源 COUNT** | 同上 |
| **占用时钟时长**（**辅助指标**） | `screen_session` | **跨来源 UNION**（区间并集） | 裁决 1：与总使用时长**分开**，不混为一谈 |
| **日均 / 覆盖天数** | 由日汇总 | **先 SUM 再算** | 分母不变（有记录的天数） |
| **上一等长周期对比** | 由日汇总 | 先 SUM 再比 | 同上 |

**展示位置（首审已裁决）**：默认显示 SUM（圆环卡、统计柱、日历色档、排行都用 SUM）；
UNION 作为**独立副指标放统计页**，今日页圆环继续突出总使用时长。文案措辞待定（§8 待确认 3）。

### 4.2 **[R2]** 跨午夜、时区与 UNION 统计范围（二审意见 ①）

| 规则 | 决定 | 理由 |
|---|---|---|
| **跨午夜会话** | **按自然日裁剪**：23:00–01:00 的会话在两日各占 1h（`[max(startMs, dayStart), min(endMs, dayEnd))`），分别计入各自日期的 SUM 与 UNION | 整段归起点日会多算 1h / 次日少算 |
| **日期与时区** | 以**自然日**切分，日边界取**聚合时本机时区**（与既有 `date` 键口径一致）；来源数据自身的 `date` 由来源设备本地时区生成，导入时原样保留 | 不引入时区字段、不改既有 date 语义 |
| **时区变更** | **不重排历史**：历史 `date` 与裁剪结果固化，新数据按新时区切日 | 避免一次时区切换重算全库 |
| **UNION 统计范围** | 只对**当日裁剪后**的区间做并集，**不跨日摊派**；只计 `kind = SCREEN` 会话（与最长会话口径一致）| 与 SUM 的日切分对齐，保证同日 `UNION ≤ SUM` |
| **恒等式** | 同日 `UNION ≤ SUM`；`SUM − UNION = 跨设备重叠时长` | 双设备场景的核心解释 |

### 4.3 **[R2 重做]**「legacy 只读保护」机制（二审意见 ②）

> **R1 的「冻结日跳过所有写入」废除**（二审不批准：会丢独立来源的原始事件）。
> 新机制：**legacy 行只读 + 来源明确的新数据独立写入 + 重算按来源隔离**。

**读写规则**：

1. **`'__legacy__'` 行只读**：普通拉取、合并、重算**不得** update / 覆盖 / 取大 / 累加任何
   `sourceDeviceId = '__legacy__'` 的行（所有表适用）；
2. **来源明确的新数据照常写入**：本机采集 → 写 `localDeviceId` 分量行；其他设备导入 →
   写该设备 ID 分量行。与 legacy 行**互不接触**；
3. **写路径统一语义**：同一 `(sourceDeviceId, date[, …])` 的写入一律 **upsert 取大/覆盖**
   （重复拉取幂等）；**跨来源求和只发生在读路径**（聚合视图/查询），
   任何写路径都不做跨来源累加或取大（P0 根因消失，§0.1）；
4. **聚合与重算按来源隔离**：聚合只读不回写；「重算某日」（如从 `screen_session` 并集重算
   日聚合的链路，`Entities.kt` 现有逻辑）必须**只重算 `sourceDeviceId` 相同的行**；
   若某条重算链路暂时无法保证来源隔离，**禁止它重算含 legacy 的日期**
   （跳过并记录原因），但**绝不丢弃独立来源的原始事件**（事件表始终逐条落库）；
5. **重复拉取不重复累计**：upsert 按完整主键（含 `seq`）覆盖；`device_merge_ledger`
   同事务记账（CR-27 机制不变，数据与账本同事务）。

**验证例子（二审指定）**：某日 legacy = 4h，同日设备 A 新用 1h、设备 B 新用 2h：

| 来源 | 行 | 值 | 谁能改它 |
|---|---|---|---|
| `__legacy__` | `day_summary('__legacy__', D)` | `screenMin = 240` | **无人**（只读） |
| A | `day_summary('A', D)` | `screenMin = 60` | 只被 A 的新数据 |
| B | `day_summary('B', D)` | `screenMin = 120` | 只被 B 的新数据 |

- `SUM(D) = 240 + 60 + 120 = 420min = 7h` ✅
- **legacy 原值仍然是 4h** ✅
- A 再用 30min → A 行取大变 90min，legacy 仍 4h，SUM 变 7.5h（对应测试 T11）✅

### 4.4 「两张表的口径不一致是**有意的**」（沿用 R1）

- `day_summary` **SUM** = 「总使用时长」；
- `screen_session` **UNION** = 「占用时钟时长」。

两台设备同时使用 1 小时：**SUM = 2h、UNION = 1h**。这两个数字都对，只是回答的问题不同。裁决 1 要求**分开展示、不得混为一谈**。

## 5. 备份格式 schema 5 → 6（裁决 3 + 二审意见 ③）

### 5.1 **[R2]** 身份约束：顶层 = **备份导出设备**

> **顶层数据的来源身份是备份导出设备，与导入设备无关。**
> **A 导出 → B 导入 → B 再导出：A 的数据必须仍然属于 A**，不得在导入时重归属 B。

```jsonc
{
  "schemaVersion": 6,
  "exportedAt": "...", "appVersion": "...",
  "device": { "id": "GAQOHMNFQWFUPBQO", "nickname": "...", "model": "..." },
  // 顶层 = 导出设备（device.id）自己的分量，形状与 schema 5 一致 → 旧读取器能解析
  "day_summary": [...], "app_usage": [...], "hour_usage": [...],
  "screen_session": [...], "unlock_event": [...], "notification_event": [...],

  // 新增：其他来源（含 '__legacy__'）的分量，各带自己的 device
  "sources": [
    { "device": { "id": "V2304A", "nickname": "...", "model": "..." },
      "day_summary": [...], "app_usage": [...], "hour_usage": [...],
      "screen_session": [...], "unlock_event": [...], "notification_event": [...] },
    { "device": { "id": "__legacy__", "label": "历史来源未知" },
      "day_summary": [...], "...": "..." }
  ],
  // 不变：pull_log / app_limit / settings
}
```

**导入派生规则**：
```
sourceDeviceId =
  顶层 device.id 存在 → device.id（导出设备身份，无论谁导入）
  顶层无 device.id     → '__legacy__'（schema <5 的旧备份，不猜、不归导入设备）
sources[] 每项        → 该项 device.id（缺 → '__legacy__'）
```

**往返不变式**：导出 → 导入 → 再导出：
- 各来源的 `sourceDeviceId` **不变**（A 的数据仍属 A；顶层始终是**当次导出设备**自己的分量）；
- `sources[]` 的设备集合与各自分量**逐值相等**（不合并、不求和、不重归属）；
- 重复导入**幂等**（upsert 含 `sourceDeviceId` + `seq`，行数与 SUM 不变）；
- 不同来源的重叠会话**互不覆盖**（PK 含 `sourceDeviceId`）；
- **数据写入与账本同事务**（CR-27 的 `mergeAccumulate` 事务边界不回退）。

### 5.2 事件行携带 `seq`

`unlock_event` / `notification_event` 的 DTO 增加 `seq`（现 DTO 无任何事件级 id，
`BackupModels.kt:88` 一带只有 `occurredAtMs` 等字段）：导出写 `seq`，导入按
`(sourceDeviceId, occurredAtMs, type, pkg, seq)` upsert；旧备份无 `seq` → 按 5.1 规则
在导入时按文件内顺序重新编号（同一文件重复导入得同一编号 → 幂等）。

### 5.3 **[R2]** 兼容性三层判定（二审：不许只凭结构相似宣称兼容）

| | 旧 App 读 schema 6 | 新 App 读 schema ≤5 |
|---|---|---|
| **能解析** | ✅ `Json { ignoreUnknownKeys = true }`（`BackupModels.kt:143/146`）忽略 `sources`/`seq`，顶层照常读 | ✅ `sources` 缺省空，整体按 §5.1 规则归属 |
| **能展示** | ⚠️ **部分**：顶层只是**导出设备的分量**，旧 UI 会把它当总量显示（少算其他来源） | ✅ 完整（旧备份无分量概念） |
| **能正常导入** | ❌ **不能**：`sources[]` 被静默丢弃，其他来源与 `'__legacy__'` 分量**丢失** | ✅ 能 |

**结论**：schema 6 导出**不保证**被旧版本完整导入。导出 UI 必须提示：
「备份包含多设备分量，旧版本导入会丢失非本机来源数据」。
新 App 对 ≤5 的导入**完全兼容**：无 `sources` → 全部数据按 §5.1 派生规则归属；
无 `device.id` → `'__legacy__'`（**绝不伪装成当前设备**，裁决 2/3）。
