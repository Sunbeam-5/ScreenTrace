## 1. 项目目标

做一个 Android App：**Shizuku 授权后，自动拉取系统 UsageStats 数据，解析并在 App 内可视化屏幕使用时间**（每日时长、时段分布、应用排行、趋势、日历）。核心功能全程本地、离线、无账号；唯一例外是用户可选的云同步（§5.10），仅手动或按频率自动触发时联网。

背景事实（已在真机 vivo 验证）：
- 数据在系统 `usagestats` 服务里，`adb shell dumpsys usagestats` 可全量导出（约 2.4MB 明文 + 13MB checkin）；
- 普通 App 的 `dumpsys` 会被拒（缺 `android.permission.DUMP`），但 **Shizuku 以 shell(uid 2000) 身份执行即可**；
- 系统只保留约 **10 个滚动日**的每日统计文件，所以必须至少每 9 天拉取一次（建议每天）；
- 系统「健康使用设备」界面的数字与事件解析结果逐日误差 ≤3 分钟，可作为对账基准。

## 2. 数据来源与拉取

### 2.1 主通道：Shizuku
- 依赖：`dev.rikka.shizuku:api:13.1.5`、`dev.rikka.shizuku:provider:13.1.5`（或最新）。
- 首次启动引导用户：启动 Shizuku（无线调试或 root）→ 本 App 请求 Shizuku 权限（弹窗授权）。
- 授权后通过 `Shizuku.newProcess` / `ShizukuBinderWrapper` 执行：
  - `dumpsys usagestats --checkin` → 机器可读格式（毫秒时间戳），**主数据源**；
  - `dumpsys usagestats` → 明文格式（补当天的 "In-memory daily stats"，今天的数据还没写进磁盘日文件）。
- 降级通道：声明 `android.permission.PACKAGE_USAGE_STATS`，引导用户在 设置→特殊访问→使用情况访问 中授权，用 `UsageStatsManager.queryUsageStats/queryEvents` 取同源数据（注意 OEM 可能限制，vivo 实测接口开放但保留此降级以防万一）。
- 拉取时机：App 打开时（节流 30 分钟内不重复）+ WorkManager 每日一次（约束：充电/任意网络不限，本地操作）。
- 每次拉取全量解析后**合并**进本地库（见 §4），系统滚动删除不影响 App 内历史。

### 2.2 原始数据结构（vivo 实测，AOSP 同源）

`--checkin` 输出（主源）：
- 用户分区：按 `user=0 / user=666 / user=999` 分块；**只取含 >50 个包的区间**（真人使用），user=666/999 是后台服务账户（2–7 个包、时长为 0），忽略。
- 统计区间行：`beginTime=(\d+) endTime=(\d+)`（毫秒），每个区间内若干：
  - `package=<pkg> totalTimeUsed=<ms> lastTimeUsed=<ms> ... appLaunchCount=<n>`
  - 屏幕聚合行：`screen-interactive: <N>x for <ms>`
- 事件行（**核心**）：`time=<ms> type=<TYPE> package=<pkg>`
  - 本机输出英文类型名；AOSP 标准 checkin 可能输出数字类型，对照：
    ACTIVITY_RESUMED=1、ACTIVITY_PAUSED=2、ACTIVITY_STOPPED=23、SCREEN_INTERACTIVE=15、SCREEN_NON_INTERACTIVE=16、KEYGUARD_SHOWN=17、KEYGUARD_HIDDEN=18。
- **坑**：文件尾部还有 Broadcast events / Notification events / 已安装包列表，解析只认上面三种行的正则，不要整段混读。

明文格式（补今天）：
- `In-memory daily stats` 段（今天 22:58 滚动日界起）：`package=<pkg> totalTimeUsed="<H:MM:SS 或 M:SS>" ... appLaunchCount=<n>`，还有 `screen-interactive: <N>x for "<H:MM:SS>"`。
- `Last 24 hour events` 段：`time="<YYYY-MM-DD HH:MM:SS>" type=<TYPE> package=<pkg>`（秒级精度）。
- **坑 1**：`totalTimeUsed="54:01"` 两段式是 **分:秒**，三段式才是 时:分:秒。
- **坑 2**：明文事件（秒级）与 checkin 事件（毫秒）重叠，合并时按 `(毫秒/1000 取整, type, pkg)` 去重。

## 3. 解析算法（照抄 `parse_usage3.py`，已与系统 UI 对账）

输入：两份 dump 文本；输出：日汇总 + 小时矩阵 + 应用排行（样例见 `report_data.json`）。

1. **事件去重**：`set[(ts//1000, type, pkg)]`，再按 ts 排序。
2. **锁屏区间**：`KEYGUARD_SHOWN→KEYGUARD_HIDDEN` 配对得区间列表 `kg`（初始视为解锁态）。
3. **亮屏区间**：`SCREEN_INTERACTIVE→SCREEN_NON_INTERACTIVE` 配对得 `screen_intervals`；末条未闭合则截到最后一事件。
4. **日界与切分**：按设备时区自然日（00:00）把每个亮屏区间 `split_by_day` 切开；每片再切进小时格。
5. **指标**（逐日）：
   - `screen` = 亮屏分钟数；`screen_unlock` = 亮屏减去与 `kg` 重叠部分（`sub_kg`）——**这是"使用时长"的对外口径**（与系统 UI 误差 ≤3 分钟）；
   - `unlocks` = 当日 `KEYGUARD_HIDDEN` 次数；`launches` = `ACTIVITY_RESUMED` 次数；
   - `hour_matrix[day][hour]` = 各小时使用分钟（用 `screen_unlock` 口径）；
   - **最长连续** = 单个 `sub_kg` 后的亮屏区间最大分钟数（今日页"最长连续"卡片用）。
6. **应用时长**：不从事件配对算，直接用系统自己的区间聚合（`totalTimeUsed`/`appLaunchCount`），按区间归属日汇总；当天用 In-memory 段补上。多用户区间只取真人区间（§2.2）。
7. **展示名**：优先 `PackageManager.getApplicationLabel`，失败回退内置映射表（`parse_usage3.py` 的 `NAMES` 表可整段搬走，含微信/B站/抖音/豆包/DSH Go 等 60+ 常见包名中文名）。
8. **已知口径差**（写进 App 的"关于/说明"页）：
   - 应用时长相加 > 总使用时长：分屏/小窗/画中画重复计时，系统数据固有；
   - 系统日界是滚动的（约前一日 22:50–当日 22:50），App 用自然日重算事件口径，与系统日文件有 ±3 分钟/日出入；
   - 11/8 实测约 20 分钟口径差（系统 UI 自己的算法），属正常误差。

## 4. 数据模型（Room / SQLite）

```
day_summary(date PK, screen_min, screen_unlock_min, unlocks, launches, longest_session_min, pulled_at)
app_usage(date, pkg, name, minutes, launches, category, PK(date,pkg))
hour_usage(date, hour, minutes, PK(date,hour))
pull_log(id, pulled_at, source, ok, note)
```
- 合并策略：同 `(date)` 重拉时覆盖/取较大值；历史只增不删。**从备份恢复（本地文件或坚果云下载）选择「合并本地」时，复用同一策略：同日数据取各字段较大值，不产生重复计数。**
- `category`：内置分类（视频娱乐/社交沟通/AI 助手/工具效率/游戏/购物/其他）按包名映射，允许用户改（排行页图例着色用）。用户对分类的修改纳入备份与同步范围。
- 备份/同步的 JSON 结构与版本字段见 §5.10，解析与 UI 均不感知该文件格式，只有备份模块读写它。

## 5. UI 规范（v2.1 统一设计系统，本节为实现与验收依据）

### 5.1 参考边界与统一目标

保留 `nsh07/Tomato` 的深墨绿、无描边 tonal 分层、胶囊形状、细线圆环、悬浮导航与日历视觉语言；参考 Apple「屏幕使用时间」的摘要层级、Android「数字健康」的直接数据入口，以及 [Material 3 的可用性原则](https://m3.material.io/foundations/usability)：每页一个视觉重点、减少同权重信息、用留白分组，不堆叠装饰。

- `screen-time-ui-tomato.html` 用于理解布局和交互，不再作为唯一真源；与本节冲突时以本节为准。`screen-time-ui-prototype.html` 为 v1，仅作对照。
- Tomato 为 GPL-3.0，只参考视觉与交互形态，不复制源码；截图仅用于离线理解风格。
- 统一不是减少功能，而是让同类信息使用同一组件、同一尺寸、同一格式和同一状态。**不得在各页面另创颜色、圆角、卡片样式、日期格式或图表规则。**

### 5.2 页面骨架与布局节奏

所有主页面共用 `ScreenScaffold + AppHeader + ContentColumn + FreshNavBar`：

- 页面左右安全边距 20dp；内容区顶部与标题区间隔 8dp；卡片间距 12dp；卡片内分组间距 20dp；内容底部预留 112dp，保证悬浮导航不遮挡最后一张卡片。
- `AppHeader`：左侧页面标题 + 当前日期/区间副标题；右侧固定为「日期、界面风格、设置」三个图标按钮。按钮视觉圆形 40dp，实际点击区域至少 48dp，统一使用 Material Symbols Rounded 风格图标。
- 主页面无返回键。排行、设置等二级页使用「返回 + 标题」顶部栏；排行保留日期按钮，底部导航保持「今日」选中但不允许在二级页重复触发导航堆栈。
- 卡片统一：无描边、无阴影、`surface` 背景、圆角 24dp、内边距 20dp。tonal 卡圆角同为 24dp，内边距 16dp；不得再出现 22/26/38dp 等页面自定义卡片圆角。
- 间距只使用 4dp 基数：4 / 8 / 12 / 16 / 20 / 24 / 32dp。360dp 宽屏不得横向溢出；更宽屏幕内容最大宽 520dp 并居中，不把卡片和柱图无限拉宽。
- 每页最多一个 hero 大数字区域、一个主图表区域。说明文字只解释口径或引导操作，不写重复标题和装饰性鸡汤。

### 5.3 字体、图标与数字格式

统一使用系统字体和 `sp`，不在组件内另设字号：

| Token | 字号/字重 | 用途 |
|---|---|---|
| `pageTitle` | 24sp / 700 | 页面标题 |
| `sectionTitle` | 18sp / 700 | 卡片标题、设置组标题 |
| `heroNumber` | 40sp / 700，字距 -0.04em | 圆环时间、唯一核心大数字 |
| `metricNumber` | 26sp / 700 | tonal 卡数值 |
| `body` | 14sp / 400 | 正文、列表主文案 |
| `label` | 12sp / 500 | 辅助说明、坐标、图例 |
| `button` | 14sp / 600 | 按钮、segmented |

- 行高约为字号的 1.25–1.4 倍；大数字使用等宽数字特性（可用则启用），避免刷新时横向跳动。图标统一 22dp，应用图标 42dp、圆角 15dp，优先真实应用图标，失败再用首字母占位。
- 圆环中心固定 `H:MM`，下方固定「小时 : 分钟」。其他中文时长：≥1 小时显示「X小时Y分钟」（整小时省略 0 分钟），不足 1 小时显示「X分钟」，零显示「0分钟」；坐标轴可用 `1h/2h`，不得混用 `4h 32m`、`4:32`、`4小时32分` 三种正文格式。
- 全宽卡（`MetricCard` 等）时长数值采用「数字 + 小单位」排版（2026-11-10 增补）：内容格式仍为「X小时Y分钟 / X分钟 / 0分钟」，拆为**同一个 Text 的 `AnnotatedString` 两段**——数字 26sp/700（等宽数字 tnum、字距 -0.02em）+ 单位 13sp/500（不加字距）；数字到单位间距 4dp、单位到下一个数字 12dp。**不得用 Row 拼接两个 Text**（基线不齐、1.3 倍缩放错位、中途断行）。与圆环中心的 `H:MM` 并存、各有适用位置：圆环空间小用 `H:MM`，全宽卡用「数字 + 小单位」；不得出现第三种时长形态。可用宽度不足时（超窄屏 / 超大字体）整体降一档字号（数字 24sp / 单位 12sp），不截断数字、不省略单位。
- 对比行（「较昨日增加/减少 X 分钟」等）使用 14sp/600 文字 + 12dp 箭头图标，颜色用 `primary`；增减方向必须由箭头形状表达，不得只靠颜色（§5.4）。
- 对比文案统一为「较昨日增加/减少 X 分钟」或「较上一区间增加/减少 X%」；无对比数据时显示「暂无上一周期数据」，不得显示 0%。

### 5.4 颜色与九套主题

所有组件只能消费语义 token：`background / surface / surfaceVariant / onSurface / onSurfaceVariant / onSurfaceMuted / primary / onPrimary / primaryContainer / onPrimaryContainer / secondaryContainer / onSecondaryContainer / navSurface / buttonSurface / chart1~5 / track / month1~3 / heat0~4 / scrim / error`。禁止组件直接引用 `FreshColors.GreenDeep`、十六进制颜色或 `Color.White`。

- 浅色默认：背景 `#F4F7F3`、卡片 `#FFFFFF`、正文 `#1D322B`、主色 `#1B6B5A`；tonal 双卡 `#A9E7C9` / `#C6E9FA`；导航底 `#B9EDD5`；轨道 `#EAF2EC`。九套浅色主题沿用下表主色与 HTML 中同名单色板，但必须先映射为上述语义 token。
- 每套主题必须同时提供浅色和深色调色板。深色不是简单反色：背景接近中性深色、卡片略亮、主色提高亮度，tonal 卡文字与背景分别使用对应 `on...` 角色。
- 普通正文和关键图例对比度 ≥4.5:1；大号文字和必要图形 ≥3:1。弱化色只用于次要信息，不得用于日期数字、关键刻度或错误状态；颜色不能作为区分系列的唯一手段，必须同时提供文字标签。
- `onSurfaceMuted` 为「数字 + 小单位」排版的单位色专用 token（2026-11-10 增补）：由前景色**向所在卡片背景色混合派生**，浅色混合比例上限 30%、深色上限 46%，并以对比度 ≥4.5:1 为硬约束——混合超限即破 4.5 时必须降低混合比例。白卡（`surface`）上的取值：浅色 `#61706B`（5.20:1）、深色 `#8E9894`（4.61:1）；tonal 卡上按同一规则相对容器色派生。禁止照抄 Apple 系统灰 `#8E8E93`（白底仅 2.97:1）。其余弱化文案仍用 `onSurfaceVariant`。

### 5.5 导航、弹层与通用组件

- 底部悬浮胶囊导航固定 3 项「今日 / 统计 / 日历」。未选中项 52dp 仅图标；选中项 spring 展开至 150dp 并显示名称；容器内边距 6dp、项间距 4dp。动画 180–250ms，开启系统减少动画时改为淡入淡出。
- 日期和界面风格均使用统一的 **Modal Bottom Sheet**，不再一个下拉面板、一个悬浮卡片。统一 scrim、顶部 28dp 圆角、拖动条、标题和关闭行为；点击面板内部不得误关闭，点外部或切页时关闭。
- 风格面板用 3×3 色点网格，色点下显示名称，当前项用勾选和文字共同标识；深浅色与动态取色在设置页配置。
- `PrimaryButton / SecondaryButton` 高度 48dp、全胶囊；每屏最多一个主按钮。`SegmentedControl` 高 40dp，选中项使用 `primary + onPrimary`，未选中项使用透明底 + `onSurfaceVariant`。
- `MetricCard` 固定为「标签 / 数值 / 可选一句说明」；双卡等宽、同高、同一字号，不得一页出现多种数值排版。数值排版按 §5.3「数字 + 小单位」执行：数字用 `onSurface`、单位用按 §5.4 规则派生的单位色（白卡即 `onSurfaceMuted`）；说明为对比文案时按 §5.3 对比行规格渲染（14sp/600 + 12dp 箭头 + `primary`）。
- `SegmentedBar` 每段必须能在下方图例中找到「名称 + 时长或百分比」；零权重段不绘制，空数据显示统一空态，不能传 0 或负权重给布局。
- 加载使用保留原布局的骨架或进度指示；错误用文字 + 重试按钮；无数据用同一张 `EmptyState` 组件。禁止白屏、只弹 Toast 后清空内容、或把无数据伪装成真实的 0 分钟。

### 5.6 日期选择与统一统计语义

使用单一 `DateSelection` 状态：`Day(date)` 或 `Range(startDate, endDate)`。冷启动默认今天；旋转、切页和进入排行时保持，清除筛选恢复今天。日期全部为设备本地时区自然日。

- 快捷项：今天、昨天、近 7 天、近 30 天、本月；指定单日使用 DatePicker；自定义区间使用 DateRangePicker，反选自动交换，最多 366 个自然日。
- 应用后显示统一筛选胶囊条「范围 · 共 N 天 · 有记录 X 天」，带清除按钮。四个数据页面读取同一状态，不允许趋势 segmented 与顶部筛选各持有一套日期。
- 「有记录」指数据库存在该日 `day_summary`，与真实使用 0 分钟区分。单日/区间完全无记录时，不应用新筛选，保留原视图并提示「该时段尚无数据，请先拉取」；部分有记录时正常展示，并显示覆盖天数。
- 单日：使用、解锁、最长连续直接取当日；圆环进度 = 当日使用/每日目标；对比前一自然日。
- 区间：今日页和趋势页主数字均为**有记录日的日均使用**，日均解锁同理；圆环进度 = 区间日均使用/每日目标；对比此前等长区间且有记录日的日均值。排行显示区间累计；最长连续取区间内最大值。
- 区间 `SUM` 包含全部有记录行；`AVG` 的分母只包含有记录日，不能把未拉取日当 0 拉低平均。趋势仍为每个所选自然日生成数据点：有记录按真实值，无记录高度为 0 并在详情标「无记录」。
- 日历以所选区间结束日为锚点：月视图跳到该月，年视图显示截至该日的过去 20 周；streak 以 `screen_unlock_min > 0` 的自然日连续段计算截至锚点的全量历史，「最久的一天 / 低于2小时」只统计当前筛选区间内的有记录日，其中真实 0 分钟计入「低于2小时」、无记录日不计入。
- 今日页夜间与趋势「22–06」统一为 **22:00（含）至次日 06:00（不含）**；其他时段依次为 06–12、12–18、18–22。

### 5.7 四个数据页面

**今日**：固定三个内容组，不额外堆叠卡片。
1. hero 圆环卡：`H:MM`、每日目标进度、上一周期对比；
2. tonal 双卡：「解锁次数」「最长连续」；区间时第一张标签改为「日均解锁」，后者只显示 `longest_session_min`，**不显示无法从现有模型可靠得到的应用名**；
3. 「应用构成」卡：`app_usage` top 4 + 其他，显示名称和时长图例；卡内下方用一条 16dp 分隔间距放「日间 / 夜间」比值条；底部「查看全部应用」次按钮进入排行。

**统计**：
1. 趋势卡同时包含日均大数字、对比文案和柱图，不再拆成两个头卡；近 7 天/近 30 天 segmented 与顶部快捷筛选调用同一 `DateSelection`；
2. 柱图 1–7 天用 24dp 粗胶囊柱，8 天及以上用 7dp 细柱；每个自然日都有数据点。内容超宽时仅绘图区横向滚动，左侧刻度列固定，不压缩、不丢弃 31–366 天数据；
3. 刻度为 0 到「向上取整后的最大整小时」均分 4 档，最小量程 1h；刻度独占 32dp，柱图不与文字重叠。零使用和无记录均不画实体柱，通过详情文案区分；
4. 「时段分布」卡用同一 `SegmentedBar` 展示 06–12 / 12–18 / 18–22 / 22–06；tonal 双卡显示最久/最少的有记录日，洞察只在数据足够时生成，否则隐藏。

**日历**：
1. 连续记录 tonal 卡 + 月/年 segmented + 对应日历卡 + tonal 双卡，顺序固定；
2. 月视图周一起始，7 列 34dp、间距 4dp；前后月补位显示灰色日期。有使用日期按统一阈值分 3 档：`(0,2h) / [2h,4h) / ≥4h`，真实 0 分钟与无记录均不着色，但详情文案分别显示「0分钟」和「无记录」；
3. 同一行连续有使用日期合并胶囊，但每一天仍保留自己的色档，可用相邻色块或分段实现，不得整组继承第一天颜色；单日圆角 10dp，连续组外轮廓全胶囊；
4. 年视图为 20 周 × 7 天，9dp 格子、3dp 圆角、3dp 间距，含星期列总宽约 252dp；超窄屏允许网格区横向滚动。色阶固定为空档（真实 0 或无记录）、`(0,2h) / [2h,4h) / [4h,6h) / ≥6h`，点击格子用底部详情或弹层显示真实日期、记录状态与时长。

**排行**：
1. 顶部返回，摘要卡显示所选单日/区间累计、应用数及分类构成；分类图例必须有名称和百分比；
2. 列表按 `minutes` 降序，默认 top 20；每项为真实图标、名称、时长和 9dp 进度条，点击区域至少 48dp；
3. 「显示全部 N 个应用」按钮必须真实展开或进入完整列表，展开后变为「收起」；应用详情为可选增强，不作为首版验收阻塞项。

### 5.8 设置与系统状态

设置从所有主页面的统一顶部入口进入，分四组卡片，不占用底部导航：

- 「目标与同步」：每日目标、拉取频率、最近成功拉取时间、手动拉取；
- 「权限与数据」：Shizuku 状态与重试、使用情况访问降级授权、应用分类管理（按包名查看并修改分类）、数据覆盖说明、导出 HTML 报告；
- 「备份与同步」：导出数据（JSON 完整备份 / CSV 明细）、从本地文件恢复、云端同步（WebDAV / Google Drive 的配置与登录、手动上传与恢复、自动同步频率与仅 Wi-Fi、上次同步时间与结果），详见 §5.10；
- 「外观」：九套风格、浅色/深色/跟随系统、跟随壁纸动态取色；
- 「关于」：§3 的统计口径差、应用时长相加可能大于总时长、本地存储及「仅手动同步时联网」说明。

首次启动使用分步向导（欢迎与主题 → Shizuku 授权 → 目标与拉取频率 → 备份与云端同步，可跳过），每步为状态卡片：显示当前检测结果、下一步操作和「稍后在设置中配置」；向导风格参考 Shizuku 的状态机式授权引导与 Fushi 的 onboarding。首次启动、未授权、拉取中、拉取失败、dump 为空、部分历史和完全无数据均需有明确状态。已有历史时拉取失败应保留旧数据并在顶部显示内联错误；首次无数据时才显示全页引导。导出使用系统 SAF 创建本地 HTML 文件，不需要网络权限或外部在线模板。

### 5.9 可访问性与验收基线

- 所有图标按钮具备 `contentDescription`；装饰图形不对读屏重复播报；图表提供摘要和逐点详情，不只支持悬停。
- 点击目标至少 48dp；字体放大至 1.3 倍时标题、数值、按钮不裁切，卡片允许增高，不以固定高度硬压文本。
- 360dp 宽、深色模式、九套主题、空数据、超长应用名和 31/366 天区间均不得重叠或白屏；动画不阻碍点击，并尊重系统减少动画设置。

### 5.10 数据导出与云同步

备份与恢复是同一套流程，区别只在来源（本地文件 / 云端）。**恢复策略永远由用户在执行前二选一：覆盖本地 或 合并本地，不存在静默默认。**

**导出（本地，SAF）**
- 「导出 JSON 完整备份」：单文件 `screen-time-backup-YYYYMMDD-HHmm.json`，结构为 `{ schemaVersion, exportedAt, appVersion, settings, day_summary[], app_usage[], hour_usage[], pull_log[] }`。`settings` 含每日目标、九套主题/深浅色选择、应用分类修改、拉取频率；`schemaVersion` 首版为 1，未来结构变更必须递增。
- 「导出 CSV 明细」：`day_summary / app_usage / hour_usage` 三张表各一个 CSV（UTF-8 带 BOM，Excel 直接打开不乱码），列名与 §4 字段一致。
- 导出走 SAF `ACTION_CREATE_DOCUMENT`，不需要存储权限；导出前显示将包含的日期范围和记录条数。

**统一恢复流程（本地文件导入 / 云端下载共用）**
1. 读取并校验备份：JSON 解析失败、缺 `schemaVersion`、版本高于当前 App，分别给出明确错误，不进入后续步骤；
2. 展示备份摘要：导出时间、App 版本、数据日期范围、各表记录条数、是否含设置；
3. 用户选择恢复策略：
   - **覆盖本地**：红色警示文案「将删除本机全部统计数据后导入」，二次确认后清空四张表再导入；
   - **合并本地（默认高亮项）**：按 §4 合并策略逐日合并——`day_summary` 同日取 `screen_unlock_min` 较大的一行整体保留；`app_usage` 同 `(date,pkg)` 取 `minutes` 较大值并保留对应 `name/category`；`hour_usage` 同 `(date,hour)` 取较大值；`pull_log` 仅追加；**设置默认不导入**，另设勾选「同时恢复设置（目标/主题/分类）」；
4. 导入在单个事务中完成，失败整体回滚；完成后显示结果摘要（新增 X 天、更新 Y 天、跳过 Z 条）并返回设置页。

**云端同步（多后端，参考 Komikku/Fushi 的提供者模型）**
- 后端以「提供者」形式接入，首版两个：① **通用 WebDAV**（预置坚果云地址 `https://dav.jianguoyun.com/dav/`，可改成任意 WebDAV 服务）；② **Google Drive**（系统账号 OAuth 登录，App 不接触账号密码）。设置页为每个提供者一张卡片：连接状态、上次同步时间与结果、「测试连接 / 登录 / 退出」按钮；结构上预留 Dropbox / OneDrive 扩展位。
- WebDAV 配置项：地址、账号（坚果云为邮箱）、密码（**坚果云「第三方应用授权密码」，不是登录密码**，配置页附一行获取指引文案）、远端目录（默认 `/screen-time/`）。
- Google Drive：OAuth 授权范围仅请求 Drive 文件访问；备份存应用数据目录（`appDataFolder`，用户不可见、不污染网盘列表）或用户指定文件夹；退出登录即清除本地令牌。Google 服务在部分网络环境不可达时按统一失败处理，不得影响 WebDAV 通道和本地功能。
- 手动同步：「上传」生成当前完整备份 → 覆盖远端固定文件 `screen-time-backup.json`；「恢复」下载远端备份 → 进入统一恢复流程（同样二选一覆盖/合并）。固定文件名与 JSON 格式对所有提供者一致。
- **自动同步**：频率可选「关闭（默认）/ 每次成功拉取后 / 每 1 天 / 每 3 天 / 每 7 天」，在每日系统数据拉取成功后自动上传；「仅 Wi-Fi 下同步」开关默认开启。自动备份使用带时间戳的文件名（`screen-time-backup-auto-YYYYMMDD-HHmm.json`），**仅保留最近 5 份**；手动上传的固定文件不受清理影响。首版不做多设备冲突检测和增量同步，远端被其他设备更新时以下载时的合并策略解决。
- 进度与状态：上传/下载/恢复进行中在对应卡片显示内联进度（参考 Komikku 的进度 banner 思路，不阻塞其他页面操作）；完成后更新「上次同步」；失败分类提示（网络不可达、401 鉴权、404 目录不存在、格式错误、远端空间不足）。

**网络边界**：除手动触发或按本节频率自动触发的云同步请求外，App 不发起任何网络请求；无统计、广告、崩溃上报 SDK。飞行模式下同步入口可见，点击提示「当前网络不可用」。

## 6. 技术栈与工程要求

- Kotlin + Jetpack Compose + Material3，minSdk 26、target 34+；使用稳定 BOM 和稳定 Material3 API，不为追求 Expressive 外观引入实验性组件。依赖限 Shizuku api/provider、WorkManager、Room、DataStore、OkHttp（云同步 HTTP）、Google Sign-In / Credential Manager（仅 Google Drive 登录用）及 JSON 序列化库；图表优先自绘 Canvas / Box。**仅声明同步必需的 `INTERNET` 权限，除 §5.10 的云同步请求（手动或按频率自动触发）外不得发起任何网络请求。**
- 推荐单向数据流：`Repository -> ViewModel -> UiState -> Compose`。Composables 不直接执行 Room 查询、日期聚合或业务计算；四页共享同一个 `DateSelection`，筛选、加载、错误和数据覆盖天数统一放入各自 UiState。
- 主题必须实现 `FreshPalette` + `CompositionLocalProvider`，接口为 `ScreenTimeTheme(variant, darkTheme, dynamicColor)`；九套主题的浅色/深色调色板集中在主题层。业务组件只能读 `LocalFreshPalette` 或 MaterialTheme 语义色，禁止静态引用 `FreshColors.*`。主题、目标、拉取频率用 DataStore 持久化；日期筛选冷启动不持久化。
- `compose-uikit/` 只能作为起点，不能原样视为完成品：`CapsuleBarChart` 补固定刻度列、动态量程、零值和横向滚动；`HeatmapCalendar` 改为 9dp/3dp 并补点击详情；`MonthCalendar` 保留每日色档、单日 10dp 和前后月灰字；所有组件去除硬编码颜色并支持深色。
- 卡片和文本尽量使用约束尺寸而非固定高度；图表必须先用 360dp 可用宽度计算布局，再决定滚动，不允许靠缩小字号、负间距或超出卡片解决拥挤。
- Room 查询与聚合严格按 §5.6：缺失日不等于真实 0 分钟；区间日均只除以有记录天数。单日、区间、上一等长周期、记录覆盖数由统一领域计算器产生，避免四页各自实现出不同结果。
- 解析器写成纯 Kotlin 模块（两段 dump 文本 → 数据类）。§3 的 `hour_matrix` 使用 `screen_unlock` 口径，移植时不得把参考 Python 中直接累加亮屏片长的写法当作正确口径；小时合计应与同日 `screen_unlock` 在分钟取整误差内一致。英文与数字事件类型先归一化再处理。
- 原 `sample-checkin.txt` / `sample-human.txt` 是格式切片，**不得修改，也不得宣称它们能单独复现完整 `report_data.json`**。测试分两层：用原切片做正则/格式测试；另在测试源码或新增测试资源中建立完整、可执行的 golden fixtures，覆盖 `M:SS`、毫秒/秒事件去重、数字事件类型、跨零点、未闭合亮屏、锁屏扣减及小时合计。
- 设置与状态：每日目标、授权状态、最近成功拉取、手动重试、导出和数据说明均接真实状态；不能只画设置页。HTML 报告导出通过 SAF `ACTION_CREATE_DOCUMENT` 生成自包含文件，无 CDN、在线字体或网络请求。
- 备份与同步：定义统一 `SyncProvider` 接口（`testConnection / upload / download / disconnect`），WebDAV 与 Google Drive 各为一个适配器；新增云端（Dropbox/OneDrive 等）只允许新增适配器，不改备份格式与恢复流程。本地导出/导入与云端上传/下载共用同一 JSON 序列化器和同一恢复流程（§5.10），不允许两套合并逻辑。WebDAV 用 OkHttp 手写 PROPFIND/MKCOL/PUT/GET 最小子集或引入 Sardine；Google Drive 登录后经 Drive REST v3 由 OkHttp 上传/下载（`appDataFolder` 或用户指定文件夹）。请求在 IO 线程执行、超时 15 秒；坚果云应用授权密码与 Google OAuth 令牌用 EncryptedSharedPreferences 存储，禁止明文写入数据库、日志或备份 JSON；覆盖/合并恢复均在单事务中完成，失败回滚并保留原数据。
- 自动同步：在每日 WorkManager 拉取任务成功后按 §5.10 频率设置链式触发上传；任务约束为「网络可用」（开启「仅 Wi-Fi」时 `NetworkType.UNMETERED`），指数退避重试最多 3 次；每次成功后清理超出保留数量的旧自动备份；自动同步失败不弹窗，仅写入同步状态并在设置页展示。
- 错误处理：Shizuku 未启动/未授权显示引导；拉取中禁止重复任务；dump 为空或失败保留旧数据并记录 `pull_log`；所有写库合并在事务中完成，连续拉取不得重复计数；同步失败（网络/401/404/格式错误）不改动本地数据，仅在界面显示原因。
- 实施顺序固定为「语义色板与字体/间距 token → 共享 DateSelection 和领域计算器 → 通用组件 → 四个数据页面 → 设置与系统状态 → 测试」。不得先复制 HTML 占位数值再假装完成数据接线；未完成能力明确列为待办，不用假按钮或假数据掩盖。

## 7. 验收标准

1. **首次拉取**：冷启动能引导 Shizuku 授权并一键拉取，正常真机上 10 秒内显示今日真实数据；未启动、拒绝授权、空输出和失败均有对应状态，不白屏。
2. **数据口径**：解析结果与系统「健康使用设备」逐日对比，误差 ≤5 分钟（需求已注明的特殊口径差除外）；小时矩阵合计与同日 `screen_unlock` 在分钟取整误差内一致。
3. **真实数据接线**：今日、统计、日历、排行全部使用解析和 Room 数据，无硬编码业务数值；最长连续不显示无来源的应用名；排行「显示全部」真实可用。
4. **离线与持久化**：飞行模式下拉取已有数据、四页浏览、筛选、主题切换、设置、HTML/JSON/CSV 导出和从本地文件恢复可用（坚果云同步入口可见但提示网络不可用）；重启后历史、目标、分类修改和外观设置不丢，连续拉取不重复计数。
5. **解析单测**：`M:SS`、秒级事件去重、跨零点切分三个原必测项全部通过，并覆盖数字事件类型、锁屏扣减、未闭合亮屏及小时合计；原切片不被修改，golden fixtures 可独立重复执行。
6. **统一页面骨架**：四页使用同一标题栏、间距、24dp 无描边卡片、字体 token、数字格式（§5.3 双形态：圆环 `H:MM`、全宽卡「数字 + 小单位」，不得第三种）、弹层和空态；360dp 宽下无横向页面溢出，宽屏内容按 520dp 上限居中。
7. **导航与圆环**：悬浮胶囊导航只有今日/统计/日历 3 项，选中弹性展开名称、未选中仅图标；排行可进入并返回且保持导航状态；圆环 9dp 细线、圆头、inset 防裁切，中心为 `H:MM`。
8. **趋势图**：7/30 天切换改变柱体形态；左侧刻度独占 32dp 且量程随数据变化；零值不画实体柱；31 天和 366 天均可通过绘图区滚动查看全部日期，刻度固定、柱体不重叠、不丢数据。
9. **日历**：月/年视图可切换；月视图连续日期连成胶囊但保留每日色档，单日为 10dp 圆角，前后月日期为灰色；年视图 20 周、9dp 格子完整落在容器内，点击任一格显示真实日期与时长。
10. **主题与可访问性**：九套主题均有浅色/深色，切换后卡片、图表、导航、日历同步变色且不重新拉取数据、不改筛选；正文对比度 ≥4.5:1、必要大号文字/图形 ≥3:1；字体 1.3 倍和减少动画开启时无裁切或操作阻塞，图标按钮点击区 ≥48dp。
11. **日期与区间**：快捷、指定单日和自定义区间均写入同一状态；筛选条显示总天数和有记录天数，四页按 §5.6 重算，清除恢复今天；完全无记录时保留原筛选并提示，部分有记录时不把缺失日计入日均。
12. **设置与导出**：目标、拉取频率、授权重试、外观和数据说明均接真实状态；SAF 可导出自包含 HTML，断网打开不出现外部资源请求；分类修改入口和保存结果可见。
13. **数据备份与恢复**：可导出 JSON 完整备份（含 schemaVersion、四表和设置）与三张表 CSV；从文件恢复前展示备份摘要；「覆盖本地」有红色警示和二次确认，执行后本地仅剩备份内容；「合并本地」按 §4 策略执行，同日取较大值、不重复计数，设置默认不随恢复变更；导入失败整体回滚、原数据不变。
14. **云同步**：坚果云 WebDAV 可配置地址/账号/应用授权密码并测试连接，Google Drive 可完成 OAuth 登录与退出；401、404、断网分别有明确提示；上传后能从云端再次下载到同一文件；下载恢复同样提供覆盖/合并二选一；凭据与 OAuth 令牌不明文出现在数据库、日志或备份 JSON 中；同步期间断网不损坏本地数据；Google Drive 不可达不影响 WebDAV 通道与本地功能。
15. **自动同步**：开启后按所选频率（每次成功拉取后 / 每 1 / 3 / 7 天）在成功拉取后自动上传，遵守「仅 Wi-Fi」开关与系统网络约束；失败静默记录并在设置页显示原因，不弹窗、不丢数据；自动备份文件名带时间戳且仅保留最近 5 份，手动上传的固定文件不被清理。
