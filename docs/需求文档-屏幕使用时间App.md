## 1. 项目目标

做一个 Android App：**Shizuku 授权后，自动拉取系统 UsageStats 数据，解析并在 App 内可视化屏幕使用时间**（每日时长、时段分布、应用排行、趋势、日历、周/月/年总结，以及解锁次数与通知打扰的下钻明细），并提供目标超时提醒、应用使用限额与桌面小组件（均纯本地）。核心功能全程本地、离线、无账号；联网只有两个可选项：用户手动或按频率触发的云同步（§5.10），以及用户点击才发起的 AI 分析（§5.11，默认关闭）。

背景事实（已在真机 vivo 验证）：
- 数据在系统 `usagestats` 服务里，`adb shell dumpsys usagestats` 可全量导出（约 2.4MB 明文 + 13MB checkin）；
- 普通 App 的 `dumpsys` 会被拒（缺 `android.permission.DUMP`），但 **Shizuku 以 shell(uid 2000) 身份执行即可**；
- 系统只保留约 **10 个滚动日**的每日统计文件，所以必须至少每 9 天拉取一次（建议每天）；
- 系统「健康使用设备」界面的数字与事件解析结果逐日误差 ≤3 分钟，可作为对账基准。

## 2. 数据来源与拉取

### 2.1 主通道：Shizuku
- 依赖：`dev.rikka.shizuku:api:13.1.5`、`dev.rikka.shizuku:provider:13.1.5`（或最新）。
- 首次启动引导用户：启动 Shizuku（无线调试或 root）→ 本 App 请求 Shizuku 权限（弹窗授权）。
- 授权后通过 `Shizuku.newProcess` / `ShizukuBinderWrapper` 执行：
  - `dumpsys usagestats --checkin` → 机器可读格式（毫秒时间戳），**主数据源**；
  - `dumpsys usagestats` → 明文格式（补当天的 "In-memory daily stats"，今天的数据还没写进磁盘日文件）。
- 降级通道：声明 `android.permission.PACKAGE_USAGE_STATS`，引导用户在 设置→特殊访问→使用情况访问 中授权，用 `UsageStatsManager.queryUsageStats/queryEvents` 取同源数据（注意 OEM 可能限制，vivo 实测接口开放但保留此降级以防万一）。
- 拉取时机（CR-03 修订、CR-04 再修订）：① App 打开时（节流：上次成功 10 分钟内不重复；上次失败/空 dump 冷却 60 秒）；② **三个主页面（今日/统计/日历）支持下拉刷新**——用户手势触发的强制拉取，绕过节流；拉取中显示内联进度与顶部提示条，不遮挡已有内容、不切骨架。**排行与详情等二级页不加下拉手势**（与返回手势、图表横滑冲突；其数据与主页面同源，主页刷新即更新）（CR-04）；③ **手动下拉 60 秒轻冷却（CR-04）**：距上次成功拉取不足 60 秒时下拉只重读本地库并轻提示「刚刚已更新」，不再执行 dumpsys（全量约 15MB，防连点）；④ WorkManager 每日一次（约束：充电/任意网络不限，本地操作）。
- **手动下拉与自动同步的联动（CR-04 明确）**：手动下拉成功视为一次「成功拉取」——自动同步频率为「每次成功拉取后」时随之触发上传（受「仅 Wi-Fi」约束）；「每 1/3/7 天」频率按时间窗口判断，不因手动刷新提前或推迟。
- 每次拉取全量解析后**合并**进本地库（见 §4），系统滚动删除不影响 App 内历史。**CR-03：屏幕会话按「区间真并集」入库**——OEM（MIUI 实测）的事件缓冲是滚动窗口，单次 dump 只覆盖最近几小时，只做「同日取大」会让亮屏时长永久偏少（真机实测屏迹 11h09 vs 系统 13h50）；会话区间逐条入库、跨拉取取并集后重算日聚合（§3-10、§4），任何一次拉取见过的时段都计入，只增不减。
- 下拉刷新与常规拉取同一失败语义：保留旧数据 + 顶部内联错误 + `pull_log` 记录；未授权时不发起拉取，直接提示去授权（不画假进度条）。

### 2.2 原始数据结构（vivo 实测，AOSP 同源）

`--checkin` 输出（主源）：
- 用户分区：按 `user=0 / user=666 / user=999` 分块。**CR-02 勘误（真实 10 天 dump 实测）**：user=666 是 vivo 隐私空间、user=999 是手机分身（第二空间），均为**真人会主动切进去使用的独立空间**，应用数据与主空间独立——三个账户的区间 / In-memory / 应用事件**全部保留**，应用时长按 `(date,pkg)` 跨账户求和（原「>50 包过滤、忽略 666/999」的描述在真机上不成立，作废）。唯一需要收敛的是**系统级镜像事件**（SCREEN_*/KEYGUARD_*，各 profile 同源广播，实测三账户相加 ≈2.98×）：同 `type`+`package` 且 `|Δt| ≤ 1000ms` 视为同一物理事件跨账户去重；应用级事件（ACTIVITY_RESUMED / 通知等）各账户独立，保持毫秒多重集合不去重（同秒多条真实通知不丢）。
- 统计区间行：`beginTime=(\d+) endTime=(\d+)`（毫秒），每个区间内若干：
  - `package=<pkg> totalTimeUsed=<ms> lastTimeUsed=<ms> ... appLaunchCount=<n>`
  - 屏幕聚合行：`screen-interactive: <N>x for <ms>`
- 事件行（**核心**）：`time=<ms> type=<TYPE> package=<pkg>`
  - 本机输出英文类型名；AOSP 标准 checkin 可能输出数字类型，对照（CR-01 补全）：
    ACTIVITY_RESUMED=1、ACTIVITY_PAUSED=2、CONFIGURATION_CHANGE=5、USER_INTERACTION=7、SHORTCUT_INVOCATION=8、NOTIFICATION_SEEN=10、STANDBY_BUCKET_CHANGED=11、NOTIFICATION_INTERRUPTION=12、SCREEN_INTERACTIVE=15、SCREEN_NON_INTERACTIVE=16、KEYGUARD_SHOWN=17、KEYGUARD_HIDDEN=18、FOREGROUND_SERVICE_START=19、FOREGROUND_SERVICE_STOP=20、ACTIVITY_STOPPED=23。
  - **通知事件（CR-01 实测确认）**：`NOTIFICATION_INTERRUPTION`（应用发布可打断通知，含视觉/声音打扰）与 `NOTIFICATION_SEEN`（用户查看了通知）都在 checkin 事件流与明文 `Last 24 hour events` 中，带毫秒/秒级时间戳与包名，部分带 `channelId`。**不需要通知监听权限即可统计历史通知**；但语义是「打扰 / 已查看」，静音与静默渠道通知不一定产生 `NOTIFICATION_INTERRUPTION`，UI 不得宣称是「全部收到的通知」。
- **坑**：文件尾部还有 Broadcast events / Notification events / 已安装包列表，解析只认上面三种行的正则，不要整段混读。

明文格式（补今天）：
- `In-memory daily stats` 段（今天 22:58 滚动日界起）：`package=<pkg> totalTimeUsed="<H:MM:SS 或 M:SS>" ... appLaunchCount=<n>`，还有 `screen-interactive: <N>x for "<H:MM:SS>"`。
- `Last 24 hour events` 段：`time="<YYYY-MM-DD HH:MM:SS>" type=<TYPE> package=<pkg>`（秒级精度）。
- **坑 1**：`totalTimeUsed="54:01"` 两段式是 **分:秒**，三段式才是 时:分:秒。
- **坑 2（CR-01 修正）**：明文事件（秒级）与 checkin 事件（毫秒）重叠。用于**区间配对**（亮屏/锁屏）的事件可继续按 `(毫秒/1000 取整, type, pkg)` 秒级去重，不影响区间；但用于**计数**的解锁/通知事件必须保留毫秒精度——实测同一秒内同一应用可发出多条真实通知（样本 10 天内秒级 set 去重会吞掉约 268 条打扰、352 条已查看），不得按秒 set 去重。多源合并时按 `(秒, type, pkg)` 分组，取两组来源各自条数的**较大值**（多重集合策略），而非普通 set。

### 2.3 OEM 差异与多机型适配（CR-04）

解析正确性依赖的每一项假设都已在两台真机上出现过反例，多机型适配因此是一等功能而非测试附属。

**已实测差异矩阵**（新机型实测后须增补本表）：

| 维度 | vivo（API 36） | 小米 HyperOS 3（Android 16，批 6e 实测） | AOSP 参考 |
|---|---|---|---|
| `dumpsys usagestats --checkin` | 输出完整 CSV 数据（区间+事件，约 13MB） | **只输出约 0.5MB 元信息**，无 `totalTimeUsed`/事件；可用数据全在不带参数的明文里 | 输出 CSV 数据 |
| 明文 `dumpsys usagestats` | 补当天 In-memory 段 | **主数据源**（3.7–4.2MB 含全量区间与事件） | 补当天 |
| user 分区语义 | user=666 隐私空间、user=999 手机分身（真人使用，全收） | 同左思路：未知账户一律保留 | work profile 通常 user≥10 |
| 系统级镜像事件 | SCREEN_*/KEYGUARD_* 三账户各记一遍（≈2.98×），按「同 type+pkg、±1000ms」收敛 | 同策略 | 同策略 |
| 通知事件 INTERRUPTION/SEEN | 有（CR-01 实测） | 待验证；**缺失时通知详情显示「当前机型不提供该数据」，不得画 0** | 有 |
| 滚动日界/事件缓冲窗口 | 约前一日 22:50–当日 22:50 | 滚动窗口更短（单次 dump 只见最近几小时，CR-03 会话并集为通用解） | 因版本而异 |

**工程规则**：

1. **形态识别不假设单一格式**：`DumpShape` 判定用带格式细节的独有特征（`^Days:`、`beginTime=<数字>`、无引号毫秒等），并提供「有数据/无数据」判定；**谁有数据谁当主输入**，两路均无数据才判通道失败，`pull_log.note` 记录两路形态。
2. **优雅降级**：任一数据类在特定机型缺失时，对应功能显示诚实「不支持/无数据」态并说明原因，绝不伪造 0 或沿用他机数据。
3. **收敛参数自适应**：镜像事件收敛窗口（±1000ms）为默认值；拉取时可自检三账户系统事件重复率，显著偏离 ≈3× 时在 `pull_log` 记录告警，供矩阵修订。
4. **新机型接入流程**：真机双 dump 留样 → 新建 golden fixtures → 与系统「健康使用设备」对账 → 登记本矩阵；**未实测机型不得宣称支持**。
5. **测试**：fixtures 至少覆盖 vivo 与 HyperOS 两种 dump 形态；DumpShape 判定、「谁有数据谁主导」分支、镜像收敛均有单测。

## 3. 解析算法（照抄 `parse_usage3.py`，已与系统 UI 对账）

输入：两份 dump 文本；输出：日汇总 + 小时矩阵 + 应用排行（样例见 `report_data.json`）。

1. **事件两级处理（CR-01 修正）**：
   - **区间层**（亮屏/锁屏配对用）：`set[(ts//1000, type, pkg)]` 秒级去重，再按 ts 排序；
   - **计数层**（解锁/通知事件用）：保留毫秒精度不去重；checkin 与明文两源重叠时按 `(秒, type, pkg)` 分组取两边条数较大值（§2.2 坑 2）。
2. **锁屏区间**：`KEYGUARD_SHOWN→KEYGUARD_HIDDEN` 配对得区间列表 `kg`（初始视为解锁态）。
3. **亮屏区间**：`SCREEN_INTERACTIVE→SCREEN_NON_INTERACTIVE` 配对得 `screen_intervals`；末条未闭合则截到最后一事件。
4. **日界与切分**：按设备时区自然日（00:00）把每个亮屏区间 `split_by_day` 切开；每片再切进小时格。**入库日期键一律为 `YYYY-MM-DD` 完整格式，由设备本地时区计算，不得使用 `MM-DD` 短格式或硬编码年份/时区。**
5. **指标**（逐日）：
   - `screen` = 亮屏分钟数；`screen_unlock` = 亮屏减去与 `kg` 重叠部分（`sub_kg`）——**这是"使用时长"的对外口径**（与系统 UI 误差 ≤3 分钟）；
   - `unlocks` = 当日 `KEYGUARD_HIDDEN` 次数；`launches` = `ACTIVITY_RESUMED` 次数；
   - `hour_matrix[day][hour]` = 各小时使用分钟（用 `screen_unlock` 口径）；
   - **最长连续** = 单个 `sub_kg` 后的亮屏区间最大分钟数（统计页"最长连续"展示用）。
6. **应用时长**：不从事件配对算，直接用系统自己的区间聚合（`totalTimeUsed`/`appLaunchCount`），按区间归属日汇总；当天用 In-memory 段补上。多用户区间只取真人区间（§2.2）。**注意：`launches`（事件计数口径）与 `app_usage.launches`（系统 `appLaunchCount` 聚合口径）是两种口径，文档与 UI 不得混用。**
7. **事件明细输出（CR-01 新增）**：
   - 解锁事件：`KEYGUARD_HIDDEN` 的毫秒时间戳逐条输出，落入 `unlock_event`，供详情页按自然日/小时聚合；
   - 通知事件：`NOTIFICATION_INTERRUPTION` / `NOTIFICATION_SEEN` 逐条输出（毫秒时间戳、类型、包名、`channelId` 可空），落入 `notification_event`；
   - 明细事件按设备本地时区归属自然日；事件覆盖范围以系统滚动窗口为界（约 10 个滚动日 + 此后每次拉取持续累积），**采集缺口与真实 0 次必须在查询层可区分**。
8. **展示名**：优先 `PackageManager.getApplicationLabel`，失败回退内置映射表（`parse_usage3.py` 的 `NAMES` 表可整段搬走，含微信/B站/抖音/豆包/DSH Go 等 60+ 常见包名中文名）。
9. **已知口径差**（写进 App 的"关于/说明"页）：
   - 应用时长相加 > 总使用时长：分屏/小窗/画中画重复计时，系统数据固有；
   - 系统日界是滚动的（约前一日 22:50–当日 22:50），App 用自然日重算事件口径，与系统日文件有 ±3 分钟/日出入；
   - 11/8 实测约 20 分钟口径差（系统 UI 自己的算法），属正常误差；
   - **通知口径（CR-01）**：「通知打扰」只统计产生打扰（视觉/声音）的通知，静音与静默渠道不计入；「已查看」是用户点开通知的次数，与打扰次数无必然包含关系。
   - **应用前台区间并入屏幕会话（CR-03 修订，2026-11-11）**：应用在前台时屏幕必然亮着，所以 `ACTIVITY_RESUMED→PAUSED` 配出的前台区间是屏幕时长的**可靠下界**，必须与 `SCREEN_INTERACTIVE` 会话一起做区间并集后再切日/切小时。不做这一步会出现两个真机现象：① 应用合计（13h31）大于屏幕时长（11h09）——MIUI 的 SCREEN 事件是滚动窗口，早间时段已过期；② 时段分布合计与屏幕时长对不上。并入后屏幕时长回到 16h46 量级，与系统「健康使用手机」的 16h37 只差个位数分钟。
   - **应用时长总量约束**：同一时刻只可能有一个应用在前台，因此「当天应用合计 ≤ 该天屏幕时长 × 1.15」是硬约束（1.15 与真机对账不变式一致，容得下滚动日界与分屏的正常重复计时）。一旦撑破，判定该天 In-memory 的 `totalTimeUsed` 整体不可信（该值在 MIUI 上会把后台常驻、画中画、跨天累计都算进来，日块里出现过 148h、914h），整天退回事件流推导值——宁可少报，也不给一组「加起来比屏幕还长」的数字。显式传入单日（批 6b 的「今日」语义）时豁免此约束。
   - **计数层口径（CR-02）**：解锁/启动/通知条数按毫秒多重集合统计（同秒多条真实通知不丢，CR-01），与系统设置界面的秒级聚合数字天然不同（实测约 +10–25% 口径差），不可直接比对；与系统 UI 对账时应比对**时长类**指标，条数类以本 App 口径为准。
10. **会话区间并集（CR-03，治滚动缓冲少算）**：解析器除日聚合外，把配对出的亮屏会话（`SCREEN_INTERACTIVE → SCREEN_NON_INTERACTIVE`，毫秒半开区间）与锁屏会话（`KEYGUARD_SHOWN → KEYGUARD_HIDDEN`）一并输出；入库后与已存区间做**扫线并集**（重叠/相邻合并、含入折叠），受影响日期的日聚合与小时矩阵**从该日全量已存区间重算**（与旧值取大），不再依赖单次 dump 的窗口覆盖。理由：OEM 事件缓冲是滚动窗口，单次拉取只见最近几小时，「同日取大」救不回任何一次拉取都没看到的时段。约束：重算必须读该日**全部**已存区间，只用「本次拉取窗口内合并结果」会退化成单次观测；解锁次数仍以事件表（只增、主键去重）为准，不从会话推导。

## 4. 数据模型（Room / SQLite）

```
day_summary(date PK, screen_min, screen_unlock_min, unlocks, launches, longest_session_min, pulled_at)
app_usage(date, pkg, name, minutes, launches, category, PK(date,pkg))
hour_usage(date, hour, minutes, PK(date,hour))
pull_log(id, pulled_at, source, ok, note)

-- CR-01 新增（只增不改：原四表、原字段与既有口径全部保持不变）
unlock_event(occurred_at_ms PK)                                      -- 解锁事件，毫秒时间戳
notification_event(occurred_at_ms, type, pkg, channel_id,            -- 通知事件
                   PK(occurred_at_ms, type, pkg))                    -- type: INTERRUPTION / SEEN

-- CR-03 新增（数据库版本 1 → 2，只增表；迁移 MIGRATION_1_2 必须显式注册，缺迁移会启动崩溃）
screen_session(start_ms, end_ms, kind, PK(start_ms, kind))            -- 亮/锁屏会话区间
                                                                     -- kind: SCREEN / KEYGUARD
                                                                     -- 索引：end_ms（按窗口查重叠）

-- CR-04 新增（数据库版本 2 → 3，只增表；迁移 MIGRATION_2_3 必须显式注册）
app_limit(pkg PK, limit_min, enabled)                                -- 应用每日时长限额（分钟，§5.12）
```
- 合并策略：同 `(date)` 重拉时覆盖/取较大值；历史只增不删。**从备份恢复（本地文件或云端下载）选择「合并本地」时，复用同一策略：同日数据取各字段较大值，不产生重复计数。**
- **会话区间合并（CR-03）**：`screen_session` 按「读重叠窗口 → 与新区间扫线并集 → 先删后插」的单事务流程维护，任一 kind 内区间互不重叠、相邻已归并；合并时必须**按 kind 过滤旧行**（重叠查询返回全 kind 混合行，不过滤会把亮屏区间打成假锁屏、反过来吞掉真实时长）。会话表是日聚合的**唯一重算输入**：受影响日期的 `screen_min / screen_unlock_min / longest_session_min / hour_usage` 全部从该日区间重算后与旧值取大，`unlocks` 取事件表当日计数。
- **备份范围（CR-04 更新）**：JSON 备份 `schemaVersion` 递增为 **4**（v1 = 原四表；v2 = 含事件表；v3 = 含会话区间；v4 = 含 `app_limit`，且 settings 增加超时提醒开关与自定义主题种子色）。恢复 v1/v2/v3 备份时按「缺少对应表」处理，不阻断导入，并在摘要中逐条提示缺失项（如「该备份不含会话区间，恢复后亮屏时长沿用原值」「该备份不含应用限额」）。
- **事件表合并（CR-01）**：`unlock_event` 按 `occurred_at_ms` 主键去重，重复插入即忽略；`notification_event` 合并时按 `(occurred_at_ms/1000, type, pkg)` 秒级分组，取两侧条数较大值（与 §2.2 坑 2 同一多重集合策略），避免吞掉同秒真实通知，也避免 checkin/明文双源重复计数。`channel_id` 缺失存 NULL。
- **事件覆盖范围（CR-01）**：系统只保留约 10 个滚动日的事件，事件明细从「首次拉取可及的窗口」开始累积，此后只增不删。查询层必须能区分三种状态：有事件记录（含真实 0 次的完整时段）、窗口外无记录、拉取缺口；UI 不得把无记录时段画成真实的 0（§5.7 详情页同规则）。
- `category`：内置分类（视频娱乐/社交沟通/AI 助手/工具效率/游戏/购物/其他）按包名映射，允许用户改（排行页图例着色用）。用户对分类的修改纳入备份与同步范围。
- 备份/同步的 JSON 结构与版本字段见 §5.10，解析与 UI 均不感知该文件格式，只有备份模块读写它。

## 5. UI 规范（v2.6 统一设计系统，本节为实现与验收依据）

### 5.1 参考边界与统一目标

保留 `nsh07/Tomato` 的深墨绿、无描边 tonal 分层、胶囊形状、细线圆环、悬浮导航与日历视觉语言；参考 Apple「屏幕使用时间」的摘要层级、Android「数字健康」的直接数据入口，以及 [Material 3 的可用性原则](https://m3.material.io/foundations/usability)：每页一个视觉重点、减少同权重信息、用留白分组，不堆叠装饰。

- `screen-time-ui-tomato.html` 用于理解布局和交互，不再作为唯一真源；与本节冲突时以本节为准。`screen-time-ui-prototype.html` 为 v1，仅作对照。
- Tomato 为 GPL-3.0，只参考视觉与交互形态，不复制源码；截图仅用于离线理解风格。
- 统一不是减少功能，而是让同类信息使用同一组件、同一尺寸、同一格式和同一状态。**不得在各页面另创颜色、圆角、卡片样式、日期格式或图表规则。**

### 5.2 页面骨架与布局节奏

所有主页面共用 `PageScaffold + AppHeader + ScrollablePage + FreshNavBar`（批 6g 重构：骨架本身**不自带滚动**，滚动下沉到 `ScrollablePage`，每页一份独立 `ScrollState`——否则从「今日」滚到一半切到「统计」，统计页会从同一偏移开始画，看起来像内容突然蹦出来）：

- 页面左右安全边距 20dp；内容区顶部与标题区间隔 8dp；卡片间距 12dp；卡片内分组间距 20dp；内容底部预留 112dp，保证悬浮导航不遮挡最后一张卡片。
- `AppHeader`：左侧页面标题 + 当前日期/区间副标题；右侧固定为「日期、界面风格、设置」三个图标按钮。按钮视觉圆形 40dp，实际点击区域至少 48dp，统一使用 Material Symbols Rounded 风格图标。
- 主页面无返回键。排行、设置等二级页使用「返回 + 标题」顶部栏；排行保留日期按钮，底部导航保持「今日」选中但不允许在二级页重复触发导航堆栈。
- 卡片统一：无描边、`surface` 背景、**圆角 28dp（CR-07）**、内边距 20dp。tonal 卡圆角 24dp，内边距 16dp；内部小块（详情面板、按钮）圆角 18dp。**阴影（CR-06 修订）**：允许 0–2dp 极淡阴影，**仅浅色模式**；深色模式 elevation 归零、靠 `surfaceVariant` 与 `surface` 的色阶差分层（深色下阴影只会糊）；描边仍然禁止。页面背景为纵向渐变：顶部 `gradientTop`（主色 10% 淡化）渐隐到 `background`（§5.4 语义 token）。
- 间距只使用 4dp 基数：4 / 8 / 12 / 16 / 20 / 24 / 32dp。360dp 宽屏不得横向溢出；更宽屏幕内容最大宽 520dp 并居中，不把卡片和柱图无限拉宽。
- 每页最多一个 hero 大数字区域、一个主图表区域。说明文字只解释口径或引导操作，不写重复标题和装饰性鸡汤。

### 5.3 字体、图标与数字格式

统一使用系统字体和 `sp`，不在组件内另设字号：

| Token | 字号/字重 | 用途 |
|---|---|---|
| `pageTitle` | 32sp / 700（CR-07 由 24sp 提大） | 页面标题 |
| `sectionTitle` | 18sp / 700 | 卡片标题、设置组标题 |
| `heroNumber` | 46sp / 800（ExtraBold），字距 -0.04em，tnum（CR-07） | 圆环时间、唯一核心大数字 |
| `statsNumber` | 40sp / 800，字距 -1.2sp，tnum（CR-07 新增） | 统计页日均大数字 |
| `metricNumber` | 30sp / 800（统计型卡 28sp），字距 -0.5sp，tnum（CR-07 由 26sp 提大） | tonal 卡数值 |
| `body` | 14sp / 400 | 正文、列表主文案 |
| `label` | 12sp / 500 | 辅助说明、坐标、图例 |
| `button` | 14sp / 600 | 按钮、segmented |

- 行高约为字号的 1.25–1.4 倍；大数字使用等宽数字特性（`tnum`），避免刷新时横向跳动。图标统一 22dp，应用图标 42dp、圆角 15dp，优先真实应用图标，失败再用首字母占位。
- **字体 family 分层（CR-06）**：数字与拉丁字母用 Manrope（SIL OFL，四个静态字重 Regular/Medium/SemiBold/ExtraBold 随包，`heroNumber`/`metricNumber` 用之 + `tnum`）；中文走系统字体（MIUI/HyperOS 即 MiSans 观感），**不打包完整中文字体**（单字重 8–10MB 会翻倍 APK，收益极小——有意识的取舍）。
- **圆环为目标环双层结构（CR-07 回滚 CR-06 的全天环勘误，以新规格 §4.2 为准）**：`progress = 当日使用 / 每日目标`，**允许超过 1、上限 2**；线宽 14dp 圆头，track 底 + 第一圈为线性渐变主色（左上→右下），**超目标时第二圈**从 12 点起按 `(progress-1)×360°` 叠画更深主色（primary 向黑混 35%）。中心三行：上「今日亮屏 / 日均亮屏」（12sp）/ 中 `H:MM`（heroNumber 46sp ExtraBold）/ 下「目标 X:XX」（12sp）；目标 ≤0 时不画进度、不显示目标行与超出 chip。环外下方标签行：「超出目标 X」（仅超目标）、「较昨日 X」（对比行规格），两者都没有时整行不显示。进场动画单一动画值 0→progress（900ms FastOutSlowIn）、数字同步滚动，减少动画直接落终值。
- 圆环中心固定 `H:MM`，**下方不再重复「小时 : 分钟」单位**（批 6g：重复单位已被真机反馈点名移除）。其他中文时长：≥1 小时显示「X小时Y分钟」（整小时省略 0 分钟），不足 1 小时显示「X分钟」，零显示「0分钟」；坐标轴可用 `1h/2h`，不得混用 `4h 32m`、`4:32`、`4小时32分` 三种正文格式。
- 全宽卡（`MetricCard` 等）时长数值采用「数字 + 小单位」排版（2026-11-10 增补）：内容格式仍为「X小时Y分钟 / X分钟 / 0分钟」，拆为**同一个 Text 的 `AnnotatedString` 两段**——数字 26sp/700（等宽数字 tnum、字距 -0.02em）+ 单位 13sp/500（不加字距）；数字到单位间距 4dp、单位到下一个数字 12dp。**不得用 Row 拼接两个 Text**（基线不齐、1.3 倍缩放错位、中途断行）。与圆环中心的 `H:MM` 并存、各有适用位置：圆环空间小用 `H:MM`，全宽卡用「数字 + 小单位」；不得出现第三种时长形态。可用宽度不足时（超窄屏 / 超大字体）整体降一档字号（数字 24sp / 单位 12sp），不截断数字、不省略单位。
- 对比行（「较昨日增加/减少 X 分钟」等）使用 14sp/600 文字 + 12dp 箭头图标，颜色用 `primary`；增减方向必须由箭头形状表达，不得只靠颜色（§5.4）。
- 对比文案统一为「较昨日增加/减少 X 分钟」或「较上一区间增加/减少 X%」；无对比数据时显示「暂无上一周期数据」，不得显示 0%。

### 5.4 颜色与九套主题

所有组件只能消费语义 token：`background / surface / surfaceVariant / onSurface / onSurfaceVariant / onSurfaceMuted / primary / onPrimary / primaryContainer / onPrimaryContainer / secondaryContainer / onSecondaryContainer / navSurface / buttonSurface / chart1~5 / track / month1~3 / heat0~4 / scrim / error`。禁止组件直接引用 `FreshColors.GreenDeep`、十六进制颜色或 `Color.White`。

- 浅色默认：背景 `#F4F7F3`、卡片 `#FFFFFF`、正文 `#1D322B`、主色 `#1B6B5A`；tonal 双卡 `#A9E7C9` / `#C6E9FA`；导航底 `#B9EDD5`；轨道 `#EAF2EC`。九套浅色主题沿用下表主色与 HTML 中同名单色板，但必须先映射为上述语义 token。
- 每套主题必须同时提供浅色和深色调色板。深色不是简单反色：背景接近中性深色、卡片略亮、主色提高亮度，tonal 卡文字与背景分别使用对应 `on...` 角色。

**自定义主题（CR-04：种子色 + 自动校正）**

- 九套预设与壁纸动态取色之外，外观设置新增「自定义主题」：用户在取色器中选择一个种子色，App 用**纯函数 `paletteFromSeed(seed, dark): FreshPalette`** 派生整套语义色板。壁纸动态取色与该引擎同源（Android 12+ 动态取色即「系统给种子色」的特例）。
- **自动对比度校正**：派生结果必须通过与批 2 回归测试同一组断言（正文 ≥4.5:1、大字/图形 ≥3:1）；任一色对不达标时，引擎按 ±2% 明度步进自动调整直至通过（收敛有保证：明度有上下界）。极端种子（近纯黑/纯白、高饱和）强制落入安全明度窗口兜底。
- **派生规则**：`chart1~5` 由种子色相在色轮上等距旋转派生；`month1~3`、`heat0~4` 按明度单调派生（保证色阶视觉有序）；tonal 双卡、导航底、单位色均从种子色按 §5.4 既有规则派生。
- **禁止自由 RGB 直填任何 token**——一切颜色必须经派生引擎 + 断言，这是「自定义不冲突」的唯一保障。
- 种子色持久化于 DataStore 并纳入备份 settings；自定义主题与九套预设同等待遇：切换不重新拉取数据、不改变筛选、不重置滚动位置。

### 5.5 导航、弹层与通用组件

- 底部悬浮胶囊导航固定 3 项「今日 / 统计 / 日历」。未选中项 52dp 仅图标；选中项 spring 展开并显示名称——**展开宽度 = 52dp 图标槽 + 间距 + 文字实测宽度 + 尾部 12–16dp**，不再固定 150dp（固定宽会让「今日」右侧留一大段空白）；容器内边距 6dp、项间距 4dp。动画 180–250ms，开启系统减少动画时改为淡入淡出。
- 主页面之间用 `HorizontalPager` 常驻三页（点到即终态，杜绝「新页先以完整不透明度画一帧再淡入」的闪现场象），支持横滑切页；二级页为覆盖层，底部导航画在最外层，二级页中仍可见。
- 日期和界面风格均使用统一的 **Modal Bottom Sheet**，不再一个下拉面板、一个悬浮卡片。统一 scrim、顶部 28dp 圆角、拖动条、标题和关闭行为；点击面板内部不得误关闭，点外部或切页时关闭。
- **页面转场统一为「容器变换（container transform）」（CR-03）**：进入二级页（排行、设置、解锁详情、通知详情）时，页面从**入口元素**（被点的卡片或按钮）的矩形区域展开——位置、宽高、圆角（24dp → 0）插值到全屏，观感与「从 App 图标展开」一致；返回时整页按同一路径**收回原处**并恢复卡片圆角，进出动效对称。约束：① 全程不透明、不做半透明叠影（半透明会让下层内容透出，呈现「视觉残留」）；② 系统返回手势、返回键、顶部返回按钮触发同一收起动画，不得一条路是滑动一条路是淡出；③ 总时长 280–360ms，spring 或 FastOutSlowIn，不为「显得流畅」延迟数据；④ 系统「减少动画」时退化为 120ms 短淡入（不做缩放位移；覆盖层始终实心，不与下层交叉淡化，否则又会叠影）；⑤ 卡片按下缩放（0.98 / 80ms）与页面展开同源，不得「先缩回再跳大」。
- 设置与查看全部应用同样使用容器变换（分别从顶部齿轮按钮、应用构成卡展开）；主页面之间的切换仍是横滑（Pager），不得用容器变换。
- 风格面板用 3×3 色点网格，色点下显示名称，当前项用勾选和文字共同标识；深浅色与动态取色在设置页配置。
- `PrimaryButton / SecondaryButton` 高度 48dp、全胶囊；每屏最多一个主按钮。`SegmentedControl` 高 40dp，选中项使用 `primary + onPrimary`，未选中项使用透明底 + `onSurfaceVariant`。
- `MetricCard` 固定为「标签 / 数值 / 可选一句说明」；双卡等宽、同高、同一字号，不得一页出现多种数值排版。数值排版按 §5.3「数字 + 小单位」执行：数字用 `onSurface`、单位用按 §5.4 规则派生的单位色（白卡即 `onSurfaceMuted`）；说明为对比文案时按 §5.3 对比行规格渲染（14sp/600 + 12dp 箭头 + `primary`）。
- **可下钻卡与纯摘要卡（CR-01 新增）**：卡片是否可点由「是否存在对应详情页」唯一决定，同类能力必须有相同表现，不得随意混用：
  - **可下钻指标卡**：整卡可点、右侧统一 12dp 前箭头（`onSurfaceVariant`）、按压 ripple、`Role.Button`、`contentDescription` 为「标签 + 当前值 + 查看详情」（如「通知打扰，今日 100 次，查看详情」）；点击区整卡 ≥48dp；
  - **纯摘要卡**：无箭头、无按压效果、不响应点击（圆环卡、日历连续记录卡等）；
  - 详情页未接线前卡片按纯摘要卡渲染，**不得提前显示箭头或点击效果**（守住假按钮红线）。
- `SegmentedBar` 每段必须能在下方图例中找到「名称 + 时长或百分比」；零权重段不绘制，空数据显示统一空态，不能传 0 或负权重给布局。
- 加载使用保留原布局的骨架或进度指示；错误用文字 + 重试按钮；无数据用同一张 `EmptyState` 组件。禁止白屏、只弹 Toast 后清空内容、或把无数据伪装成真实的 0 分钟。

### 5.6 日期选择与统一统计语义

使用单一 `DateSelection` 状态：`Day(date)` 或 `Range(startDate, endDate)`。**冷启动默认近 7 天（CR-03）**，旋转、切页和进入排行时保持；用户主动选择单日时才切换到单日口径。日期全部为设备本地时区自然日。默认近 7 天的理由：单日默认下统计页只有一根柱、时段分布残缺，首屏看不到任何趋势，观感像数据坏了。

**「今日」页与两个下钻详情页锚定今天（CR-03 修订，2026-11-11 真机反馈）**：这两处**不跟随全局筛选**，永远显示今天。原因是量纲冲突——它叫「今日」，却在近 7 天筛选下同时呈现「日均圆环」和「区间累计应用构成」，两套量纲叠在一张卡上，用户对照系统统计时必然觉得「数字对不上」（实测：应用合计 13h31 而圆环 11h09）。现在今日页只呈现今天，量纲单一、可与系统逐项对账；统计页与日历页仍跟随筛选（趋势与热力图本来就是区间视图）。

- 快捷项：今天、昨天、近 7 天、近 30 天、本月；指定单日使用 DatePicker；自定义区间使用 DateRangePicker，反选自动交换，最多 366 个自然日。
- **自定义区间支持手输日期（CR-03）**：区间面板提供「开始 / 结束」两个可编辑日期字段，点击弹出数字键盘，按「年 / 月 / 日」分段输入（也直接接受 `2026-11-01` 这种完整输入）；输入中即时校验（非法月份、日期不存在、结束早于开始分别提示，不静默纠正），合法后「应用」才可点。手输与日历点选双向同步：日历上选了日期，字段同步回填；手输合法值，日历联动高亮。
- ~~应用后显示统一筛选胶囊条「范围 · 共 N 天 · 有记录 X 天」，带清除按钮。~~ **CR-03 调整：全局筛选胶囊条已移除**——顶部副标题本来就显示当前区间（如「11月5日 – 11月11日」），胶囊条属冗余信息且跨页常驻、占用首屏一行高度（其出现/消失还会让下方内容跳一格）；恢复「今天」使用日期弹层里已有的「今天」快捷项，功能不缺。统计页与日历页读取同一 `DateSelection`（今日页锚定今天，见上），不允许趋势 segmented 与日期弹层各持一套日期。
- 「有记录」指数据库存在该日 `day_summary`，与真实使用 0 分钟区分。单日/区间完全无记录时，不应用新筛选，保留原视图并提示「该时段尚无数据，请先拉取」；部分有记录时正常展示，并显示覆盖天数。
- 单日：使用、解锁、最长连续直接取当日；圆环进度 = 当日使用/每日目标（CR-07 还原目标环语义，可超 1 上限 2）；对比前一自然日。
- 区间：今日页和趋势页主数字均为**有记录日的日均使用**，日均解锁同理；圆环进度 = 区间日均使用/每日目标（CR-07）；对比此前等长区间且有记录日的日均值。**排行不跟区间累计，固定按锚点单日计算（CR-03，§5.7 排行-2）**；最长连续取区间内最大值。
- 区间 `SUM` 包含全部有记录行；`AVG` 的分母只包含有记录日，不能把未拉取日当 0 拉低平均。趋势仍为每个所选自然日生成数据点：有记录按真实值，无记录高度为 0 并在详情标「无记录」。
- 日历以所选区间结束日为锚点：月视图跳到该月，年视图显示截至该日的过去 20 周；streak 以 `screen_unlock_min > 0` 的自然日连续段计算截至锚点的全量历史，「最久的一天 / 低于2小时」只统计当前筛选区间内的有记录日，其中真实 0 分钟计入「低于2小时」、无记录日不计入。
- 今日页夜间与趋势「22–06」统一为 **22:00（含）至次日 06:00（不含）**；其他时段依次为 06–12、12–18、18–22。

两个页面共用同一个 `MetricDetailPage` 结构，只替换指标与数据源；为**二级页**（返回 + 标题顶部栏），不占底部导航，进入时底部导航保持「今日」选中；返回今日页恢复进入前的滚动位置。

1. **共用结构**（自上而下，顺序固定）：
   - 摘要区：大数字 + 小单位排版（§5.3）；单日显示当日合计，区间显示「日均 + 区间合计」；通知详情固定为双指标「打扰 X 次 / 已查看 Y 次」；
   - 「图表 / 数据表」`SegmentedControl`，默认图表；两者必须渲染**同一份查询结果**，数字对不上即验收不通过；
   - 图表区：单日为 0–23 时逐小时胶囊柱图，区间为逐日胶囊柱图（沿用 `CapsuleBarChart` 规格：刻度独占、零值不画实体柱、超宽仅绘图区滚动）；按住或拖动柱体显示跟随气泡「11–12时 · 38条」「11月8日 · 95次」，气泡即时跟随手指、不做追赶动画；
   - 数据表：三列「时间段 / 次数 / 占比」，按时间升序，占比以区间合计为分母；表格在详情页内展开，**不使用弹窗承载大表格**；
   - 明细区：**通知详情**显示同区间应用通知排行（按打扰次数降序，图标 + 名称 + 次数 + 9dp 进度条，区分打扰/已查看两组数据可切换）；**解锁详情不显示应用排行**（现有事件无法可靠归因到应用，不得伪造），改为显示「最高频时段 / 每小时平均 / 最活跃日期」；
2. **数据状态**：沿用全局 `DateSelection`，切区间两详情页同步重算；真实 0 次显示「0」，采集缺口或窗口外时段标注「该时段无记录」并以空档样式区分，不得把无记录画成 0 的一排柱；
3. **转场与动效**（CR-01 统一规则，总时长 ≤500ms，不为了显得流畅而人为延迟数据）：
   - 卡片按下缩放至 0.98（约 80ms），松开后按**容器变换**展开（§5.5：从该卡片/按钮的矩形展开到全屏，320ms），两个详情页同一转场；不再使用「横向滑动 + 淡入」；
   - 大数字淡入并上移 12dp（约 180ms），**不做从 0 滚动到目标值的数字动画**；
   - 柱体从基线 `scaleY 0→1`（220–280ms），逐柱错开 8ms、总错开封顶 360ms；坐标轴先稳定显示；
   - 图表 ↔ 数据表切换：旧内容淡出 120ms、新内容淡入 160ms，容器高度稳定不跳动；
   - 数据加载超过约 150ms 才显示同尺寸骨架；已有缓存直接渲染，不重复播完整入场动画；
   - 系统「减少动画」开启时：取消错开、位移与缩放，直接淡入呈现结果（与 §5.5 导航一致）。

### 5.8 设置与系统状态

设置从所有主页面的统一顶部入口进入，分七组卡片，不占用底部导航：

- 「目标与同步」：每日目标、拉取频率、最近成功拉取时间、手动拉取；
- 「提醒与限额」（CR-04）：目标超时提醒开关（默认开启）、通知权限状态与系统授权引导（被拒时开关置灰并说明）、应用限额管理入口（按包名设置每日上限），详见 §5.12；
- 「权限与数据」：Shizuku 状态与重试、使用情况访问降级授权、应用分类管理（按包名查看并修改分类）、数据覆盖说明、导出 HTML 报告；
- 「备份与同步」：导出数据（JSON 完整备份 / CSV 明细）、从本地文件恢复、云端同步（WebDAV / Google Drive 的配置与登录、手动上传与恢复、自动同步频率与仅 Wi-Fi、上次同步时间与结果），详见 §5.10；
- 「统计口径」（CR-03，输入方式 CR-05 修订）：低使用阈值 `x`——**1–24 小时可调**（默认 2 小时，步进 1 小时）；设置页只显示一行「当前 x 小时」，点开**底部弹层的滚轮选择器**（一屏 5 个候选、吸附滚动、中间一格即当前值，可点选某格直接滚过去），「完成」后落地。该值同时驱动日历「低于 x 小时」计数与月/年视图色档边界（§5.7 日历-6）；改完立即生效，不重新拉取数据。
- 「外观」：九套风格、浅色/深色/跟随系统、跟随壁纸动态取色、**自定义主题（种子色取色器，CR-04，§5.4）**；
- 「AI 分析」（CR-03）：开关（默认关闭）、endpoint / 模型名 / API Key 配置与「测试连接」、「包含应用名称」开关、一句话数据边界说明（只发聚合统计，见 §5.11）；未配置时此组只显示说明与「去填写」，不画假连接状态；
- 「关于」：§3 的统计口径差、应用时长相加可能大于总时长、通知口径说明（**「通知打扰」仅统计产生视觉/声音打扰的通知，静音与静默渠道不计入；「已查看」是点开通知的次数**，CR-01）、事件明细自首次拉取窗口起累积的说明、**提醒与限额的数据滞后说明（数据截至上次成功拉取，非实时，CR-04）**、本地存储及「仅同步时联网」说明。

首次启动使用分步向导（欢迎与主题 → Shizuku 授权 → 目标与拉取频率 → 备份与云端同步，可跳过），每步为状态卡片：显示当前检测结果、下一步操作和「稍后在设置中配置」；向导风格参考 Shizuku 的状态机式授权引导与 Fushi 的 onboarding。首次启动、未授权、拉取中、拉取失败、dump 为空、部分历史和完全无数据均需有明确状态。已有历史时拉取失败应保留旧数据并在顶部显示内联错误；首次无数据时才显示全页引导。导出使用系统 SAF 创建本地 HTML 文件，不需要网络权限或外部在线模板。

### 5.9 可访问性与验收基线

- 所有图标按钮具备 `contentDescription`；装饰图形不对读屏重复播报；图表提供摘要和逐点详情，不只支持悬停。
- 点击目标至少 48dp；字体放大至 1.3 倍时标题、数值、按钮不裁切，卡片允许增高，不以固定高度硬压文本。
- 360dp 宽、深色模式、九套主题、空数据、超长应用名和 31/366 天区间均不得重叠或白屏；动画不阻碍点击，并尊重系统减少动画设置。

### 5.10 数据导出与云同步

备份与恢复是同一套流程，区别只在来源（本地文件 / 云端）。**恢复策略永远由用户在执行前二选一：覆盖本地 或 合并本地，不存在静默默认。**

**导出（本地，SAF）**
- 「导出 JSON 完整备份」：单文件 `screen-time-backup-YYYYMMDD-HHmm.json`，结构为 `{ schemaVersion, exportedAt, appVersion, settings, day_summary[], app_usage[], hour_usage[], pull_log[], unlock_event[], notification_event[], screen_session[], app_limit[] }`。`settings` 含每日目标、九套主题/深浅色选择、自定义主题种子色、应用分类修改、拉取频率、低使用阈值、超时提醒开关；**`schemaVersion` 首版为 4**（v1 = 原四表、v2 = 含事件表、v3 = 含会话区间、v4 = 含应用限额与新增设置项；恢复 v1/v2/v3 时须兼容识别并逐条提示对应缺失项，不阻断导入）。未来结构变更必须递增。
- 「导出 CSV 明细」：`day_summary / app_usage / hour_usage / unlock_event / notification_event / screen_session / app_limit` 各一个 CSV（UTF-8 带 BOM，Excel 直接打开不乱码），列名与 §4 字段一致。
- 导出走 SAF `ACTION_CREATE_DOCUMENT`，不需要存储权限；导出前显示将包含的日期范围和记录条数。

**统一恢复流程（本地文件导入 / 云端下载共用）**
1. 读取并校验备份：JSON 解析失败、缺 `schemaVersion`、版本高于当前 App，分别给出明确错误，不进入后续步骤；
2. 展示备份摘要：导出时间、App 版本、数据日期范围、各表记录条数、是否含设置；
3. 用户选择恢复策略：
   - **覆盖本地**：红色警示文案「将删除本机全部统计数据后导入」，二次确认后清空**八张表**（含 CR-03 的 `screen_session`、CR-04 的 `app_limit`）再导入；
   - **合并本地（默认高亮项）**：按 §4 合并策略逐日合并——`day_summary` 同日取 `screen_unlock_min` 较大的一行整体保留；`app_usage` 同 `(date,pkg)` 取 `minutes` 较大值并保留对应 `name/category`；`hour_usage` 同 `(date,hour)` 取较大值；`pull_log` 仅追加；**事件表按 §4 事件合并策略执行**（`unlock_event` 主键去重、`notification_event` 秒级分组取较大条数）；**`screen_session` 按 §4 区间并集合并**（扫线并集后重算受影响日期）；**`app_limit` 同 `pkg` 取备份值覆盖**（限额是用户意图，以备份为准）；**设置默认不导入**，另设勾选「同时恢复设置（目标/主题/分类/低使用阈值/提醒开关）」；
4. 导入在单个事务中完成，失败整体回滚；完成后显示结果摘要（新增 X 天、更新 Y 天、跳过 Z 条）并返回设置页。

**云端同步（多后端，参考 Komikku/Fushi 的提供者模型）**
- 后端以「提供者」形式接入，首版两个：① **通用 WebDAV**（预置坚果云地址 `https://dav.jianguoyun.com/dav/`，可改成任意 WebDAV 服务）；② **Google Drive**（系统账号 OAuth 登录，App 不接触账号密码）。设置页为每个提供者一张卡片：连接状态、上次同步时间与结果、「测试连接 / 登录 / 退出」按钮；结构上预留 Dropbox / OneDrive 扩展位。
- WebDAV 配置项：地址、账号（坚果云为邮箱）、密码（**坚果云「第三方应用授权密码」，不是登录密码**，配置页附一行获取指引文案）、远端目录（默认 `/screen-time/`）。
- Google Drive：OAuth 授权范围仅请求 Drive 文件访问；备份存应用数据目录（`appDataFolder`，用户不可见、不污染网盘列表）或用户指定文件夹；退出登录即清除本地令牌。Google 服务在部分网络环境不可达时按统一失败处理，不得影响 WebDAV 通道和本地功能。
- 手动同步：「上传」生成当前完整备份 → 覆盖远端固定文件 `screen-time-backup.json`；「恢复」下载远端备份 → 进入统一恢复流程（同样二选一覆盖/合并）。固定文件名与 JSON 格式对所有提供者一致。
- **自动同步**：频率可选「关闭（默认）/ 每次成功拉取后 / 每 1 天 / 每 3 天 / 每 7 天」，在每日系统数据拉取成功后自动上传；「仅 Wi-Fi 下同步」开关默认开启。自动备份使用带时间戳的文件名（`screen-time-backup-auto-YYYYMMDD-HHmm.json`），**仅保留最近 5 份**；手动上传的固定文件不受清理影响。首版不做多设备冲突检测和增量同步，远端被其他设备更新时以下载时的合并策略解决。
- 进度与状态：上传/下载/恢复进行中在对应卡片显示内联进度（参考 Komikku 的进度 banner 思路，不阻塞其他页面操作）；完成后更新「上次同步」；失败分类提示（网络不可达、401 鉴权、404 目录不存在、格式错误、远端空间不足）。

**网络边界**：除手动触发或按本节频率自动触发的云同步请求，以及 §5.11 中用户**主动点击**触发的 AI 分析请求外，App 不发起任何网络请求；无统计、广告、崩溃上报 SDK。飞行模式下同步与 AI 分析入口可见，点击提示「当前网络不可用」。

### 5.11 周期总结（周 / 月 / 年）与 AI 分析（CR-03 新增）

**入口与周期定义**
- 入口：统计页底部「本周总结 / 本月总结 / 本年总结」卡片（按当前日期给出周期名），进入二级页（容器变换转场，§5.5）；页内 `SegmentedControl` 切换周 / 月 / 年。日历页顶部提供同一入口。
- 周期：周 = 周一至周日（设备本地时区）、月 = 自然月、年 = 自然年；当前周期未结束时标题写「截至 M月D日」，并标注「未结束」。
- 对比：与此前**等长**周期比较（跨月天数不同时按日均比较，不用总时长直接比），沿用 §5.3 对比行规格。

**内容结构（顺序固定，一页读完，不堆卡片）**
1. hero：周期总使用时长 + 日均（「数字 + 小单位」，§5.3）；
2. 对比行：较上一周期日均增加/减少 X%；
3. 趋势图：沿用 §5.7 趋势图规范（统一量程、0/中/顶三档刻度、平均线、点柱看详情）。周视图 7 根粗柱、月视图 28–31 根细柱一屏放下、年视图 12 根柱（每月日均，柱下写 `1月…12月`，只标首/中/末月）；
4. tonal 双卡：最长一天 / 最短一天（含日期）；连续记录天数并入说明行；
5. 应用榜：周期 top 5（图标 + 名称 + 时长 + 占比），「查看全部」进入排行页并**携带周期口径**（副标题写明周期，不得退化成单日，也不得无标识地累加区间）；
6. 时段分布：06–12 / 12–18 / 18–22 / 22–06 占比；
7. 结论：**规则生成**的 3–6 条洞察（如「本周日均比上周多 2 小时 10 分钟」「周三最长」「夜间使用占比 31%」），每条形如「事实 + 一句解释」，不使用夸张修辞、不做价值评判；数据不足时不出结论、不给假洞察；
8. 覆盖说明：周期内有记录 N 天 / 共 M 天，缺口日显式标注（不得把未记录日当 0 参与日均，也不画成 0 柱）。

**分享与导出**：支持（a）复制总结纯文本；（b）导出 PNG 长图与 HTML 报告（SAF），导出前可选「隐藏应用名称」（只显示占比与颜色）。导出内容与页内数字必须同源，不得另算一套。

**AI 分析（可选增强，默认关闭，两种模式）**

原则：本地优先、显式同意、最小必要数据、不内置任何第三方密钥、不代收数据、无遥测、无后台自动请求。

- **模式 A：复制给 AI（默认，零配置）**——「复制总结」把结构化文本（周期、总时长、日均、对比、时段占比、Top 5 应用与占比、覆盖天数）写入剪贴板，用户自行粘贴给任何 AI 工具。App 不联网，零权限成本。
- **模式 B：自带密钥（OpenAI 兼容接口）**——设置页「AI 分析」组配置 endpoint / 模型名 / API Key（存 EncryptedSharedPreferences；**备份与导出默认不含密钥**）。用户在总结页点「生成 AI 点评」时才发起一次 `POST {endpoint}/chat/completions`：
  - 请求体只含**聚合统计**（周期、总时长、日均、对比、时段占比、Top N 应用名与时长）与固定提示词；**不含**逐条事件明细、不含 dump 原文、不含包名；
  - 「包含应用名称」开关默认**关闭**（只发「Top1 应用 2 小时」这类匿名描述），打开后才发应用名；
  - 发送前弹出 payload 预览与一句数据说明，用户可取消；每次请求都需要用户再次点击（不做定时/自动）；
  - 结果追加在总结底部，标注「AI 生成，仅供参考」；失败（网络不可达 / 401 / 403 / 限流 / 返回格式不符）只显示可重试提示，绝不影响本地总结与统计；
  - 不把任何内容用于训练或上传到 App 自有服务器（App 没有自有服务器）；不做医疗、心理诊断或投资建议类的结论引导。
- **合规与红线**：AI 入口不得出现在未开启状态的主流程里（设置项可见但默认关闭）；未配置密钥时点击「生成 AI 点评」引导去设置，不发空请求；任何情况下都不得静默上传数据。

### 5.12 提醒、应用限额与桌面小组件（CR-04 新增）

三者均为纯本地能力；共同前提是**数据截至上次成功拉取，非实时**——该语义必须在相关入口与「关于」页明示，不得让用户误以为超限会被即时拦截。

**目标超时提醒**
- 触发时机：每次成功拉取后（打开 App 节流拉取、手动下拉、每日 WorkManager 任务）检查当日 `screen_unlock_min` 是否超过每日目标；超过即发一条本地通知，**每日最多一条**；当日修改目标后不再补发，次日按新目标重新判定。
- 权限：targetSdk 34 需 `POST_NOTIFICATIONS` 运行时权限，在首启向导或设置「提醒与限额」组申请；用户拒绝后开关置灰并显示系统引导文案，不得假装已开启。
- 通知渠道：独立渠道「使用提醒」，用户可在系统设置单独关闭；文案注明数据截至时间（如「截至 14:30，今日已使用 4小时32分钟」）。

**应用使用限额**
- 入口：设置「提醒与限额」组的管理页，或排行页条目操作进入；按包名设置每日上限（15 分钟–23 小时 45 分，步进 15 分钟，滑杆 + 数字双向输入），存 `app_limit` 表（§4）；可停用/删除单个限额。
- 效果：① 排行页条目进度条按「当日已用 / 限额」渲染，超限条目加「已超限」标记（`error` 色 + 文字，不单靠颜色）；② 每次成功拉取后检查，超限应用发本地通知（**每应用每日最多一条**，与目标提醒共用「使用提醒」渠道）；③ 数据滞后语义同上，文案注明截至时间。
- **明确不做**：强制锁机、悬浮窗拦截、无障碍监控、后台常驻检测——本 App 是统计工具，不是管控工具；任何实现不得滑向这些方向。

**桌面小组件**
- 用 Glance（`androidx.glance:glance-appwidget`）实现，两种尺寸：**2×2**（今日使用 `H:MM` + 每日目标进度条）与 **4×2**（今日使用 + 目标进度 + 解锁次数 + 通知打扰次数）；点击小组件打开 App 今日页。
- 数据：只读本地 Room 的最近一次拉取结果，**纯离线、不触发拉取、不发起网络**；无数据时显示「打开 App 拉取数据」引导态，不显示假 0。
- 更新时机：每次成功拉取后主动更新 + 系统定期回调（约 30 分钟）+ 主题变更后重绘。
- 外观：Android 12+ 用系统动态取色（GlanceTheme），低于 12 用 App 当前主题种子色经 §5.4 派生引擎生成；深浅色跟随系统；圆角与字体风格和 App 内卡片一致。
- **隐私**：小组件只显示聚合数字，不显示任何应用名称（桌面可被他人瞥见）。

## 6. 技术栈与工程要求

- Kotlin + Jetpack Compose + Material3，minSdk 26、target 34+；使用稳定 BOM 和稳定 Material3 API，不为追求 Expressive 外观引入实验性组件。依赖限 Shizuku api/provider、WorkManager、Room、DataStore、OkHttp（云同步与 AI 分析 HTTP）、Google Sign-In / Credential Manager（仅 Google Drive 登录用）、**Glance（桌面小组件，CR-04）**及 JSON 序列化库；图表优先自绘 Canvas / Box。**仅声明可行的 `INTERNET` 权限，除 §5.10 的云同步请求与 §5.11 的用户主动点击触发的 AI 请求外，不得发起任何网络请求。CR-04 新增声明 `POST_NOTIFICATIONS`**（仅用于 §5.12 的本地提醒，运行时申请、被拒降级不崩溃）；小组件不申请任何额外权限。
- 推荐单向数据流：`Repository -> ViewModel -> UiState -> Compose`。Composables 不直接执行 Room 查询、日期聚合或业务计算；四页共享同一个 `DateSelection`，筛选、加载、错误和数据覆盖天数统一放入各自 UiState。
- 主题必须实现 `FreshPalette` + `CompositionLocalProvider`，接口为 `ScreenTimeTheme(variant, darkTheme, dynamicColor)`；九套主题的浅色/深色调色板集中在主题层。业务组件只能读 `LocalFreshPalette` 或 MaterialTheme 语义色，禁止静态引用 `FreshColors.*`。**CR-04：自定义主题与动态取色共用纯函数派生引擎 `paletteFromSeed(seed, dark)`**；引擎输出必须过与批 2 回归测试同一组对比度断言，不达标由引擎自动校正（±2% 明度步进），测试覆盖极端种子（`#000000`/`#FFFFFF`/`#FF0000`/`#00FF00`/`#0000FF` + 随机 50 个种子）全部通过。主题、目标、拉取频率、提醒开关、限额变更用 DataStore/Room 持久化；日期筛选冷启动不持久化。
- **提醒与限额工程要求（CR-04）**：超限判定为纯函数 `evaluateAlerts(daySummary, appUsage, limits, goal, lastNotifiedMap)`，JVM 单测覆盖「每日每应用最多一条」「进程重建后不重复提醒」「目标当日修改不补发」；「已提醒」状态持久化于 DataStore（按日期+包名），不得存内存；通知发送是副作用边界，与判定分离。
- `compose-uikit/` 只能作为起点，不能原样视为完成品：`CapsuleBarChart` 补固定刻度列、动态量程、零值和横向滚动；`HeatmapCalendar` 改为 9dp/3dp 并补点击详情；`MonthCalendar` 保留每日色档、单日 10dp 和前后月灰字；所有组件去除硬编码颜色并支持深色。
- 卡片和文本尽量使用约束尺寸而非固定高度；图表必须先用 360dp 可用宽度计算布局，再决定滚动，不允许靠缩小字号、负间距或超出卡片解决拥挤。
- Room 查询与聚合严格按 §5.6：缺失日不等于真实 0 分钟；区间日均只除以有记录天数。单日、区间、上一等长周期、记录覆盖数由统一领域计算器产生，避免四页各自实现出不同结果。
- 解析器写成纯 Kotlin 模块（两段 dump 文本 → 数据类）。§3 的 `hour_matrix` 使用 `screen_unlock` 口径，移植时不得把参考 Python 中直接累加亮屏片长的写法当作正确口径；小时合计应与同日 `screen_unlock` 在分钟取整误差内一致。英文与数字事件类型先归一化再处理（映射表按 §2.2 完整 15 项）。
- **事件明细工程要求（CR-01）**：解析器除日聚合外同步输出解锁/通知事件流；计数层保留毫秒精度，checkin 与明文合并按 §2.2 坑 2 多重集合策略实现，并有单测证明同秒多条通知不丢失、双源不重复计数。**首版不引入 `NotificationListenerService`**——UsageStats 事件已满足打扰/已查看双指标与按应用归因；未来若要统计静默通知，只能作为可选增强另立需求，不得在本版混入。解锁/通知详情的聚合查询走契约层统一入口（两个详情页共用同一 `metricDetail` 查询，禁止各写一套聚合逻辑）。
- **周期总结工程要求（CR-03）**：周/月/年的周期切分、上一周期对比、结论文案全部由纯函数领域计算器生成（可 JVM 单测，不依赖 Compose）；归月/归周一律按设备时区，跨年周与不足一周的当期都要有确定行为（当前周/月/年显示「未结束」，对比仍按等长已完成周期或日均比例）。结论模板只允许陈述事实和直接推导（「日均较上周增加 X」「最多使用为周三」），不得输出因果归因或健康建议。
- **AI 分析工程要求（CR-03）**：定义 `AiProvider` 接口（`testConnection / summarize`），首版仅一个 OpenAI 兼容适配器（OkHttp，超时 30 秒，不自动重试）；请求体由纯函数 `buildPrompt(payload, includeAppNames)` 生成并有单测断言「不含事件明细/不含包名」；密钥存 EncryptedSharedPreferences，不得进日志、数据库、备份 JSON 或崩溃信息；UI 层只在用户点击时调用，不得挂在自动任务或 `LaunchedEffect` 里。
- 原 `sample-checkin.txt` / `sample-human.txt` 是格式切片，**不得修改，也不得宣称它们能单独复现完整 `report_data.json`**。测试分两层：用原切片做正则/格式测试；另在测试源码或新增测试资源中建立完整、可执行的 golden fixtures，覆盖 `M:SS`、毫秒/秒事件去重、数字事件类型、跨零点、未闭合亮屏、锁屏扣减及小时合计；**CR-01 增补 fixtures：解锁事件小时聚合、通知事件按类型/包名聚合、同秒多条通知、双源合并取较大条数**。`parse_usage_v2.py` 与 `screen_usage_report.json`（资料源目录）为 CR-01 的实测参照，其中 `MM-DD` 日期键与硬编码时区是 Python 参照的遗留，Kotlin 移植不得照抄。
- 设置与状态：每日目标、授权状态、最近成功拉取、手动重试、导出和数据说明均接真实状态；不能只画设置页。HTML 报告导出通过 SAF `ACTION_CREATE_DOCUMENT` 生成自包含文件，无 CDN、在线字体或网络请求。
- 备份与同步：定义统一 `SyncProvider` 接口（`testConnection / upload / download / disconnect`），WebDAV 与 Google Drive 各为一个适配器；新增云端（Dropbox/OneDrive 等）只允许新增适配器，不改备份格式与恢复流程。本地导出/导入与云端上传/下载共用同一 JSON 序列化器和同一恢复流程（§5.10），不允许两套合并逻辑。WebDAV 用 OkHttp 手写 PROPFIND/MKCOL/PUT/GET 最小子集或引入 Sardine；Google Drive 登录后经 Drive REST v3 由 OkHttp 上传/下载（`appDataFolder` 或用户指定文件夹）。请求在 IO 线程执行、超时 15 秒；坚果云应用授权密码与 Google OAuth 令牌用 EncryptedSharedPreferences 存储，禁止明文写入数据库、日志或备份 JSON；覆盖/合并恢复均在单事务中完成，失败回滚并保留原数据。
- 自动同步：在每日 WorkManager 拉取任务成功后按 §5.10 频率设置链式触发上传；任务约束为「网络可用」（开启「仅 Wi-Fi」时 `NetworkType.UNMETERED`），指数退避重试最多 3 次；每次成功后清理超出保留数量的旧自动备份；自动同步失败不弹窗，仅写入同步状态并在设置页展示。
- 错误处理：Shizuku 未启动/未授权显示引导；拉取中禁止重复任务；dump 为空或失败保留旧数据并记录 `pull_log`；所有写库合并在事务中完成，连续拉取不得重复计数；同步失败（网络/401/404/格式错误）不改动本地数据，仅在界面显示原因。
- 实施顺序固定为「语义色板与字体/间距 token → 共享 DateSelection 和领域计算器 → 通用组件 → 四个数据页面 → 设置与系统状态 → 测试」。不得先复制 HTML 占位数值再假装完成数据接线；未完成能力明确列为待办，不用假按钮或假数据掩盖。

## 7. 验收标准

1. **首次拉取**：冷启动能引导 Shizuku 授权并一键拉取，正常真机上 10 秒内显示今日真实数据；未启动、拒绝授权、空输出和失败均有对应状态，不白屏。
2. **数据口径**：解析结果与系统「健康使用设备」逐日对比，误差 ≤5 分钟（需求已注明的特殊口径差除外）；小时矩阵合计与同日 `screen_unlock` 在分钟取整误差内一致。
3. **真实数据接线**：今日、统计、日历、排行全部使用解析和 Room 数据，无硬编码业务数值；最长连续不显示无来源的应用名；排行「显示全部」真实可用。
4. **离线与持久化**：飞行模式下拉取已有数据、四页浏览、筛选、主题切换、设置、HTML/JSON/CSV 导出和从本地文件恢复可用（坚果云同步入口可见但提示网络不可用）；重启后历史、目标、分类修改和外观设置不丢，连续拉取不重复计数。
5. **解析单测**：`M:SS`、秒级事件去重、跨零点切分三个原必测项全部通过，并覆盖数字事件类型、锁屏扣减、未闭合亮屏及小时合计；原切片不被修改，golden fixtures 可独立重复执行。
6. **统一页面骨架**：四页使用同一标题栏、间距、24dp 无描边卡片、字体 token、数字格式（§5.3 双形态：圆环 `H:MM`、全宽卡「数字 + 小单位」，不得第三种）、弹层和空态；360dp 宽下无横向页面溢出，宽屏内容按 520dp 上限居中。
7. **导航与圆环**：悬浮胶囊导航只有今日/统计/日历 3 项，选中弹性展开名称、未选中仅图标；排行可进入并返回且保持导航状态；圆环 9dp 细线、圆头、inset 防裁切，中心为 `H:MM`。
8. **趋势图**：7 天粗柱 / 30 天细柱一屏放下（标签恰 4 个），量程与参考线按第 20 条执行；左侧刻度独占 32dp、不与柱体重叠；零值不画实体柱；31 天以上可通过绘图区滚动查看全部日期，刻度固定、不丢数据。
9. **日历**：月/年视图可切换；月视图连续日期连成胶囊但保留每日色档，单日为 10dp 圆角，前后月日期为灰色；年视图 20 周、9dp 格子完整落在容器内，点击任一格显示真实日期与时长。
10. **主题与可访问性**：九套主题均有浅色/深色，切换后卡片、图表、导航、日历同步变色且不重新拉取数据、不改筛选；正文对比度 ≥4.5:1、必要大号文字/图形 ≥3:1；字体 1.3 倍和减少动画开启时无裁切或操作阻塞，图标按钮点击区 ≥48dp。
11. **日期与区间**：快捷、指定单日和自定义区间均写入同一状态；筛选条显示总天数和有记录天数，四页按 §5.6 重算，清除恢复今天；完全无记录时保留原筛选并提示，部分有记录时不把缺失日计入日均。
12. **设置与导出**：目标、拉取频率、授权重试、外观和数据说明均接真实状态；SAF 可导出自包含 HTML，断网打开不出现外部资源请求；分类修改入口和保存结果可见。
13. **数据备份与恢复**：可导出 JSON 完整备份（含 schemaVersion、八张表和设置）与八张表 CSV；从文件恢复前展示备份摘要；「覆盖本地」有红色警示和二次确认，执行后本地仅剩备份内容；「合并本地」按 §4 策略执行（含事件表合并与 `app_limit` 覆盖），同日取较大值、不重复计数，设置默认不随恢复变更；导入失败整体回滚、原数据不变；v1/v2/v3 旧备份可识别并逐条明确提示缺失项（事件明细/会话区间/应用限额）。
14. **云同步**：坚果云 WebDAV 可配置地址/账号/应用授权密码并测试连接，Google Drive 可完成 OAuth 登录与退出；401、404、断网分别有明确提示；上传后能从云端再次下载到同一文件；下载恢复同样提供覆盖/合并二选一；凭据与 OAuth 令牌不明文出现在数据库、日志或备份 JSON 中；同步期间断网不损坏本地数据；Google Drive 不可达不影响 WebDAV 通道与本地功能。
15. **自动同步**：开启后按所选频率（每次成功拉取后 / 每 1 / 3 / 7 天）在成功拉取后自动上传，遵守「仅 Wi-Fi」开关与系统网络约束；失败静默记录并在设置页显示原因，不弹窗、不丢数据；自动备份文件名带时间戳且仅保留最近 5 份，手动上传的固定文件不被清理；**手动下拉刷新成功在「每次成功拉取后」频率下同样触发上传（CR-04）**。
16. **解锁/通知详情（CR-01）**：今日页「解锁次数」「通知打扰」双卡为统一样式的可下钻卡（箭头、ripple、读屏描述齐全，其余卡片保持纯摘要样式）；点击进入对应详情页并共享全局日期筛选，返回恢复滚动位置；单日逐小时、区间逐日柱图与数据表渲染同一查询结果；通知详情可按应用排行（打扰/已查看可切换），解锁详情不出现应用归因；通知打扰/已查看与卡片数字、详情图表、数据表三者一致；真实 0、无记录、采集缺口三态可区分且不互相伪装；不申请通知监听权限。
17. **事件解析与合并（CR-01）**：解析器输出解锁/通知事件流且计数层保留毫秒精度；单测证明同秒多条真实通知不丢失、checkin 与明文双源合并不重复计数；**系统级镜像事件跨账户收敛（CR-02：三账户不重复计数，收敛后解锁数与单账户量级相当）**；数字事件类型映射覆盖 §2.2 全部 15 项；事件按设备本地时区归属 `YYYY-MM-DD` 自然日；连续拉取事件不重复入库。
18. **会话区间并集（CR-03）**：连续两次拉取分别只覆盖上午/下午时，`day_summary.screen_unlock_min` 等于两段并集（不是单次最大值）；重拉只看到子集时旧聚合不被缩水；锁屏区间正确扣减且小时矩阵同口径；`screen_session` 同 kind 内不重叠、不残留含入/相邻段；v1→v2 迁移后原数据完好、`screen_session` 表可用；单测覆盖扫线合并与跨零点切片。
19. **下拉刷新（CR-03 新增、CR-04 修订）**：今日/统计/日历三个主页面在滚动到顶部时下拉可触发拉取，排行与详情等二级页无下拉手势；未授权时提示去授权、不画假进度；距上次成功拉取不足 60 秒时只重读本地库并提示「刚刚已更新」，不再 dumpsys；失败保留旧内容并显示内联错误；完成后轻提示且不重置滚动位置；与自动同步的联动按 §2.1 规则执行。
20. **趋势图统一规范（CR-03）**：近 7 天与近 30 天使用同一量程算法（`0 → min(ceil(max),24h)`）；有 0 / 中（半量程）/ 顶 三个刻度与一条平均线且平均线数值等于有记录日柱值算术平均；近 30 天为细柱且 30 天全部落在一屏内、日期标签恰好 4 个；31–366 天仍可滚动查看全部日期。
21. **点柱看详情（CR-03）**：点/长按任一柱弹出「该日时长 + 周几/月日 + 前三名应用（图标+名称+时长）」浮层，随柱移动、不遮该柱；无记录日显示「无记录」；数值与该日详情一致。
22. **容器变换转场（CR-03）**：设置、排行、两个详情页与周期总结均从入口卡片/按钮位置展开、返回收回原处，全程不透明无叠影；系统返回手势与顶部返回键同一动画；系统「减少动画」时退化为淡入淡出；主页面之间仍为横滑。
23. **统计口径可调（CR-03，输入方式 CR-05 修订）**：设置页阈值点击弹出滚轮选择器，可滚动选 1–24 小时（一档一小时），停下必然对齐整小时、无越界值可输入；修改后日历计数与月/年色档边界立即跟随，且不触发重新拉取。
24. **日历对齐（CR-03）**：月视图网格在卡片内水平居中、星期表头与日期列对齐；年视图 20 周完整落在卡片内、右侧不截断；360dp 与窄屏下不溢出容器。
25. **自定义区间可手输（CR-03）**：自定义区间支持按年/月/日输入开始与结束日期，非法输入即时提示且不静默纠正，与日历点选双向同步；应用后四页按同一状态重算。
26. **排行口径（CR-03）**：「查看全部应用」从今日页进入按锚点单日统计并写明日期，不累加区间；从周期总结进入按该周期统计并写明周期；两种入口副标题与数字口径一致，不得同标题不同口径；应用数与时长与当日「应用构成」卡一致（区间态下卡片标注「区间累计」以避免歧义）。
27. **周期总结（CR-03）**：周/月/年三种周期均可进入并有明确的当期「未结束」标识；总时长、日均、对比、最长/最短日、Top5、时段占比与应用内数据一致；有记录天数与缺口天数明示，未记录日不计入日均也不画成 0；结论为规则生成的事实陈述，数据不足时不出结论；导出的纯文本/长图/HTML 与页内数字同源。
28. **AI 分析（CR-03）**：默认关闭、未配置密钥时不发请求；开启后仅在用户点击时发起一次请求，发送前可见 payload 预览且可取消；payload 不含事件明细与包名，「包含应用名称」默认关闭；密钥不出现在日志、数据库与备份 JSON；请求失败不影响本地总结；飞行模式下提示网络不可用；全程无后台自动请求与遥测。
29. **自定义主题（CR-04）**：取色器选择种子色后，`paletteFromSeed` 派生的浅色与深色整套色板全部通过对比度断言（正文 ≥4.5、大字/图形 ≥3），含极端种子（纯黑/纯白/高饱和原色）与随机 50 个种子；图表五色可区分、月历/热力色阶明度单调；种子色重启不丢且随备份恢复；切换自定义主题不重新拉取数据、不改变筛选。
30. **目标超时提醒与应用限额（CR-04）**：每次成功拉取后判定，超每日目标发一条本地通知（每日最多一条、文案注明数据截至时间）；应用限额可设置/停用/删除并在排行页以「已用/限额」进度条与「已超限」标记呈现，超限每应用每日最多一条通知；`POST_NOTIFICATIONS` 被拒时功能诚实降级（开关置灰 + 引导）；进程重建与重启后不重复提醒；不存在任何强制锁机/拦截行为；限额纳入备份。
31. **桌面小组件（CR-04）**：2×2 与 4×2 两种尺寸可添加；显示最近一次拉取的真实数据（今日时长、目标进度，4×2 另含解锁与通知打扰次数），无数据时显示引导态而非假 0；点击打开 App 今日页；拉取成功后小组件同步更新；不显示任何应用名称；断网与飞行模式下正常显示已有数据；低 Android 版本用当前主题种子色派生、12+ 跟随系统动态取色。
32. **多机型适配（CR-04）**：`DumpShape` 形态识别与「谁有数据谁主导」分支有单测覆盖 vivo 与 HyperOS 两种 dump 形态；通知事件缺失的机型详情页显示「当前机型不提供该数据」而非 0；镜像事件收敛自检告警写入 `pull_log`；§2.3 矩阵随新机型实测增补，未实测机型不宣称支持。

33. **Manrope 数字字体（CR-06）**：`heroNumber`/`metricNumber` 使用 Manrope + tnum，中文正文仍为系统字体；APK 增量 < 1MB；切英文/数字界面字重视觉变粗。
34. **背景渐变与卡片阴影（CR-06）**：浅色页面顶部有极淡主色渐隐到中性底；卡片 0–2dp 极淡阴影仅浅色生效，深色模式无阴影边、靠色阶分层；`FreshPaletteContrastTest` 全绿。
35. **目标环双层（CR-07）**：未超目标一圈渐变主色弧；超目标时第二圈从 12 点按超出比例叠画深色；progress 超 2 倍封顶；中心「今日亮屏 / H:MM / 目标 X:XX」三行；目标 ≤0 无进度无目标行无超出 chip；进场动画从 0 起不闪帧，减少动画直接落终值。
36. **顶部按钮收敛（CR-06）**：今日/统计/日历三页顶部仅「日期」「设置」两枚圆按钮；风格切换入口保留在设置页（色块网格、点选即生效）。
37. **今日页迷你柱（CR-06）**：圆环卡内近 7 天迷你柱 + 星期标签 + 「日均 X」；数据与统计页趋势同源；最长连续保留为圆环卡底部一行小字。
38. **统计页固定详情条（CR-06）**：选中柱的详情显示在图表正上方固定条（不浮动、不遮柱）；未选中显示常驻提示；左右滑动切换选中日并轻震。
39. **日历四档（CR-06，CR-07 修订口径）**：月视图四档色阶（复用 heat1~4）+ 底部图例 + 今日白底主色外环；档位按「当天使用 / 每日目标」≤100%/≤140%/≤175%/>175% 切分，且读用户实际每日目标（不是固定阈值 `x`）；最深档用白字，九套主题下日号对比度 ≥4.5:1；改目标后档位随之重算。
