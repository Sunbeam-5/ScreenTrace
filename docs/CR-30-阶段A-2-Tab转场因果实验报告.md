## 4. Perfetto 长帧证据与归因（逐帧分解）

典型长帧（expA far 120Hz r1，188.3ms，jank=Dropped Frame）的完整分解：

| 维度 | 证据 | 结论 |
|---|---|---|
| **UI thread** | `Choreographer#doFrame 175.4ms = animation 32.8ms + traversal 142.4ms` | **元凶** |
| **Compose** | `traversal` 内 `AndroidOwner:measureAndLayout 139.1ms`，其中 **7 个 `Compose:recompose` 重组域串行（合计 ≈115ms）+ `Compose:applyChanges` ≈28ms**；`Record View#draw() 141.7ms`（draw 记录随布局重跑） | **重组+布局/绘制记录** |
| **RenderThread / GPU** | `prepareAndDraw 1.7–6.8ms`、`Drawing 5–9ms`/帧 | **正常，不是瓶颈** |
| **GC** | 窗口内无 GC 段（仅 JIT `VerifyClass createSpringAnimations` 痕迹，<1ms） | **无贡献** |
| **调度** | 主线程 Runnable（等 CPU）≈0.0–0.4ms | **无贡献** |
| **动画路径** | B 组瞬时跳页（scroll 4–7ms）仍复现同型长帧 | **排除** |

三条长帧分解明细（expA far 120Hz，3 重复 × 2 条/轮全部一致）：
188.3 / 201.6 / 166.1 / 193.2 / 163.4ms——全部为
`doFrame → animation(≈30ms) + traversal(≈120–178ms) → measureAndLayout(≈117–175ms) → 5–7×Compose:recompose(20–35ms/域)`。

> **归因结论（GPT 要求的六选一）**：长帧由 **UI 线程的 Compose 重组 + 布局/绘制记录**造成；
> 不是 RenderThread/GPU、不是 GC、不是调度、不是动画插值路径。

## 5. 操纵检验

> PerfProbe tick = 页根 Composable **函数执行次数**，**不等于**完整 recomposition 次数
> （子树是否跳过未逐层验证）；本节只用它验证操纵是否生效。

| 组 | 滚动时长 scrollStart→scrollEnd | 页根执行次数/次滚动 | 操纵是否生效 |
|---|---|---|---|
| A 对照 | 453–489ms（3 轮 6 次） | 3（三页各 1） | — |
| B 关动画 | **4–7ms** | **0** | **生效**（动画归零、页根零执行） |
| C 隔离重组 | 460–478ms | 3（与 A 相同） | **未生效**：movableContentOf 同位复用仍执行内容 lambda |
| D 空内容 | — | 页面不存在 | — |

C 组操纵未生效的说明：`movableContentOf` 仅在内容**移动**时保状态，父级重组同位重调用仍会
执行内容——因此 **C 组数据不构成「页面重组被隔离」的证据**，该因果问题实际由 **B 组回答**：
B 组页根 0 执行 + 0 动画，长帧原样存在 → **页面重组不是长尾的原因**。

## 6. 结论

1. **长尾形态**：每次有效 Tab 切换产生 1 条 158–240ms 的长帧（Dropped Frame / Buffer Stuffing），
   其余帧 p50≈9ms；48 轮 × 2 切换全部复现，无一例外。
2. **长帧六维归因**：UI 线程 Compose 重组 + measureAndLayout + draw 记录（≈115–175ms 重组/布局，
   7 个重组域）；RT/GPU ≤10ms、GC 无、调度无、动画路径排除（B 组）。
3. **页面内容排除**：D 组三页为空 Box，长帧原样（229/161ms）→ 长尾与页面内容（图表/列表/壁纸）无关。
4. **页面重组排除**：B 组页根 0 执行仍长帧 → 长尾与页面重组无关。C 组操纵未生效，不作证据。
5. **重组域归属**：长帧内 7 个重组域在页面内容之外（chrome/布局层：AppNav 结构、ScrollablePage
   包装、顶栏、导航条、覆盖层等），单组件级归因需开 composition tracing 二分（见 §8）。
6. **与 A-1 的衔接**：A-1 排除了数据查询/图表计算/壁纸解码；A-2 进一步排除动画、页面内容、
   页面重组；剩余嫌疑收敛到**切换帧的常驻 chrome 重组 + 全树 measure/layout 重跑**。

## 7. 是否支持/否定「Pager 预加载为主要原因」

**否定（以现有证据的强度）**：

- 若长尾源于三页常驻的**页面内容预组合/预布局代价**，D 组（空内容）应显著缩小长尾——实测不变。
- 若长尾源于切换时的**页面重组放大**，B 组（页根 0 执行）应消失——实测不变。
- 长帧分解显示代价在 chrome 层重组域，与 beyondBoundsPageCount 携带的页面子树无直接对应。

**保留的限定**：按 GPT 本批约束（不得修改 Pager 预加载数量），未做 `beyondBoundsPageCount=0`
对照组 E；上述为间接排除。若后续仍需彻底确认，可在获批批次补 E 组（1 组 × 3 重复即可）。
但即使 E 组出现差异，其机制也应解释为 chrome/布局树规模效应，而非「预加载导致查询/重组放大」。

## 8. 下一步推荐方案（仅建议，不实施）

1. **组件级二分定位**（首选）：开 Compose composition tracing（或逐层剔除法）把 §4 的 7 个
   重组域定位到具体组件（候选：AppNav 顶层重组传播、ScrollablePage 包装、顶栏四按钮、
   FreshNavBar、PullToRefreshContainer、覆盖层壳、壁纸主题层）。
2. **重组域收缩**：定位后对非目标组件做 skip/稳定化（参数稳定、状态下沉），目标是让切换帧
   重组域 ≤1 个。
3. **布局重跑收缩**：traversal/measureAndLayout 随重组域收缩应同步下降；若仍超预算再单独查
   布局树规模。
4. （可选）E 组 beyondBoundsPageCount 对照，彻底关闭预加载争议。
5. **导航体验方向**：远距 tab 的过渡语义（Fade Through 等）属产品裁决项，与本次根因无关，单独拍板。
