## 0. 结论

**（2026-11-23 修订：补入「屏幕一直未熄」这一事实后，结论已翻转，见 `1.2。）**

今天这一屏里有三个数，**没有一个是对的**：

| 显示 | 值 | 真相 | 性质 |
| --- | --- | --- | --- |
| 今日亮屏 | 0 分钟 | ≈ **10 小时 40 分**（00:00–10:40，屏幕整晚亮着） | **漏算**（应为 640 分钟量级） |
| 应用构成 共 | 24 小时（屏迹 100%） | ≈ 10.7 小时 | **错日归属**（数值本身对，日期错） |
| 日间 / 夜间 | 0% / 100% | — | **除零兜底**（无数据被渲染成「全是夜间」） |

昨天（11-22）显示 629 分钟，真相是 **24 小时**；周六（11-21）显示 1368 分钟，真相约 11 小时。
**长亮屏场景下，App 的亮屏时长与应用时长都会失真。**

两条独立的故障线：

- **线 1（漏算，本次用户报的现象）**：MIUI 的 SCREEN 事件是**滚动窗口**；「只开一次屏、永不熄屏」的场景下，
  开机事件一旦滚出缓冲，App 就再也看不到「屏幕还亮着」→ 该日亮屏记 **0**。
- **线 2（错日归属）**：checkin 给的是 **24 小时窗口**，解析器把整段按「区间结束日」归属 →
  屏迹那 24 小时全记在 11-23。

（checkin dump 头部：`Currently Active:com.screentrace.app,`）。

`SCREEN_INTERACTIVE` / `SCREEN_NON_INTERACTIVE` 事件为 **0 条**。
该依据只说明**事件已滚出缓冲**，不能说明**屏幕没亮**。补入 `1.1 的事实后，
正确结论是：**事件缺失 = 漏算，不是真值**。

## 3. 线 1：亮屏时长为什么会漏算（用户报的现象）

### 3.1 机制

- 屏幕一直亮 → 系统只发一次 `SCREEN_INTERACTIVE`，**永远没有** `SCREEN_NON_INTERACTIVE`。
- 解析器把「未闭合的开屏」收在**缓冲最后一条事件**上
  （`UsageDumpParser.kt` 的 `on?.let { screens.add(it to intervalEvents.last().ms) }`）。
  所以**在开机事件还在缓冲里的时候**，每次拉取都能累计到「拉取时刻」为止——这解释了
  11-21 17:44→11-22 10:28 那条 17.4 小时的会话。
- 但 MIUI 的事件缓冲是**滚动窗口**（本项目代码注释里已记：实测只保留最近几小时）。
  开机事件滚出缓冲后：
  - 解析器产不出任何开屏会话 → 本轮对该日/次日的亮屏贡献为 **0**；
  - 入库侧 `IngestPipeline` 只对**有新入库区间**的日期做重算（`rangeStart..rangeEnd`），
    没有新区间就**根本不重算** → 11-23 的 `screenMin` 停在 **0**。

### 3.2 为什么「应用在前台＝屏幕亮着」这条兜底也没救回来

解析器确实把**应用前台区间**并进了屏幕会话（`UsageDumpParser.kt`：
`SessionUnion.union(screens + foreground.spans)`，注释写明「应用在前台时屏幕必然是亮的」）。
但本例里应用前台区间同样来自 `ACTIVITY_RESUMED/PAUSED/STOPPED` 事件——
周六下午那次 `ACTIVITY_RESUMED` 也已滚出缓冲，缓冲里只剩 11-23 10:38 的几条
（`PAUSED/STOPPED` 10:38:45、`RESUMED` 10:38:47 / 10:39:01），于是前台区间也只有 1 分钟量级。

**即：只要「一直亮屏」持续到超过缓冲窗口，两条来源一起断，App 就彻底看不到屏幕还亮着。**

## 4. 线 2：应用时长错日归属

### 4.1 机制

MIUI 的 checkin dump 给的每段区间是一段**约 24 小时、以 ~09:2x 本地时刻为锚**的窗口
（**不是自然日**）。而 `UsageDumpParser.kt:385` 把整段按区间结束日归属：

    val date = Instant.ofEpochMilli(iv.endMs - 60_000).atZone(zone).toLocalDate()

本次窗口 `[11-22 10:31, 11-23 10:31]`，屏迹的 `totalTimeUsed` = 86,400,000 ms（**正好 24 小时**）。
这 24 小时在现实中**是真的**（屏幕亮着、屏迹在前台），但它被整段记在 11-23：
11-23 只过了 10.7 小时，却显示 24 小时。

### 4.2 为什么「正好 1440」没被拦下（顺带查实）

| 判据 | 位置 | 为什么没拦住 |
| --- | --- | --- |
| 单应用硬上限 | `IngestSanity.kt:81` `totalMs > MINUTES_PER_DAY * 60_000L` | 判据是 **>**，本例正好 **=** 86,400,000 → 不触发 |
| 当天应用合计 vs 屏幕时长 | `IngestSanity.kt:117` `if (reference < MIN_REFERENCE_MIN) return MINUTES_PER_DAY.toDouble()` | 当天 screenMin=0 → 参照物取 1440 上限 → 合计 1440 **不超** |
| 解析期总量约束 | `UsageDumpParser.kt:468` `screenMs > 0 && …` | 前置条件不成立 → **整条相对判据被跳过** |

**但请注意：在本场景里「1440」这个值本身是对的**（真的亮了 24 小时）。
所以门禁**不该**简单地把它丢掉——**该修的是归属日，不是数值**。
这一点很重要：初版诊断把 1440 当成「编出来的假值」是不准确的。

## 5. 最小复现（用 App 自己的解析器跑）

合成一段 24 小时 checkin 区间（`beginTime=11-22 10:31`, `endTime=11-23 10:31`）+
一行 `package=com.screentrace.app totalTimeUsed=86400000`，喂给 `UsageDumpParser.parse`：

    PROBE2 interval hours=24.0
    PROBE2 days=[]                                       ← 该日没有任何屏幕指标
    PROBE2 appUsage 2026-11-23 com.screentrace.app totalMs=86400000 min=1440.0 launches=2
    PROBE2 sanity dropped=[] appRowsAfter=1 hourAfter=0

输出与真机库里 11-23 屏迹 = **1440 分钟完全一致**；`IngestSanity.check` 的 `dropped=[]`
说明门禁确实没拦（在本场景下**不该拦**，见 `4.2）。

对照：把**真机当前**的 dump（10:41 拉的，checkin 段已变「无数据」）喂进同一个解析器，
输出是「亮屏 1 分钟、屏迹 1.15 / 75.32 分钟」——说明
**1440 那行来自 10:31 那次「checkin+data」的拉取**，且入库取大、不会被后来的小值改回去。

（探针完整输出：`evidence/bug_idle_day_fake_24h/probe_output.txt`）

## 6. 影响面与次生问题

1. **长亮屏期间的数据会持续恶化**：滚进缓冲的事件越少，可观测的亮屏时长越少，
   而真值恒定 → 越往后偏差越大（今天 0 分钟 vs 真相 10.7 小时）。
2. **脏值不自愈**：`app_usage` 取大写入，后续小值改不回来。
3. **checkin 可用性会漂移**：`pull_log` 记录 10:38 之后「checkin 无数据（plain-nodata），本次明文主导」，
   说明同一 ROM 上 checkin 段会时有时无 → 采集主通道随时可能只剩明文一路。
4. **日/夜条除零**：`AppViewModel.kt:1375` `dayPercent = if (todayTotalMinutes <= 0) 0 else …`
   → 夜间取补数 100%，无数据被渲染成「全是夜间」。

## 7. 候选方案（供裁决，本轮**不实施**）

### 方案 A：跨拉取维持「屏幕还亮着」的状态（治**线 1**，用户报的现象）

在会话层持久化「开屏未闭合」：本次拉取若没看到 `SCREEN_NON_INTERACTIVE`，
而上一轮存下的 SCREEN 会话正好收在上轮拉取时刻 → 判定屏幕仍在亮，
把该会话**延展到本轮拉取时刻**再并入并集。

- 效果：亮屏时长按真实连续亮屏时间累计，日切分后每天 ≈ 真相（周六 ~11h、周日 24h、今天 ~10.7h）。
- 代价：需要持久化「开屏状态」（可复用 `screen_session` 表 + 一个开屏标记）；
  **风险点**：设备重启 / 拔线熄屏 / 系统强制息屏时，判断会失准（需要用「上次会话结束时刻 == 上次拉取时刻」
  这类严格条件兜底，重启后 `SCREEN_INTERACTIVE` 会重新出现，不会误判为继续亮）。
- 口径影响：亮屏时长口径更准，属**收紧/修正**，不改 `3-4 文本。

### 方案 B：checkin 区间按天分摊（治**线 2**）

把 `UsageDumpParser.kt:385` 的「归属日」改为按区间覆盖的各日分摊，权重复用现成的
`dayWeights`（`UsageDumpParser.kt:582`，In-memory 已在用同一套逻辑）。

- 效果：屏迹的 24 小时按 `[11-22 10:31→24:00] ≈ 13.5h` 与 `[00:00→11-23 10:31] ≈ 10.5h` 落两天。
- 代价：**改需求文档 `3-4「应用时长按区间归属日」口径**，所有历史日的应用排行数值会变
  （每个 24h 窗口约 9.4 小时的使用量从结束日挪回开始日）→ 需配套历史重算。
- 注意：分摊只解决「哪天」的问题，**不解决「亮屏是 0」**——今天 11-23 的亮屏真相仍然要有方案 A 才准。

### 方案 C：门禁收紧（只补漏，不改数）

- 把 `> 24h` 改成 `>= 24h`（或留容差）、相对判据在前置条件不成立时不再整条跳过。
- **但**：在「真的亮 24 小时」的场景下，这些值是合理的；一刀切丢弃会**丢掉真实数据**。
  因此建议门禁只在**证据自相矛盾**时丢弃（例如「当天屏幕证据为 0 却出现应用时长」且屏幕证据不是缺失而是明确为 0），
  并且**与方案 A 配套**——A 修好亮屏后，相对判据才重新有参照物。

### 方案 D：UI 诚实化（止血，不改数据）

当天无屏幕证据时显示「该日亮屏数据缺失（系统事件已过期）」而不是 0 分钟；
日/夜条在无数据时不显示 0%/100%。**库里数值不变**，只是不骗人。

### 7.1 待裁决问题（给 GPT）

1. **方案 A 的跨拉取「开屏状态」是否可接受？** 它需要新增持久化状态（是否允许动 `screen_session` 表结构？
   还是可用现有行 + 一个标记位表达）。
2. **允许改 `3-4 的「区间归属日」口径吗？** 允许 → 历史各日应用数值会变，需要同步重算与改文档。
3. **历史脏数据怎么办？** ① 只清「可判定越界」的行（今天 1440 这行），不动其它天；
   ② 用现有 `SourceRebuild` 重算 11-18~11-23（可能连带删掉真实亮屏数据）；
   ③ 先不清，只止血。
4. **「当天无屏幕证据」要不要单列为可丢弃判据？** 在方案 A 落地前，这会让长亮屏的日子被整日丢弃，
   等于「用丢数据换不显示假数」。
5. **是否需要 UI 层（方案 D）单独兜底？**（数据未修好之前，至少别显示 0 分钟与 0%/100%）。
