## 0. 背景、范围与硬红线

### 0.1 现象

真机（Redmi 2407FRK8EC / Android 16 / HyperOS 3）自 2026-11-21 周六下午起，因插着 USB 且开启开发者模式「插着数据线不休眠」，**持续约 42 小时未息屏**。期间 App 读到的是：

- 今日页「亮屏 0 分钟」；
- 「应用构成 共 24 小时（屏迹 100%）」；
- 「日间 0% / 夜间 100%」。

库内事实：`day_summary` 2026-11-23 的 `screenMin=0`、`longestSessionMin=0`、`launches=2`；`app_usage` 2026-11-23 `com.screentrace.app` = **1440 分钟**；`hour_usage` 2026-11-23 **24 个桶全为 0**；`screen_session` 当日仅 3 秒；2026-11-21 17:44 → 11-22 10:28 存在一段 **17.4 小时**的连续会话。

### 0.2 本文档要解决什么

三件不同性质的事，必须分开处理、分开裁决：

1. **线 1 · 亮屏会话漏算**：长亮屏时该日亮屏时长记 0，且应用前台区间同断；
2. **线 2 · 跨日区间错日归属**：约 24 小时的 checkin 区间被整段记到区间结束日，导致单日应用时长 1440 分钟；
3. **线 3 · 缺分母被渲染成精确百分比**：日/夜条显示「日间 0% / 夜间 100%」。

线 3 是**独立的 UI 诚实性缺陷**，与线 1、线 2 无因果依赖：即使线 1/2 完全修好，只要某一天确实没有任何小时桶，线 3 依然会触发。它应当有独立的对策与独立的验收。

### 0.3 硬红线（本文档全程遵守，请评审逐条核对）

| 编号 | 红线 |
|---|---|
| RL-1 | **不得**把「上次没看到息屏事件就把会话延长到现在」当作方案。任何时长都必须能指认其证据类型。 |
| RL-2 | 长亮屏时长必须区分三类：**① 完整事件证据**（有 SCREEN_INTERACTIVE→NON_INTERACTIVE 成对事件）、**② 可靠状态证据**（有明确的状态采样或系统级状态证明，但缺成对事件）、**③ 无法确定的区间**。③类**不得伪造成精确时长**。 |
| RL-3 | **不得**把区间按自然日重叠比例分摊后**冒充**精确日数据。要么保留窗口级聚合，要么显式标记为估算并全链路携带标记。 |
| RL-4 | `screen_session` **是否改表结构必须由 GPT/负责人裁决**，本设计只给利弊与迁移方案，不自行决定。 |
| RL-5 | **不得**把 `IngestSanity` 的 `> 1440` 简单改成 `>= 1440`。本例 1440 分钟是**真实值**（长亮屏 42 小时里 24 小时确实在前台），门禁该放行；该修的是归属日与证据等级。 |
| RL-6 | **不得**动 CR-28 已冻结的数据口径：来源维度、legacy 只读、跨来源 SUM、会话 UNION 不相加、来源间区间不合并、`screen_session` 为日聚合唯一重算输入。 |
| RL-7 | **不得**清库、删备份、给 legacy 强分配身份、改 SUM 语义、混淆 UNION 与 SUM、无依据缩小总量、未经批准重算历史。 |
| RL-8 | **不得**把 ADB 合成手势冒充真实手指；**不得**把施工方自述冒充独立验证。 |
| RL-9 | UI **不得**把缺分母渲染成「日间 0% / 夜间 100%」。 |

### 1.2 线 1 · 亮屏会话漏算（该日亮屏 = 0 分钟）

**触发条件**：设备持续亮屏，`SCREEN_INTERACTIVE` 只在开屏时发一次，此后长时间不再有 `SCREEN_NON_INTERACTIVE`。

**为什么产不出会话**：

```kotlin
// app/src/main/java/com/screentrace/app/data/parse/UsageDumpParser.kt:303-312
val screens = mutableListOf<Pair<Long, Long>>()
var on: Long? = null
for (e in intervalEvents) {
    when {
        e.type == "SCREEN_INTERACTIVE" && on == null -> on = e.ms
        e.type == "SCREEN_NON_INTERACTIVE" && on != null -> { screens.add(on!! to e.ms); on = null }
    }
}
on?.let { screens.add(it to intervalEvents.last().ms) }   // ← 依赖缓冲里还留着开屏事件
```

MIUI 的 usagestats 事件缓冲是**滚动窗口**（实测只保留最近几小时）。开机事件滚出缓冲后：

- `on` 永远是 `null` → `screens` 为空 → 产不出任何亮屏会话；
- `foreground.spans` 同样来自 `ACTIVITY_RESUMED/PAUSED` 配对，事件滚出后也配不出来 →
- `normalizedScreens = SessionUnion.union(screens + foreground.spans)` 为空 → `screenDay` / `hourMatrix` / `longestDay` 全空。

**为什么入库侧也不兜底**：

```kotlin
// app/src/main/java/com/screentrace/app/data/IngestPipeline.kt:149 起
val incomingSessions = result.screenSessions + result.keyguardSessions
if (incomingSessions.isNotEmpty()) {
    ...  // 只有这里才重算 day_summary / hour_usage
}
```

本次拉取 `incomingSessions` 为空 → **整段重算逻辑不执行** → 该日的 `day_summary` 保持上一轮的旧值（`screenMin=0`）。

这正是「亮屏 0 分钟」的直接成因，也导致「应用在前台 ⇒ 屏幕亮着」这条兜底随之失效（前台区间同源同断）。

**真机佐证**：`screen_session` 当日仅 3 秒；而 2026-11-21 17:44 → 11-22 10:28 存在一段 **17.4 小时**连续会话——那是在缓冲还留有开屏事件时拉到的。长亮屏跨过缓冲窗口后，再也拉不到同样的会话。

### 1.3 线 2 · 跨日区间错日归属（应用 24 小时全压一天）

**checkin 的区间语义**：MIUI 的 `dumpsys usagestats --checkin` 输出里，`beginTime=… endTime=…` 描述的是**一个约 24 小时、以 ~09:2x 为锚的统计窗口**，不是「自然日」。真机样本 `reference/sample-checkin.txt` 的同一形态。

**归属代码**：

```kotlin
// app/src/main/java/com/screentrace/app/data/parse/UsageDumpParser.kt:385
val date = Instant.ofEpochMilli(iv.endMs - 60_000).atZone(zone).toLocalDate()
// → 整段按「区间结束时刻所在自然日」归属
```

于是 2026-11-21 09:2x → 2026-11-22 09:2x 这段 24 小时区间，**整段落进 11-23**（本例 `endMs` 落在 11-23 09:2x 附近，`-60_000` 只是为了避开边界抖动）。

**为什么恰好是 1440 分钟**：该区间内只有一个包在前台——`com.screentrace.app` 自己（长亮屏时人一直在看屏迹或别的应用，但系统的 `totalTimeUsed` 窗口里，屏迹是累计最长的那个）。合成复现里 `totalTimeUsed=86400000` 毫秒 = 1440 分钟。

**为什么小时矩阵全 0**：区间路径（`perUserInterval`）**只写 `app_usage`，不写 `hour_usage`**。`hour_usage` 来自 `hourMatrix`，而 `hourMatrix` 来自 `normalizedScreens`——线 1 已经断了。所以 11-23 的 24 个小时桶全是 0，而 `app_usage` 有 1440 分钟。

> **这两个数出自两条互不相干的管线**：`app_usage` 走区间/明文路径，`hour_usage` 走会话路径。线 1 让后者归零、线 2 让前者爆表，两者叠加才产生「应用 24 小时 / 亮屏 0 分钟 / 小时矩阵全 0」这个自相矛盾的组合。

### 1.4 线 3 · 缺分母被渲染成精确百分比

```kotlin
// app/src/main/java/com/screentrace/app/ui/AppViewModel.kt:1375
val todayTotalMinutes = todayHours.sumOf { it.minutes }
val todayNight = UsageCalculator.nightMinutes(todayHours)
val dayPercent = if (todayTotalMinutes <= 0) 0 else ((todayTotalMinutes - todayNight) * 100 / todayTotalMinutes)
```

`hour_usage` 24 桶全 0 → `todayTotalMinutes = 0` → `dayPercent = 0`。

```kotlin
// app/src/main/java/com/screentrace/app/uikit/AppBreakdown.kt:125-130
private fun DayNightBar(dayPercent: Int) {
    val left = dayPercent.coerceIn(0, 100)
    val right = 100 - left
    ... Text(text = "$left%", ...)   // 日间
    ... Text(text = "$right%", ...)  // 夜间
}
```

`right = 100 - left = 100` → 渲染成「日间 0% / 夜间 100%」。

**缺陷本质**：`dayPercent` 这个 Int 表达不了「**分母不存在**」与「**分母为 0 且日间占比真的是 0%**」两种不同状态，而 UI 把两者压成同一个 0。夜里不使用手机（正常情况）时 `hour_usage` 全 0 是**合法的**——此时显示「日间 0% / 夜间 100%」同样是错的（真实占比是「无数据」，不是「夜间 100%」）。

### 1.5 门禁为何未拦（且本例**不该**拦）

| 门禁位置 | 判据 | 本例是否成立 | 结论 |
|---|---|---|---|
| `IngestSanity.kt:81` | `it.totalMs > MINUTES_PER_DAY * 60_000L`（严格大于 24h） | 本例正好 **= 24h** → 不成立 | **不放行是对的**：长亮屏下 1440 分钟是真实值 |
| `IngestSanity.kt:117` | 参照物 `< 60` 分钟时退回 1440 上限 | 成立（当天 screenMin=0） | 上限 1440，合计 1440 → 不触发丢弃 |
| `UsageDumpParser.kt:468` | `screenMs > 0 && total > screenMs * 1.15` | 前置 `screenMs > 0` **不成立**（当天 0） | 相对判据无从生效 |
| `SourceRebuild.kt` | `MAX_DAY_MIN = 1440`、超 24h 清洗 | 恰好 1440 | 不清洗 |

**结论**：本例 1440 分钟**不是脏数据**，是**归属错误**。任何「把 1440 判成假值并丢弃」的改法都会**丢掉真实数据**，直接违反 RL-5 与 RL-7。

> 修订记录：初版诊断曾把 1440 判成「编出来的假值」，**该结论已推翻**（初版稿已从 `docs/` 撤下，存 `app/build/probe/`）。本设计沿用修订版判断。

## 2. 两个问题的复现条件

### 2.1 线 1 复现条件（亮屏漏算）

必要条件（同时满足）：

1. 设备持续亮屏 ≥ 缓冲区窗口长度（实测 MIUI usagestats 事件缓冲只保留最近数小时）；
2. 该窗口内**没有**产生新的 `SCREEN_NON_INTERACTIVE`（长亮屏即如此）；
3. 该窗口内的 `ACTIVITY_RESUMED/PAUSED` 事件也已滚出缓冲（否则前台区间还能兜底出 `normalizedScreens`）；
4. 拉取发生在上述事件滚出之后。

充分性验证（已做，App 自己的解析器）：用真机**当前** dump（checkin 已空、明文只剩最近几分钟）喂进解析器 → 输出「亮屏 1 分钟、屏迹 1.15 分钟 / 75.32 分钟」，**完全正常**。

→ 证明：线 1 的缺失**不是解析器永久性缺陷**，而是**数据在源端已经不存在**。解析器拿不到滚出缓冲的事件，只能产出一小段。这是设计约束的边界，不是可以靠改解析器补齐的。

### 2.2 线 2 复现条件（错日归属）

必要条件：

1. checkin 输出中存在 `beginTime=… endTime=…` 形态的区间（真机 MIUI 恒有）；
2. 该区间的 `endTime` 与 `beginTime` 落在**不同的自然日**（24 小时窗口几乎必然跨日，除非恰好 00:00 起算）；
3. 区间内的包在该日的 `totalTimeUsed` 较大（否则分摊到两天的误差不显著）。

**已验证的最小复现**（用 App 自己的解析器，不依赖真机）：

```text
输入：合成 24h checkin 区间 + package=com.screentrace.app totalTimeUsed=86400000
输出：PROBE2 appUsage 2026-11-23 com.screentrace.app totalMs=86400000 min=1440.0
      PROBE2 days=[]            ← 该日没有任何屏幕指标
      PROBE2 sanity dropped=[]  ← 门禁未拦
```

输出与真机库内 2026-11-23 屏迹 = 1440 分钟**分毫不差**。

### 2.3 两个问题的独立性

| | 触发源 | 写入的表 | 门禁 | 关系 |
|---|---|---|---|---|
| 线 1 | 源端事件滚出滚动缓冲 | `day_summary.screenMin`、`hour_usage`、`screen_session` | `IngestPipeline` 的 `incomingSessions.isNotEmpty()` 空转 | **独立** |
| 线 2 | checkin 窗口跨自然日 | `app_usage` | `IngestSanity` 按「> 24h」判 | **独立** |

线 1 让 `hour_usage` 归零，线 2 让 `app_usage` 爆表。**两者叠加才产生用户看到的自相矛盾**。修好任一条都不会自动修好另一条。这直接决定了：不能只做「一个 bug 一个补丁」，必须两条线各自给出方案。

### 3.2 证据状态机（线 1 核心：长亮屏时长的证据类型）

这是本文档最关键的一张图。**它明确规定了什么能被记成「精确分钟数」，什么只能被记成「有界区间」，什么必须留空。**

```text
                       ┌────────────────────────────────────┐
                       │  观察到 SCREEN_INTERACTIVE        │
                       └───────────────┬────────────────────┘
                                       │
                ┌──────────────────────┴───────────────────────┐
                │ 后续是否出现配对的 SCREEN_NON_INTERACTIVE？│
                └──────────────────────┬───────────────────────┘
                       观察到           │ 未观察到
          ┌────────────────────────────┴────────────────────────────┐
          │                                                         │
          ▼                                                         ▼

 │ 可入 hour_usage   │                                ▼               ▼

 └────────────────────┘              │【E2 可靠状态证据】  │  │【E3 无法确定区间】  │
                                       │ 有明确状态证明      │  │ 只能给出「≥ 起点」  │
                                       │ 「屏幕仍是亮的」    │  │ 无法给精确分钟数    │
                                       │ 但缺成对事件        │  │                    │
                                       │ ⇒ 只能记为          │  │ ⇒ 必须：            │
                                       │   有界区间 + 标记   │  │   不产生精确时长    │
                                       │   「估算/上界」     │  │   界面显示「无数据」  │
                                       │   不得写进精确列     │  │   或「≥ N 分钟」    │
                                       └──────────────────────┘  └────────────────────┘
```

### 3.3 归属状态机（线 2 核心：一个区间该记到哪一天）

            │
            ▼
   ┌────────────────────────┐
   │ begin 与 end 同自然日？ │

 └──────────────┘           │                  │
                          自然日窗口          滚动窗口（≈24h，以 09:2x 为锚）
                             │                  │
                             ▼                  ▼
                   ┌───────────────┐   ┌──────────────────────────────┐
                   │ 按该自然日   │   │ 【禁止】整段记到 end 所在日    │
                   │ 精确归属     │   │        （= 当前行为，线 2 缺陷） │
                   └───────────────┘   │                              │
                                       │  两条候选路径（见 §4.3）：   │

### 3.4 日聚合重算状态机（`IngestPipeline` 侧）

```text
   本次解析产出 sessions
            │
            ▼
   ┌──────────────────────────────────────┐
   │ incomingSessions.isNotEmpty()？      │
   └──┬───────────────────────────────┬──┘
   否 │                               是 │
      ▼                                ▼
 ┌────────────┐          ┌──────────────────────────────┐
 │ **不重算**  │          │ 按自然日切片：                 │
 │ 该日保持旧值│          │  stored = sessionDao.overlapping│
 │ screenMin=0 │          │  slice = SessionUnion.daySlices │
 │ （线 1 断点）│         │  重算 day_summary + hour_usage  │
 └────────────┘          │  与旧值取大（MergePolicy）       │
                        └──────────────────────────────┘
```

**关键点**：当前重算的触发条件是「**有没有新区间**」，而不是「**有没有新证据**」。线 1 的本质就是「证据在源端消失了，但库里也没有任何东西可用来触发重算」。修复必须围绕这一点做设计（见 §4.2）。

## 4. 方案对比与推荐

### 4.1 线 1 候选方案（长亮屏时长的来源）

**先明确被排除的方案**：

> ❌ **「上次没看到息屏事件，就把会话延长到本次拉取时刻」**
>
> 这是 RL-1 明令禁止的方案，理由是它**凭空造出精确时长**：
>
> - 上次拉取与本次拉取之间设备可能息过屏又亮起、可能中间重启、可能中间关机；
> - 延长出来的时长是「假设一直亮着」的上界，不是观测到的事实；
> - 它会把这条假设写进 `screen_session`，而 `screen_session` 是日聚合的唯一重算输入 → 假设会**被当成事实参与并集运算**，污染所有下游数字；
> - 它与 `IngestPipeline` 的跨拉取并集语义叠加后，误差会**单调累积**（每多拉一次就多延长一次）。
>
> 若确实要使用「上一次已知亮屏的时刻」这个信息，正确用法是**记为 E3（无法确定区间）的上界**，并在数据与 UI 上显式标记，**绝不写进精确时长列**。

候选方案如下：

| 编号 | 方案 | 做法 | 能修好什么 | 代价 / 风险 | 证据支持 |
|---|---|---|---|---|---|
| **A** | 跨拉取维持「屏幕还亮着」状态 | 新增一张「屏幕状态」持久化表，记录「上次确认亮屏的时刻」与「上次确认息屏的时刻」 | 提供 E2/E3 的**上界锚点**，让 UI 能说「≥ N 分钟」而不是「无数据」 | 新增状态表；状态本身也只是**推断**（见 §4.1.1）；不产生精确分钟数 | 真机 17.4 小时连续会话证明会话可以跨拉取存在 |
| **B** | 区间按自然日切分归属 | 跨日的 checkin 区间**按重叠比例切到各自然日**，而不是整段记到结束日 | 修线 2 的「单日 1440 分钟」 | **直接违反 RL-3**：重叠比例切分是**估算**，切出来的分钟数是假的精确值；且 §4.3 会论证这条路在大多情况下并不必要 | 真机区间样本 `reference/sample-checkin.txt` |
| **C** | 允许估算但**显式标记估算** | 与 B 同样的切分结果，但每个被估算的格子带 `ESTIMATED` 标记，一路带到 UI、统计、导出 | 能给出「有用的近似」，且不冒充精确 | 需要**数据模型 + UI + 备份 + 统计分母**四端同时支持标记；标记一旦在某端丢失就会退化成 B | 需 GPT 裁决「估算值是否可进日均/总量」 |
| **D** | UI 诚实化（缺分母不显示百分比） | `dayPercent` 从 Int 改为可空/带状态；无分母时显示「无数据」而非「0% / 100%」 | 修线 3 **完全独立** | 只改 UI + ViewModel，不动数据 | 真机 UI dump 直接佐证 |
| **E** | 维持现状 + 文档化 | 在需求文档写明「长亮屏期间屏幕时长可能记 0」 | 无 | 用户看到的是**错误数据**；违反 §7-16 红线 | — |

#### 4.1.1 关于方案 A 的关键限制（必须写清楚，否则会被误用）

方案 A 记录的是「上次**确认**亮屏的时刻」。但「确认」来自哪？只有三种来源：

1. **一次配对的 `SCREEN_INTERACTIVE`→`SCREEN_NON_INTERACTIVE`**（E1，精确）；
2. **一次未配对的 `SCREEN_INTERACTIVE`**（这是 E3 的上界锚点：只能说「从这一刻起，至少亮到下次确认息屏之前」）；
3. **应用前台区间**（`ACTIVITY_RESUMED`→配对）——这是「屏幕亮着」的**可靠状态证据**，因为 Android 在前台 Activity 可见时屏幕必然亮着（除非息屏但 Activity 仍可见——MIUI 上确有此情形，见 §13.1 的 N4）。

因此方案 A 的正确定位是：

```text
持久化「状态锚点」，不持久化「时长结论」。

  下次拉取时：
    若拿到配对事件  → E1：精确区间，正常入库 screen_session
    若拿到未配对事件 → E3：得到上界 [开屏时刻, 拉取时刻]，标记为上界，不进精确列
    若什么都没拿到   → 沿用上次的锚点，上界继续延长（仍然只是上界）
```

**再次强调**：上界 `≥ N 分钟` 与精确 `N 分钟` 在数据模型与 UI 上必须是**不同的东西**。

### 4.2 五个方案的对比小结

| 维度 | A（状态锚点） | B（直接切分） | C（切分+标记） | D（UI 诚实化） | E（现状） |
|---|---|---|---|---|---|
| 是否产生**精确**分钟数 | 否 | 是（假的） | 否（标为估算） | — | 否 |
| 违反 RL-3 | 否 | **是** | 否 | 否 | 否 |
| 是否需要改数据模型 | 需要 | 不需要 | 需要 | 不需要 | 不需要 |
| 是否需要改备份格式 | 视方案而定 | 否 | **需要**（v7） | 否 | 否 |
| 是否影响 CR-28 口径 | 需谨慎（见 §8） | 否 | 需谨慎 | 否 | 否 |
| 能否独立交付 | 可单独做 | 不可单独做 | 需配套 | **可单独做** | — |
| 用户可见改善 | 「≥ N 分钟」 | 假精确 | 「约 N 分钟（估算）」 | 「无数据」 | 无 |

**推荐组合**：**D（必做，且可独立先做）+ A（推荐，但需裁决是否引入新表）+ C 视 §4.3 裁决**。
**明确不推荐 B**。
### 4.3 线 2 候选方案：「保留窗口级聚合」vs「允许估算但标记估算」

这是 GPT 点名要求对比的两案。

#### 方案甲 · 保留窗口级聚合

**定义**：不把跨日的滚动窗口切到各自然日，而是**把该窗口整体作为一个「窗口级记录」保留**，在需要按日呈现时，明确声明「该窗口跨日，无法拆到日」。

**具体形态**：

- 数据层：为跨日窗口引入「区间级（interval-level）」记录载体（可以是新增一张 `usage_window` 表，也可以复用 `screen_session` 的语义扩展），记录 `[beginTime, endTime] + 包 + 时长`；
- 聚合层：**不**把窗口时长计入任何单日的 `app_usage.minutes`；
- 展示层：
  - 应用排行页：跨日窗口的包**单独成行**，标注「11-21 09:2x → 11-22 09:2x（跨日窗口）」，时长显示为一个**窗口总量**，不假装是某一天；
  - 「应用构成」卡：**只统计可归属到单日的时间**；跨日窗口部分以「另有 24 小时来自跨日窗口，无法按日拆分」的形式单列；
  - 日/夜条：**分母只含有归属明确的时间**，跨日窗口不参与；
  - 单日趋势图（统计页 / 日历页）：该日**可能为空**，需明确「无单日归属数据」而不是 0。

**优点**：

1. **零伪造**。任何显示的数字都能指认其来源区间；
2. **不触碰 CR-28 冻结口径**：不涉及 SUM / UNION 语义变化；
3. **备份兼容最简**：新表可选加，旧备份不受影响；
4. **不需要给每个格子打标记**，因此不会在某个端点丢标记。

**缺点**：

1. **用户看到的信息变少**：原来「某天用了很多」变成「某个跨日窗口用了很多」，对「今天用了多久」这类问题没有直接答案；
2. **单日趋势出现空洞**：长亮屏 / 长会话场景下，统计页与日历页的某些天会缺数；
3. 需要新增「窗口级」的展示语言与 UI 元素（新的呈现形态）。

#### 方案乙 · 允许估算但显式标记估算

**定义**：把跨日窗口按**自然日重叠比例**切到各天，但每个被切分的格子携带 `ESTIMATED` 标记，一路贯穿数据层 → ViewModel → UI → 导出。

**标记必须贯穿的链路**：

```text
  解析层   : AppUsageRow.minutes  +  isEstimated: Boolean
  入库层   : app_usage 表增列 estimated（或独立标记表）
  聚合层   : day_summary.screenMin / app_usage.minutes 需区分「精确部分」与「估算部分」
  ViewModel: TodayData / StatsData 需携带「精确值 + 估算值 + 总量」三者
  UI 层    : 数字前缀「约」，或用不同色带 / 图标区分，并给出「其中 X 分钟为估算」说明
  统计层   : 日均 / 总量的分母口径需裁决「估算值是否计入」
  导出层   : CSV / JSON 必须带标记列；HTML 报告必须带标记
  备份层   : 备份 schemaVersion +1，估算标记必须往返保真
```

**优点**：

1. **单日视图连续**，不出现空洞；
2. 对「长亮屏当天到底用了多久」给得出**有用的近似**；
3. 与产品直觉一致（「大概用了一天」）。

**缺点**：

1. **标记一旦在某端丢失就退化成方案 B**（假精确）——这是最大的风险；
2. **分母口径会变得含混**：「日均 7 小时」里有多少是估的？
3. **备份 / 合并 / 跨设备**三处都要处理估算标记，CR-28 的「同 (date,pkg) 取大」在混合精确 / 估算时需要新规则；
4. **估算比例本身是任意的**：一个 24 小时窗口按重叠比例切到 11-21 / 11-22，切出来的「11-21 有 18 小时」在长亮屏场景下可能与事实完全不符。

#### 两案对比结论

| 维度 | 方案甲（保留窗口级聚合） | 方案乙（允许估算但标记估算） |
|---|---|---|
| 是否伪造精确日数据 | 否，不伪造 | 否，不伪造（前提：标记全链路保真） |
| 标记丢失风险 | 无标记需求 | **高**（漏一处即退化为假精确） |
| 对 CR-28 的冲击 | 小（不涉及 SUM / UNION） | 中（取大规则需扩展、备份需新版本） |
| 对备份格式的冲击 | 小（新表可选；旧备份可读） | **大**（schemaVersion 6 → 7，旧读取器 `ignoreUnknownKeys` 会静默丢标记） |
| 实现复杂度 | 中（新增窗口级存储 + 新 UI 形态） | 高（标记贯穿 7 个层） |
| 单日连续性 | 差（有空洞） | 好 |
| 用户理解成本 | 中（要解释「跨日窗口」） | 低（「约 18 小时」） |
| **长期可维护性** | **高**（语义清晰，难错） | 中（标记体系会随功能增长而漏标） |

**本文档的倾向性意见（供 GPT 参考，不代替裁决）**：

1. **短期推荐方案甲**，理由：它不需要给每个数字挂标记，因此在「标记丢失 → 假精确」这个最大的风险上没有暴露面；而 GPT 的硬约束里最强调的正是「不得把估算冒充精确」；
2. **方案乙可以作为后续增强**，前提是：① 先完成方案甲；② 标记体系与端点清单一次性定死并写进需求文档；③ 备份兼容策略与 CR-28 取大规则**同时**定稿；
3. **两案都不解决线 1**（亮屏 0 分钟）——线 1 需要 §4.1 的 A / C / D 组合；
4. **两案都需要先裁决 §4.4**（`screen_session` 是否改表结构），因为窗口级记录的载体选择依赖于它。

### 4.4 `screen_session` 是否改表结构：利弊与迁移方案（**待裁决，本文档不自行决定**）

**背景**：CR-28 已冻结「`screen_session` 是日聚合的唯一重算输入」「同来源并集、跨来源不合并」。任何改表结构都会触及这两条，因此必须由 GPT / 负责人裁决。

| 选项 | 改动 | 优点 | 缺点 | 对 CR-28 的影响 | 迁移成本 |
|---|---|---|---|---|---|
| **选项 1：不动表** | `screen_session` 保持 `(startMs, endMs, kind, sourceDeviceId)`，只存 **E1 精确区间** | 零 Room 迁移、零备份版本变更、UNION 语义完全不动、日聚合输入仍是纯精确值 | 估算 / 上界信息**没有结构化落库位置**，只能塞进 `pull_log.note` 文本或另建文本表；UI 只能说「无数据」，给不出「≥ N 分钟」 | **无** | **无** |
| **选项 2：加列** | 新增 `evidence`（`EXACT` / `BOUNDED` / `ESTIMATED`）+ `confidence` 列 | 证据类型结构化、可查询、可备份往返；日聚合可按证据类型分列 | Room 8 → 9；`MergePolicy.mergeSessions` 要重新定义「不同证据类型的区间能否合并、合并后取强还是取弱」；若估算区间进了并集，`day_summary.screenMin` 就不再是纯精确值，**污染 CR-28 冻结口径** | **高**（并集合并语义变更） | 中（1 个 migration + schema JSON + 备份 v7） |
| **选项 3：独立新表** | 新增 `screen_evidence`（或 `usage_window`）表承载估算 / 上界 / 窗口级记录，`screen_session` 完全不动 | `screen_session` 保持「日聚合唯一重算输入」的纯精确语义；CR-28 零冲击；估算信息有结构化落库位置 | 多一张表要维护；**「估算区间是否计入 `day_summary.screenMin`」仍需单独口径裁决**——若计入，则 `day_summary` 同样不再纯精确 | **低**（`screen_session` 不动） | 中（1 个 migration + schema JSON + 备份 v7） |
| **选项 4：不动表 + 纯文本登记** | 新增一张只存文本的 `screen_gap_note` 表（date, reason, upperBoundMin, sourceDeviceId） | 成本最低；不触碰任何数值列 | 文本表无法参与聚合与合并；只能用于 UI 提示 | **无** | 低 |

**本文档的倾向性意见**：

1. **选项 1 或 3 优先于选项 2**——选项 2 会把估算值灌进 CR-28 冻结的并集管线，风险最大；
2. 若最终采用方案乙（估算进日数据），**选项 3 是唯一不破坏 CR-28 的载体**，但它带来的「估算是否计入 `day_summary.screenMin`」问题必须同时裁决——建议答案是**计入但分列**（新增 `screenMinEstimated` 列，`screenMin` 保持精确部分），否则 UI 无法区分；
3. 若采用方案甲（窗口级聚合），选项 1 + 一张 `usage_window` 表即可，同样不动 `screen_session`；
4. **无论选哪个，都不得**在未裁决前动 `screen_session` 的表结构或 `MergePolicy.mergeSessions` 的语义。

### 4.5 门禁方案：为什么不能把 `> 1440` 改成 `>= 1440`

**直觉方案**：`IngestSanity.kt:81` 的 `it.totalMs > MINUTES_PER_DAY * 60_000L` 改成 `>=`，让 1440 分钟被当作脏数据丢掉。

**为什么错**：

1. **会丢掉真实数据**。本例 1440 分钟来自 24 小时滚动窗口里的真实 `totalTimeUsed`，长亮屏 42 小时里屏迹确实长期在前台；丢掉它 = 用「界面整齐」换「真实数据」，违反 RL-7 的「无依据缩小总量」与 §7-16 红线；
2. **会误伤真实整天使用的用户**。真机确实存在「单日单个应用使用满 24 小时」的可能（游戏挂机、导航常驻），改 `>=` 会把这些正常数据全部清空；
3. **把线 2 的归属错误掩盖成丢弃问题**。真正的 bug 是「24h 窗口整段记到一天」，不是「24h 这个数值本身非法」；
4. **门禁会失去它的本职**。`> 1440` 是「物理上不可能」的最后一道硬判据；改成 `>=` 之后，它就变成了「可疑值检测器」，而可疑不等于非法。

**推荐的替代门禁设计（区分七种状态）**：

```text
单日应用合计 = 1440 分钟时，必须区分：

  ① 真实 1440       —— 证据支持（配对事件 + 完整归属）  → 放行
  ② 窗口造成的 1440 —— 来自跨日滚动窗口整段归属        → 修归属（线 2），不是丢弃
  ③ 缺屏幕证据      —— screenMin=0 导致相对判据无从生效 → 放行，但标记「缺分母」
  ④ 部分缺失        —— 有事件但缓冲滚出                → 标记「部分缺失」
  ⑤ 采集失败        —— dump 失败 / 被截断              → 失败路径，不入库
  ⑥ 暂无数据        —— 该日本来就没拉过                → 不产生行
  ⑦ 真实为零        —— 确实一天没用                    → 放行
```

实现上意味着：`IngestSanity` 需要拿到「该日的证据状态」而不是只看 `totalMs` 与 `screenMin` 两个数。**这本身就是 §5 数据模型变更的动因之一**（需要落库一个质量标记）。

### 4.6 推荐方案（汇总）

| 优先级 | 内容 | 是否需 GPT 裁决 | 可否独立实施 |
|---|---|---|---|
| P0 | **方案 D · UI 诚实化**（缺分母不显示 0% / 100%；无数据不显示「0 分钟」） | 否（是修正错误渲染，不是口径变更） | **可** |
| P0 | **线 2 归属修正**（跨日窗口不再整段记到结束日） | **是**（改动 §2.2 口径 + 需先定 §4.3 走甲还是乙） | 需先裁决 |
| P1 | **方案 A · 屏幕状态锚点**（提供上界，不产生精确时长） | **是**（需裁决是否新增表 → §4.4） | 需先裁决 |
| P1 | **门禁七态化**（§4.5） | **是**（新增质量标记 = 口径变更） | 需先裁决 |
| P2 | **方案乙 · 估算标记全链路**（若 §4.3 裁决走乙） | **是** | 需先裁决 |

**推荐路径**：P0 独立先做（改动面小、可立即验证、不触碰任何冻结口径）→ 同时提请 GPT 裁决 §4.3 与 §4.4 → 裁决后按「线 2 归属 → 门禁七态 → 方案 A → 方案乙」的顺序推进，每步单独提交。

## 5. 数据模型变更建议

### 5.1 总体原则

1. **精确值与估算值必须分列存储**，不能混在同一列靠外部约定区分；
2. **「无数据」不是 0**——要么没有行，要么有一个显式的质量标记；
3. **证据类型要能被查询**（「这一天有多少时间是估算的」），不能只存在于 `pull_log.note` 文本里；
4. **不新增 / 不修改 CR-28 已冻结的语义**：来源维度、legacy 只读、跨来源 SUM、会话 UNION 不相加；
5. **任何新列都必须是可空或带默认值**，保证旧备份 / 旧库可读。

### 5.2 建议的「数据质量」枚举（跨表共用）

```text
enum class DataQuality {
    EXACT,          // 完整事件证据推导出的精确值
    UPPER_BOUND,    // 只有上界（如「≥ N 分钟」），不是精确值
    ESTIMATED,      // 估算值（窗口分摊等），带估算依据
    PARTIAL,        // 部分缺失（有数据但不完整）
    MISSING,        // 采集失败 / 无数据
    UNKNOWN         // 来源不明（legacy 行的默认态）
}
```

**注意 `UNKNOWN` 与 `EXACT` 的关系**：CR-28 的 legacy 行（`__legacy__`）**不得**被强分配身份，也**不得**被追溯标成 `EXACT`（无法证明）。因此 legacy 行的默认质量标记必须是 `UNKNOWN`，而不是 `EXACT`——这是一条必须写进 CR-28 兼容分析的约束。

### 5.3 逐表建议

| 表 | 现状 | 建议 | 依赖 §4.4 裁决 |
|---|---|---|---|
| `screen_session` | `(startMs, endMs, kind, sourceDeviceId)`，只存精确区间 | **选项 1**：不动。**选项 3**：另建 `screen_evidence` 表承载非精确证据 | 是 |
| `day_summary` | `(date, screenMin, screenUnlockMin, unlocks, launches, longestSessionMin, pulledAt, sourceDeviceId)` | 新增可空列 `screenQuality: String?`（取值见 §5.2）。**默认 `null` = 沿用旧语义**，旧行与旧备份不需要回填 | 否（加可空列 + 默认值即可） |
| `hour_usage` | `(date, hour, minutes, sourceDeviceId)` | 新增可空列 `quality: String?`，语义同上 | 否 |
| `app_usage` | `(date, pkg, name, minutes, launches, category, sourceDeviceId)` | 新增可空列 `minutesEstimated: Boolean = false`（或 `quality`）。**`minutes` 永远是「该格子的总分钟数」，另设一列标明其中是否含估算** | 否 |
| 新表 `usage_window`（方案甲） | 无 | `(beginMs, endMs, pkg, minutes, launches, kind, sourceDeviceId)` —— 承载跨日滚动窗口的**窗口级**记录，**不参与任何单日 `app_usage` 聚合** | 是（是否采用方案甲） |
| 新表 `screen_evidence`（选项 3） | 无 | `(startMs, endMs, kind, quality, sourceDeviceId)` —— 承载 E2 / E3 证据（上界 / 部分缺失），**不进 `screen_session` 并集** | 是 |

### 5.4 ViewModel / 领域层的模型变更

```text
TodayData:
    dayPercent: Int              →  dayPercent: Int?          // null = 无分母
    dayPercentQuality: String?                                 // 可选：标明该值来源

Summary（day_summary 派生）:
    screenMin: Int               →  screenMin: Int
    screenQuality: String                              // EXACT / PARTIAL / MISSING / UNKNOWN
    screenMinEstimated: Int = 0                        // 若走方案乙：其中估算的部分
```

**关键**：`dayPercent` 从 `Int` 改为 `Int?` 是**类型层面的诚实化**——它让「无分母」在编译期就必须被处理，而不是靠 `if (total <= 0) 0` 这种运行时兜底糊过去。

### 5.5 仓库 / DAO 层

- `DaySummaryDao.get(key, src)` 的返回类型不变，但**新增**「按质量查询」的方法（供统计页 / 周期总结页区分精确与估算）；
- `AppUsageDao` 的读取需要能返回「该行是否含估算」；
- **CR-28 约束**：`MergePolicy.mergeDay` / `mergeHour` / `mergeSessions` 在涉及新列时：
  - 旧行（无新列）视作 `UNKNOWN`（保守），**不得**因为新列为空就丢弃旧行；
  - 合并时**质量标记取弱**（`UNKNOWN` 弱于 `EXACT`；`ESTIMATED` 弱于 `EXACT`）——**保守方向**，宁可标弱不标强；
  - **legacy（`__legacy__`）行仍只读**，不参与任何改写。

## 6. Room migration 方案

### 6.1 现状

- 数据库结构版本：**`version = 8`**（`ScreenTraceDatabase.kt`）；
- 备份文件 `schemaVersion`：**`6`**（`BackupCodec.SCHEMA_VERSION`，`BackupModels.kt:172`）——**两套版本号，不要混**；
- 导出的 schema JSON 目录：`app/schemas`（`ksp { arg("room.schemaLocation", ...) }`）。

### 6.2 各选项对应的迁移

#### 选项 1 / 选项 4（不动 `screen_session`）

```text
Room: 8 → 8（无迁移）
      仅当新增「质量标记列」时：
        8 → 9  ALTER TABLE day_summary ADD COLUMN screenQuality TEXT
        8 → 9  ALTER TABLE hour_usage  ADD COLUMN quality TEXT
        8 → 9  ALTER TABLE app_usage   ADD COLUMN minutesEstimated INTEGER NOT NULL DEFAULT 0
      （三列均可空 / 带默认值，旧行不需要回填 —— 符合「不追溯改写历史」的红线）
Backup: 6 → 6（若备份 DTO 不带标记）或 6 → 7（若带标记，见 §7）
```

#### 选项 2（`screen_session` 加列）

```kotlin
val MIGRATION_8_9 = object : Migration(8, 9) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE `screen_session` ADD COLUMN `evidence` TEXT NOT NULL DEFAULT 'UNKNOWN'")
        db.execSQL("ALTER TABLE `screen_session` ADD COLUMN `confidence` REAL")
    }
}
```

**警告（必须写进实施说明）**：

1. 新列的默认值必须是 `UNKNOWN` 而不是 `EXACT`——旧行的证据类型其实**不可知**，按 RL-7「不追溯改写历史」不得谎称精确；
2. `MergePolicy.mergeSessions` 的**并集合并语义必须同步扩展**（不同 evidence 的区间能否合并？合并后取强还是取弱？）——这会**触及 CR-28 冻结口径**，因此选项 2 的迁移**不是纯技术改动**，必须先裁决；
3. 若估算区间进入并集，`day_summary.screenMin` 就不再是纯精确值 → 必须同步加 `screenMinEstimated` 分列，否则 UI 与备份都无法区分。

#### 选项 3（独立新表）

```kotlin
val MIGRATION_8_9 = object : Migration(8, 9) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("""
            CREATE TABLE IF NOT EXISTS `screen_evidence` (
                `startMs` INTEGER NOT NULL,
                `endMs` INTEGER NOT NULL,
                `kind` TEXT NOT NULL,
                `quality` TEXT NOT NULL,
                `sourceDeviceId` TEXT NOT NULL DEFAULT '__local__',
                PRIMARY KEY(`startMs`, `kind`, `quality`, `sourceDeviceId`)
            )
            """.trimIndent()
        )
        db.execSQL("CREATE INDEX IF NOT EXISTS `index_screen_evidence_endMs` ON `screen_evidence` (`endMs`)");
        db.execSQL("CREATE INDEX IF NOT EXISTS `index_screen_evidence_sourceDeviceId` ON `screen_evidence` (`sourceDeviceId`)");
    }
}
```

**注意主键**：`screen_session` 的主键是 `(startMs, kind, sourceDeviceId)`；新表加了 `quality`——这是**必要的**，因为同一段区间可以同时存在「精确观测」与「上界推断」两种证据。

### 6.3 迁移的通用纪律

| 纪律 | 说明 |
|---|---|
| **绝不使用 `fallbackToDestructiveMigration`** | 它会**清库**重建，直接违反 RL-7。本项目当前也未启用它，**不得引入**。 |
| **只增不改** | 既有列不改名、不改类型、不改语义（CR-01 红线）。 |
| **不追溯回填** | 新列对旧行留空 / `UNKNOWN`，**不得**用「看起来更整齐」的理由回填成 `EXACT`（RL-7）。 |
| **schema JSON 必须入库** | `app/schemas/<version>.json` 必须随迁移一起提交，供 `room-testing` 的 `MigrationTestHelper` 校验。 |
| **索引声明逐字一致** | `Entities.kt` 的 `indices = [Index(...)]` 必须与 migration 建的索引名逐字一致（**CR-28 真机踩过**：迁移建了索引、实体没声明 → Room schema 校验炸、App 起不来）。 |
| **迁移必须有测试** | `MigrationTestHelper` 跑 `8 → 9`，断言列存在、旧行可读、旧行语义未被改写。 |
| **迁移不重算历史** | 迁移**只改结构**。历史数据的重算 / 重建是独立动作，须走 §9 的原则并单独审批（RL-7「未经批准重算」）。 |

## 7. 备份兼容

### 7.1 现状

- 备份 `schemaVersion = 6`（`BackupCodec.SCHEMA_VERSION`，`BackupModels.kt:172`）；
- `BackupFile` 顶层六表 = **备份导出设备**自己的分量，`sources[]` = 其他来源分量（含 `'__legacy__'`）；
- 所有列表都给默认空值（`= emptyList()`），旧备份缺键 → 视为「该备份不含此表」→ `BackupSummary.missingTables` 逐条提示；
- 兼容检查在 `BackupModels.kt:223-226`：`schemaVersion < 2 / 3 / 4 / 5` 逐条给出「该备份不含哪些内容」提示；
- 旧读取器 `ignoreUnknownKeys` → **能解析、能展示（只见顶层）、不能正常导入**（三层兼容）。

### 7.2 兼容设计要点

| 变更 | 备份处理 |
|---|---|
| `day_summary` 加质量列 | **DTO 加可空字段 + 默认值**（`screenQuality: String? = null`）。旧备份缺该键 → `null` → 沿用旧语义。**不 bump 版本**也可（可空 + 默认值向后兼容），但**建议 bump 到 7** 以便在 UI 上提示「该备份含质量标记」。 |
| `app_usage` 加估算标记 | 同上：`minutesEstimated: Boolean = false`。 |
| `hour_usage` 加质量列 | 同上。 |
| 新增 `usage_window` / `screen_evidence` 表 | 备份里加**可选列表**（`= emptyList()`）。旧备份缺 → 空 → 恢复后这些证据为空，**不报错**。备份 schemaVersion bump 到 7。 |
| **`screen_session` 加列（选项 2）** | `ScreenSessionDto` 加 `evidence: String? = null`。**风险**：旧读取器 `ignoreUnknownKeys` 会**静默丢掉** `evidence` → 备份往返后估算区间变成精确区间 → **假精确**。这是选项 2 的额外风险，**又一条不推荐选项 2 的理由**。 |

### 7.3 备份的三条硬约束

1. **备份里出现估算值时，必须同时出现标记**。绝不允许「备份里有 1440 分钟但没有说明它是估算的」这种状态；
2. **恢复时不得把估算值转成精确值**：`overwrite` 与 `merge` 两条恢复路径都要保留质量标记；
3. **legacy 分量的估算标记必须原样保留**：CR-28 规定 legacy 只读，恢复时 legacy 行不得被改写，也不得被强分配身份。

### 7.4 与 CR-28 备份结构的交互

- CR-28 的备份结构是「顶层 = 导出设备分量，`sources[]` = 其他来源分量」。**新增列 / 表必须同时落到顶层与 `sources[]`**（`BackupSource` 有自己的六表列表）；
- `BackupSource` **不含** `pull_log` / `app_limit` / `settings`——新增的「质量标记」属于数据表，**要加进 `BackupSource`**；
- 若采用方案甲（窗口级记录），`usage_window` 必须**按来源分量**导出，否则跨设备合并时会把 A 设备的窗口记到 B 设备名下。

### 7.5 CSV 导出与 HTML 报告

`BackupRepository.exportCsv` 是七张表各一个 CSV 文件（§5.10）。若新增列：

- CSV **必须加列**并写清「估算」含义（表头注释或独立列）；
- `AppViewModel.buildHtmlReport` 生成的 HTML 报告里若出现估算数字，**必须带标记**（§7-16 要求「卡片数字与详情同源」，同样适用于「估算标记的同源」）。

## 8. CR-28 兼容分析

### 8.1 CR-28 已冻结的口径（本设计不得改动）

| 编号 | 冻结口径 |
|---|---|
| F1 | 六表 + 事件表带 `sourceDeviceId` 来源维度；**跨来源数据不合并**，展示层按来源 SUM |
| F2 | legacy（`__legacy__`）**只读**：普通拉取 / 合并 / 重算不得改写，**不得强分配身份** |
| F3 | 跨来源 **SUM** 的是「同一天同一应用的使用时长」，不是会话 |
| F4 | 会话 **UNION 不相加**：同一时刻不同来源的会话各占一行、永不合并（合并会破坏「占用时钟时长」的同时性信息）；日聚合用并集而非求和 |
| F5 | `screen_session` 是**日聚合的唯一重算输入** |
| F6 | 备份三层兼容：顶层 = 导出设备分量，`sources[]` = 其他来源分量（含 legacy） |
| F7 | 重建工具按来源独立重算，流水记 `rebuild_log` |

### 8.2 逐项变更对 CR-28 的影响

| 本设计的变更 | 是否触及 CR-28 | 说明 |
|---|---|---|
| `day_summary` / `hour_usage` / `app_usage` 加可空元数据列 | **不触及**（F1–F7 均不变） | 新列是**元数据**，不是数值；来源维度、合并语义、UNION 语义都不变 |
| `MergePolicy` 取大时同时携带元数据 | **需同步实现**（不改语义） | 见 §8.3 |
| **选项 2**：`screen_session` 加列 | **直接触及 F4 / F5** | 并集合并语义要扩展；`screen_session` 不再是纯精确输入 |
| **选项 3**：独立新表 | **不触及**（新表自带 `sourceDeviceId`，跨来源同样不合并） | 推荐路线 |
| 方案甲的 `usage_window` 表 | **需同步实现** | 必须按来源分量存与导出 |
| `SourceRebuild` 重建工具 | **必须同步支持** | 否则重建会丢质量标记 → 重建出来的行会被误认为精确 |
| 备份 DTO 加列 / 加表 | **需同步实现** | 顶层与 `sources[]` 都要加 |

### 8.3 元数据与「取大」的交互（一个必须单独裁决的细节）

CR-28 的合并规则是「同 (date, pkg) 取较大值」。引入质量标记后有两种做法：

| 做法 | 说明 | 评价 |
|---|---|---|
| **元数据取弱** | 数值取大，但标记独立取弱（`UNKNOWN` 恒压 `EXACT`） | **不好**：会出现「数值来自新行（EXACT）、标记来自旧行（UNKNOWN）」的错配，UI 会把一个精确值标成未知 |
| **元数据随行绑定** | 数值与标记**同行取**，取大时两者一起取 | **更好**：标记与它描述的数值始终同源；保守性由「取大」本身提供 |

**本文档倾向「元数据随行绑定」**，但需 GPT 确认——这属于 CR-28 合并规则的**扩展**，虽然不改数值语义，仍应在实施前明确记录。

### 8.4 legacy 行的处理

- legacy 行（`__legacy__`）的默认质量标记必须是 `UNKNOWN`，**不得**追溯成 `EXACT`；
- legacy 行的数值**一律保留原值**，不得因为「现在有更好的算法」而就地改写（那属于重建，须走 §9 的审批流程）；
- **不得**给 legacy 行分配来源身份（RL-7）；
- 备份里 legacy 分量的质量标记必须往返保真，不得在导入时被「补齐」成 `EXACT`。

### 8.5 结论

**CR-28 的数据口径不需要修改。** 需要改的是「CR-28 的实现要同步支持新增的元数据」：

1. `MergePolicy` 的元数据绑定规则（§8.3）；
2. `SourceRebuild` 必须能重建出带标记的行；
3. 备份的顶层与 `sources[]` 必须同时携带新元数据；
4. legacy 行的默认态是 `UNKNOWN`。

**唯一的例外**：若裁决采用**选项 2**（`screen_session` 加列），则 CR-28 的 F4 / F5 需要**显式修订**并写进需求文档——这属于口径变更，必须由 GPT / 负责人拍板，本设计**不代为决定**。

## 9. 历史数据处理原则

### 9.1 四条原则

1. **可从原始证据重建的才重建**；只能保留原值的保留并标记可信度；来源或日归属不可确认的一律**保留原记录 + 标记**，**不得为界面整齐伪造精确值**；
2. **不追溯改写**：Room 迁移只改结构，不改数值；质量标记列对旧行留空 / `UNKNOWN`；
3. **不清库、不删备份**（RL-7）：不得用「迁移时清空重建」当修复手段（历史上 `MIGRATION_2_3` / `MIGRATION_3_4` 清过 `app_usage` / `hour_usage`，那是当时有充分理由的特定事故修复，**不能当成常规手段**）；
4. **重算必须经批准**：历史重建是独立动作，走 `rebuild_log`（CR-28 批次 D）留痕，可回滚。

### 9.2 本例数据的逐项处置

| 数据 | 现状 | 能否从原始证据重建 | 处置 |
|---|---|---|---|

### 9.3 一条必须写进实施说明的反面禁令

> ❌ **不得**用「应用在前台 ⇒ 屏幕亮着」把 11-23 的 1440 分钟**反推成亮屏时长**。
>
> 那是把线 2 的错误（时长记错日）直接转嫁成线 1 的错误（亮屏时长凭空出现），两个缺陷叠加后用户看到的是「亮屏 24 小时」——比现在的「亮屏 0 分钟 / 应用 24 小时」更难解释，而且**两个数都没有证据支撑**。

## 10. UI 展示口径

### 10.1 覆盖范围

必须逐页核对，不能只改今日页：

| **统计页** | `ui/` 统计屏 + `AppViewModel.loadAll` 的 `StatsData` | 时段分布、日均（§5.7 第 7 条）、趋势 |
| **日历页** | `ui/CalendarScreen.kt` | 月视图色阶、无数据格子的着色 |
| **周期总结页** | `AppViewModel.openPeriod` / `periods` / `extremes` / `topAppsPerDay` | 极值、最长连续、日均的分母口径 |
| **排行弹层** | CR-18 已定「只给单日、详情跟随归属」 | 若该日含估算 / 跨日窗口，弹层必须带标记 |
| **详情页** | `repository.metricDetail` | §7-16「卡片数字与详情同源」→ **标记也必须同源** |

### 10.2 状态 → 文案对照表（核心交付物）

| 数据状态 | 亮屏时长 | 应用构成 | 日 / 夜条 | 排行 |
|---|---|---|---|---|
| 有精确数据 | 正常显示 | 正常显示 | 正常显示 | 正常 |
| **部分缺失**（有数据但不完整） | 显示数值 + 「不完整」角标 | 同左 | 同左 + 角标 | 带角标 |
| **缺分母**（`hour_usage` 全 0 且非真实为零） | 显示「—」+「数据不完整」 | 正常显示（若应用数据本身有证据） | **不显示百分比**，整块显示「无数据」 | 正常 |
| **含估算** | 「约 X」+ 估算说明 | 「约 X」+ 说明 | 正常但带标记 | 带标记 |
| **采集失败** | 「—」+ 失败说明 | 「—」 | 「无数据」 | 空态 |
| **真实为零** | 「0 分钟」 | 「0 分钟」 | **不显示百分比**（无分母） | 空态 |

### 10.3 三条硬性要求

1. **缺分母时，日 / 夜条不得渲染成两个百分比。** 无论 `dayPercent` 是「真实 0%」还是「无数据」，只要 `total == 0`，就**不显示百分比数字**——改为显示「无数据」或整块隐藏。当前实现 `right = 100 - left` 在 `left = 0` 时必然产出「夜间 100%」，这是**结构性错误**，必须改。
2. **「0 分钟」与「无数据」必须能区分。** 现在两者都显示 0。需要一个来自数据层的质量标记来区分，而不是靠 UI 猜。
3. **估算 / 上界的表述必须出现在数字旁边，而不是藏在说明文字里。** 建议：精确值用常规样式；估算值加「约」前缀 + 弱化色；上界用「≥ N 分钟」。

### 10.4 实现要点

- `TodayData.dayPercent: Int` → `Int?`（§5.4），`null` 表示无分母；
- `DayNightBar` 的入参从 `Int` 改为 `Int?`：`null` 时不渲染两个百分比，只渲染「无数据」文案（或整块不渲染）；
- **不要**用「夜间补 100%」或任何形式的补集计算来「凑出」两个数——补集的前提是分母存在且已知；
- 亮屏时长为 0 时，UI 需要能区分「真实 0」与「缺证据」→ 依赖 §5.3 的质量标记列；
- 日历页月视图：`UsageCalculator.monthLevel` 现有口径是 `!recorded || minutes <= 0 -> 0`（不着色）。含估算的格子建议**不着色**或用单独一档并在图例说明；
- 周期总结页的「最长连续」「日均」「极值」若含估算，卡片上必须带标记，且**分母口径要写明**是否含估算。

### 10.5 与既有 UI 红线的关系

- §7-16「卡片数字必须与详情同源」→ **标记也必须同源**；
- CR-15 A1 的「真日均」口径 → 若分母含估算，必须在卡片上说明；
- CR-18 的排行弹层「只给单日、详情跟随归属」→ 若该日只有窗口级记录（方案甲），弹层应显示「该日无单日归属数据」而不是 0。

## 12. 回滚方案

### 12.1 分级回滚

| 级别 | 对象 | 回滚方式 | 注意 |
|---|---|---|
| L1 | 单个提交 | `git revert <sha>`（**不要**用 `git checkout --`，项目纪律明令禁止用 `git checkout --` 撤销未提交改动） | 文档提交与实现提交分开 revert |
| L2 | 一批实现（文档 / 实现 / 真机收口三笔） | revert 实现笔，保留文档笔 | 文档保留「已回滚」的记录，不删 |
| L3 | Room schema 变更 | **Room 不支持降级迁移** → 旧 APK 装在新 schema 上会 schema hash 校验失败 | 见 §12.2 |
| L4 | 备份格式变更（v6 → v7） | 旧版 App **无法读取 v7 备份**（`schemaVersion` 过高会被判 Invalid） | 见 §12.3 |
| L5 | 历史重建 | `rebuild_log` 里有快照 → 可回滚到重建前 | 重建前必须已快照 |
| L6 | 真机 | 重装上一个 debug APK：`adb -s GAQOHMNFQWFUPBQO install -r app/build/outputs/apk/debug/app-debug.apk` | 卸载会丢数据，**优先 `-r` 覆盖安装** |

### 12.2 Room schema 的回滚策略

**这是本设计里最需要小心的一处**：

- Room 的 schema hash 校验意味着**一旦发布带迁移的版本，旧 APK 在新库上会启动失败**；
- 因此**schema 变更应当放在整批的最后一步**，或者干脆**不引入 schema 变更**（选项 1 / 选项 4 天然满足）；
- 如果必须做 schema 变更，回滚路径只有两条：
  1. **向前修复**：发布一个包含 `MIGRATION_9_8` 的过渡版本（Room 允许在同版本号内提供降级路径，但需手工管理），或
  2. **数据回滚**：清库重装（**最后手段**，需用户明确同意，因为会丢本地数据，且违反 RL-7 的「不清库」精神）。
- **本设计的建议**：把「只加可空元数据列」与「改表结构 / 加表」分开两步；前者风险最低（列可空，旧 APK 读新库仍会因 hash 不匹配失败——**注意 Room 的 hash 校验与列无关**，只要 schema 变了就会失配）。

> **诚实提示**：**只要 Room schema 版本号变了，旧 APK 就无法在新库上启动**，与是否只是加列无关。因此 schema 变更的发布策略必须与版本发布策略一起裁决（例如「只随首个正式版发布，不再提供 debug 覆盖路径」）。

### 12.3 备份格式的回滚策略

- v7 备份旧版 App 读不了（`schemaVersion` 过高 → `DecodeResult.Invalid`）；
- 因此**备份格式变更必须最后做**，且发布前必须确认「不再回退到旧版 App」；
- 若必须提前发布，则采用**双写**策略：v7 备份里同时保留 v6 可读的信息（新字段可空、旧字段照旧），并确保 v6 读取器能降级解读；
- **任何情况下都不得**通过「删掉 v6 兼容分支」来「简化」实现。

### 12.4 回滚演练清单

1. 合并前先 `git tag` 标出当前可用点；
2. 每个实现提交都能单独 revert 后重新跑全量单测（必须仍全绿）；
3. 真机回滚演练：装新 APK → 造数据 → revert → 装旧 APK → 验证能读（**注意 schema 变更的限制，见 §12.2**）；
4. 备份回滚演练：v7 备份 → 旧版 App 导入 → 验证「明确报错」而不是「静默导入错误数据」。
