## 0. 背景、范围与硬红线

### 0.1 现象

真机（Redmi 2407FRK8EC / Android 16 / HyperOS 3）自 2026-11-21 周六下午起，因插着 USB 且开启开发者模式「插着数据线不休眠」，**持续约 42 小时未息屏**。期间 App 读到的是：

- 今日页「亮屏 0 分钟」（**归档 UI XML 实为「亮屏 10 分钟 / 最长连续 9 分钟」——两者不是同一采样点，见 §3.5**）；
- 「应用构成 共 24 小时（屏迹 100%）」；
- 「日间 0% / 夜间 100%」。

### 0.2 三条独立故障线

| 线 | 症状 | 性质 | 本轮可修？ |
|---|---|---|---|
| **线 1** | 长亮屏期间该日亮屏记 0，应用前台区间同断 | **证据缺失**（源端数据已被丢弃） | 需先有能证明**连续亮屏区间**的独立证据（E2 范畴，§4.2.4），或接入**窗口级 W1**（§4.1.3，仅补充窗口总量）；**当前不可修** |
| **线 2** | 约 24h 滚动窗口被整段记到结束日，单日 1440 分钟 | **归属错误**（值是真的，日错了） | **可修**（D5 已获方向性同意） |
| **线 3** | 缺分母被渲染成「日间 0% / 夜间 100%」 | **渲染错误**（UI 诚实性） | **可修**（不依赖任何裁决） |

线 3 与线 1 / 线 2 无因果依赖，是**独立缺陷**。

### 0.3 硬红线（v2，含 GPT 本轮新增项）

| 编号 | 红线 |
|---|---|
| RL-1 | **不得**把「上次没看到息屏事件就把会话延长到现在」当作方案。任何时长都必须能指认其证据类型。 |
| RL-2 | 证据必须分四类并逐项声明边界：**E1 精确事件对 / E2 独立可证状态区间 / E3 仅锚点 / W1 窗口级累计增量**。E3 **不得生成任何时长**（既不得给上界，也不得给下界）。**W1 不是区间证据**：不得生成 `screen_session` 精确会话区间、不得参与精确会话 UNION（v2.1 新增，§4.1.3）。 |
| RL-3 | **不得**把区间按自然日重叠比例分摊后**冒充**精确日数据。 |
| RL-4 | `screen_session` **是否改表结构必须由 GPT/负责人裁决**。本设计按 D2 方向（独立证据表）推进，但**表的最终形态仍待确认**。 |
| RL-5 | **不得**把 `IngestSanity` 的 `> 1440` 简单改成 `>= 1440`。 |
| RL-6 | **不得**动 CR-28 已冻结的数据口径（见 §8）。 |
| RL-7 | **不得**清库、删备份、给 legacy 强分配身份、改 SUM 语义、混淆 UNION 与 SUM、无依据缩小总量、未经批准重算。 |
| RL-8 | **不得**把 ADB 合成手势冒充真实手指；**不得**把施工方报告冒充 GPT 独立验证。 |
| RL-9 | UI **不得**把缺分母渲染成「日间 0% / 夜间 100%」。 |
| **RL-10** | **「≥ N 分钟」是下界表述，不是上界表述。** 不得把 `UPPER_BOUND` 之类上界命名与「≥ N」混用。**本设计不产出任何区间不等式表述**（D3：暂不允许显示「≥ N 分钟」）。 |
| **RL-11** | **Activity 前台区间不得直接等价于亮屏时间。** N4（MIUI 息屏而 Activity 仍可见的发生率）未验证前，Activity 只能作为**辅助证据**，不得生成精确亮屏区间。 |
| **RL-12** | **采集状态与数据质量是两个独立维度**，不得合并成一个枚举。采集成功不代表数据完整；数据不完整不等于采集失败。 |
| **RL-13** | **不得自行补造时间**。原始材料无法证明的采样时刻，标注「无法关联」，不猜、不补。 |
| **RL-14** | **不得把证据缺失伪装成真实零值。**「没有采集到事件」**不等于**「该时段没有使用」。事件缺失、缓冲区滚动、解析失败、证据不足，一律**不得**记为 0；`EMPTY` 只能表达「本次采集没有拿到记录」（v2.1 新增，§5.2.1）。 |

### 1.2 线 1 · 亮屏会话漏算

```kotlin
// UsageDumpParser.kt:303-312
val screens = mutableListOf<Pair<Long, Long>>()
var on: Long? = null
for (e in intervalEvents) {
    when {
        e.type == "SCREEN_INTERACTIVE" && on == null -> on = e.ms
        e.type == "SCREEN_NON_INTERACTIVE" && on != null -> { screens.add(on!! to e.ms); on = null }
    }
}
on?.let { screens.add(it to intervalEvents.last().ms) }   // ← 依赖缓冲里还留着开屏事件
```

MIUI 的 usagestats 事件缓冲是**滚动窗口**。开机事件滚出缓冲后：`on` 永远是 `null` → `screens` 为空；`foreground.spans` 同样配不出来 → `normalizedScreens` 为空 → `screenDay` / `hourMatrix` / `longestDay` 全空。

入库侧也不兜底：`IngestPipeline` 只在 `incomingSessions.isNotEmpty()` 时才重算该日 → 该日 `day_summary` 保持旧值。

**关键定性（v2 明确）**：这是**证据缺失**，不是解析缺陷。证据在**源端**已被丢弃，App 侧任何算法都无法凭空还原。**唯一诚实的出路是找到另一条独立证据源**（E2 范畴：能证明连续亮屏区间的独立证据，见 §4.2.4）或**明确承认该日状态未知**。

### 1.3 线 2 · 跨日区间错日归属

MIUI 的 checkin 里 `beginTime=… endTime=…` 描述的是**一个约 24 小时、以 ~09:2x 为锚的统计窗口**，不是自然日。

```kotlin
// UsageDumpParser.kt:385
val date = Instant.ofEpochMilli(iv.endMs - 60_000).atZone(zone).toLocalDate();
// → 整段按「区间结束时刻所在自然日」归属
```

于是约 24h 的窗口**整段落进结束日**。合成复现里 `totalTimeUsed=86400000` 毫秒 = 1440 分钟，输出与真机库内分毫不差。

**为什么小时矩阵全 0**：区间路径（`perUserInterval`）**只写 `app_usage`，不写 `hour_usage`**；`hour_usage` 来自 `hourMatrix`，而 `hourMatrix` 来自 `normalizedScreens`（线 1 已断）。

### 1.4 线 3 · 缺分母被渲染成精确百分比

```kotlin
// AppViewModel.kt:1375
val dayPercent = if (todayTotalMinutes <= 0) 0 else ((todayTotalMinutes - todayNight) * 100 / todayTotalMinutes)

// uikit/AppBreakdown.kt:125-130
private fun DayNightBar(dayPercent: Int) {
    val left = dayPercent.coerceIn(0, 100)
    val right = 100 - left;      // ← left=0 时必然产出「夜间 100%」
}
```

**缺陷本质**：`Int` 表达不了「**分母不存在**」与「**日间占比真的是 0%**」两种状态；`right = 100 - left` 把两者压成同一个 0。

### 1.5 门禁为何未拦（且本例**不该**拦）

| 门禁位置 | 判据 | 本例是否成立 | 结论 |
|---|---|---|---|
| `IngestSanity.kt:81` | `totalMs > 24h`（严格大于） | 本例正好 **= 24h** → 不成立 | **放行是对的** |
| `IngestSanity.kt:117` | 参照物 `< 60` 分钟时退回 1440 上限 | 成立 | 上限 1440，合计 1440 → 不丢 |
| `UsageDumpParser.kt:468` | `screenMs > 0 && total > screenMs * 1.15` | 前置 `screenMs > 0` **不成立** | 相对判据无从生效 |
| `SourceRebuild.kt` | `MAX_DAY_MIN = 1440` | 恰好 1440 | 不清洗 |

**结论**：1440 分钟**不是脏数据**，是**归属错误**。任何「把 1440 判成假值并丢弃」的改法都会**丢掉真实数据**，违反 RL-5 与 RL-7。

## 2. 复现条件

### 2.1 线 1 的复现条件（亮屏漏算）

必要条件（同时满足）：

1. 设备持续亮屏 ≥ 缓冲区窗口长度；
2. 该窗口内**没有**产生新的 `SCREEN_NON_INTERACTIVE`（长亮屏即如此）；
3. 该窗口内的 `ACTIVITY_RESUMED/PAUSED` 事件也已滚出缓冲；
4. 拉取发生在上述事件滚出之后。

**已验证**：用真机**当前** dump（checkin 已空、明文只剩最近几分钟）喂进解析器 → 输出「亮屏 1 分钟、屏迹 1.15 / 75.32 分钟」，**完全正常**。

→ 证明：线 1 的缺失**不是解析器永久性缺陷**，而是**数据在源端已经不存在**。

### 2.2 线 2 的复现条件（错日归属）

1. checkin 输出中存在 `beginTime=… endTime=…` 形态的区间；
2. 该区间的 `endTime` 与 `beginTime` 落在**不同的自然日**（约 24h 窗口几乎必然跨日）；
3. 区间内的包在该日的 `totalTimeUsed` 较大（否则误差不显著）。

**已验证的最小复现**（App 自己的解析器）：

```text
输入：合成 24h checkin 区间 + package=com.screentrace.app totalTimeUsed=86400000
输出：PROBE2 appUsage 2026-11-23 com.screentrace.app totalMs=86400000 min=1440.0
      PROBE2 days=[]            ← 该日没有任何屏幕指标
      PROBE2 sanity dropped=[]  ← 门禁未拦
```

### 2.3 两个问题的独立性

| | 触发源 | 写入的表 | 门禁 | 关系 |
|---|---|---|---|---|
| 线 1 | 源端事件滚出滚动缓冲 | `day_summary.screenMin`、`hour_usage`、`screen_session` | `IngestPipeline` 的 `incomingSessions.isNotEmpty()` 空转 | **独立** |
| 线 2 | checkin 窗口跨自然日 | `app_usage` | `IngestSanity` 按「> 24h」判 | **独立** |

#### 3.5.3 三处「无法关联」——必须如实标注

**① 报告结论「今日亮屏 0 分钟」对应哪个采样点？**

→ 对应 **DB 副本（10:40:44 快照，其内容对应 pull_log 171 @ 10:38:49）**。**不对应 UI XML。**

**② UI XML 显示「亮屏 10 分钟 / 最长连续 9 分钟」，与 DB 切片的 `screenMin=0 / longestSessionMin=0` 矛盾吗？**

→ **不矛盾，但两者不是同一采样点**：

- DB 副本里 2026-11-23 **只有一个来源** `02ebd900-…`，`screenMin=0`、`longestSessionMin=0`，`SUM(screenMin)=0`（跨来源 SUM 也为 0，因为只有一个来源）；
- 库内今日 `screen_session` 只有一条 **3 秒**会话（10:38:44→10:38:47）→ 切片后 `screenMin = round(3/60) = 0`，**与库内数值自洽**；
- UI XML 是 **10:54:21 的实时抓取**，比 DB 副本晚 **13 分 37 秒**；这 13 分钟里设备上是否又发生了拉取、亮屏是否累积到 10 分钟，**归档材料无法证明**（设备 DB 的后续状态没有进副本）。

→ **因此：UI XML 与 DB 切片无法证明同刻；两者之间的状态变化没有留痕。** 这一条在 v1 里被当成「同一份数据自相矛盾」处理，是**误读**。

**③ 产生 1440 分钟的那份 dump 还在吗？**

→ **不在归档里。** 归档的 checkin dump 是 10:4x 的 **plain-nodata** 形态（无 `beginTime/endTime`、无 `timeRange`、无 `time="…"` 事件行），对应 pull_log 170 / 171 的「checkin 无数据」。

→ pull_log 169（10:31:38）是**唯一**一条 `checkin 0.3MB/checkin+data` 的记录，也就是 1440 分钟的来源；但**那份 dump 未被保存**。

→ 因此「1440 来自 10:31 那次 checkin+data 拉取」这一结论目前**只由 pull_log 笔记 + 探针推断支撑，没有原始 dump 可复核**。这是当前证据链的**最大缺口**，必须在下一轮补齐（见 §13 的 N7）。

#### 3.5.4 方法学声明

1. **探针是 JVM 侧重跑**，不是设备上的入库过程；它的输出不能用来推断「设备当时库里是什么」；
2. **探针自述时间只到十分钟位**，**不足以**与 dump 采集时刻排序，任何「探针先于/后于采集」的断言都不做；
3. **不补造时间**：以上每一行的时间要么有明确锚点，要么已标注为「无法自证」；
4. 本节的结论只用于**界定证据强度**，不用于反推任何具体时长。

| 维度 | **E1 精确事件对** | **E2 独立可证状态区间** | **E3 仅锚点** | **W1 窗口级累计增量**（计数器差值） |
|---|---|---|---|---|
| **定义** | `SCREEN_INTERACTIVE` 与 `SCREEN_NON_INTERACTIVE` **成对出现**，区间 [t1,t2] | 由**两个以上互相独立的证据源**共同证明「[t1,t2] 期间屏幕**持续**亮」 | 只有「某时刻 t 屏幕是亮的」这一**点观测** | 两次采样之间累计器读数的**差值 Δ**，是一个**窗口级总量**，**不含任何时间点信息** |
| **能证明什么** | 该区间内屏幕持续亮 | 该区间内屏幕**连续**亮 | 仅 t 时刻亮 | 仅「[t0,t1] 窗口内累计亮屏总时长 = Δ」——**是总量，不是区间** |
| **不能证明什么** | 区间之外是否亮；区间内是否被系统判定为「非交互」（锁屏但 Activity 可见的情形另算） | 依赖具体证据源的适用边界（见 §4.2 / §4.2.4） | **不能证明 t 之后到下次观测之间一直亮**；不能证明任何区间 | **不能证明窗口内何时亮、亮了几段**；不能证明连续；不能证明与相邻窗口的连续性；**不能当单日精确亮屏时长** |
| **是否允许生成时长** | **允许**，且为精确值 | **允许**，为精确值（前提是证据链完整且适用边界成立） | **不允许**（连下界都不允许，见下） | **允许，但仅作为窗口级总量**（不归属任何自然日） |
| **是否允许进入精确统计** | 允许 → `screen_session` → 日聚合 | 允许 → `screen_session` → 日聚合 | **不允许**（不写 `screen_session`，不参与 `SessionUnion.union`） | **不允许**（**不写 `screen_session`**、**不参与 `SessionUnion.union`**、**不参与 `day_summary.screenMin` 重算**） |
| **是否允许展示上下界** | 直接展示精确值 | 直接展示精确值 | **不允许**。本设计**不产出任何区间不等式表述**（RL-10 / D3） | **不适用**（Δ 是精确的窗口总量，不是区间不等式） |
| **是否允许参与日聚合** | 允许 | 允许 | **不允许** | **不允许** |
| **是否允许进入备份和恢复** | 允许 | 允许 | **仅可作为「状态锚点」元信息**随行携带；**不得**被恢复成时长 | **允许**（作为窗口级记录随备份往返，性质不变；**不得**被恢复成单日时长） |

#### 4.1.1 关于 E3 不能给下界 —— 严格论证

```text
  已知：t1 = 10:00 观察到 SCREEN_INTERACTIVE（屏幕亮）
        t2 = 11:00 再次拉取，没有观察到 SCREEN_NON_INTERACTIVE

  能推出的唯一事实：「t1 时刻屏幕是亮的」

  不能推出的：「t1 到 t2 之间屏幕一直亮」
    —— 中间可能发生：息屏 → 重新亮屏 → 再息屏；息屏 → 重启；息屏 → 关机；
       甚至 SCREEN_NON_INTERACTIVE 事件本身被缓冲丢弃（线 1 的同一机制）。

  ⇒ 若要说「至少亮了 X 分钟」，需要**独立于屏幕事件**的证据，
     例如系统屏幕状态在 t2 仍为 on（这属于 E2，不是 E3）。

  ⇒ 在只有 E3 的情况下：可写入「t1 时刻亮屏」这一锚点，
     **不得**写入任何时长，**不得**写「≥ N」，**不得**写「≤ N」。
```

#### 4.1.2 v1 的错误（已修正）

| v1 写法 | 问题 | v2 修正 |
|---|---|---|
| `DataQuality.UPPER_BOUND`（上界）配「≥ N 分钟」（**下界**） | **自相矛盾**；把「区间不等式」当成了证据类型 | **删除**上界/下界这类表述；E3 改为 `ANCHOR_ONLY`（仅锚点） |
| 「E3 可产出 `≥ N 分钟`」 | 从点观测推不出区间下界 | E3 **不产出任何时长** |
| 「未闭合开屏会话收在 `intervalEvents.last().ms`」 | 把「没看到息屏」当成了「一直亮」 | 该收尾**只能产生 E3 锚点**，不得写进 `screen_session`（RL-1 / RL-2） |

#### 4.1.3 累计计数器的证据等级与九类异常降级（GPT R11-1 · v2.1 新增；**v2.2 重写降级表**）

**核心判定**：

> **`screen-interactive` 累计计数器属于「窗口级累计增量」证据（W1），不属于 E1 / E2 / E3 中的任何一类。**
> **E2 保留给真正能证明「某连续区间内屏幕持续亮」的独立证据**（例如 §4.2.4 中两个采样点的系统屏幕状态均为 ON，且区间内没有任何息屏证据）。
> **累计计数器无论 A/B/C 实验结果如何，都不进入 E2** —— 因为它**没有时间分布信息**，只给总量。

**七条硬性规定**：

| 编号 | 规定 | 依据 |
|---|---|---|
| **W-1** | 计数器**只能证明两个采样时刻之间的累计亮屏时长变化**（Δ = C(t1) − C(t0)），其语义终点就是「窗口总量」 | 计数器是一个标量累计量，采样点是它的唯一定位信息 |
| **W-2** | **两次采样之间的累计增量不能证明具体亮屏时间段** —— 无法知道 Δ 分布在窗口的哪一段、亮了几段、每段多长 | 标量不含分布信息；「分布未知」不可由总量倒推 |
| **W-3** | **累计计数器不得直接转换成 `screen_session` 精确会话区间** | 写入 `screen_session` 会让「窗口总量」冒充「精确区间」，进而被 `SessionUnion.union` 当成连续区间切日 → **直接违反 RL-1 / RL-10** |
| **W-4** | **累计计数器不得参与精确会话 UNION** | UNION 的输入必须是**已证明的连续区间**（E1 / E2）；总量参与 UNION 会产生虚假的「连续亮屏」跨日区间 |
| **W-5** | 若验证成功，**应归入独立的窗口级聚合证据**（W1），与 D2 的独立证据表同层存放，**不进入 `day_summary` / `hour_usage` / `app_usage` 的单日口径** | 方案甲（§4.4）的粒度就是窗口级 |
| **W-6** | **计数器重置、回绕、设备重启、采样缺失或来源不可靠时，必须降级**，且降级方向**一律是「不产出数值」** | 见下方降级表；「宁可少报，不给可疑值」与 §4.1.2 同源 |
| **W-7** | **不得将计数器差值直接当成单日精确亮屏时长**，**尤其当采样窗口跨日时** —— 跨日窗口的 Δ 既不能拆到日，也不能归属任一天 | 跨日采样窗口是本 bug 的核心场景（W-7 与 §4.4 方案甲同源） |

**降级策略表（GPT R11-1 第 6 点；v2.2 按 GPT v2.2 R11-02 重写为**九类异常 X-1~X-9** + 两类前置条件 X-10 / X-11**）**：

| # | 异常类别 | 判定依据 | 降级动作 | 是否产生 C 层 | 绝不允许的做法 |
|---|---|---|---|---|---|
| **X-1** | **Δ 与 E1 证据矛盾** | 同窗口 E1 区间合计 > Δ，或 E1 与 Δ 明显冲突 | **保留 A 层 + B 层**（原始差值与冲突标记留作取证）；Δ 判为不可用 | **否**（V-5 不通过） | 仅打 UNKNOWN 标签就让数值继续流入统计；静默改写 Δ 或删除 E1 证据 |
| **X-2** | **计数器重置 / 归零** | C(t1) < C(t0)，或 C(t1) = 0 | **丢弃该样本**；不产出 Δ | **否** | 取绝对值、取模、强行置 0 后当作「真实 0」 |
| **X-3** | **计数器回绕** | 读数骤降但非归零（到达上限后回绕） | **丢弃该样本**；不产出 Δ | **否** | 按回绕模运算「还原」出 Δ；把回绕前后读数相减 |
| **X-4** | **设备重启** | 无法与正常累计区分 | **一律按重置处理并丢弃**（保守方向） | **否** | 猜测「重启前的累计」并补算 |
| **X-5** | **采样间隔过长** | Δt 超过阈值（阈值取值属 D2 落地细节，本轮只定规则） | **保留 A 层原始读数**（诊断用）；**不产出 Δ** | **否** | 把长间隔的 Δ 当作某一天的精确亮屏时长 |
| **X-6** | **采样缺失** | 中间某次拉取没拿到计数，采集序列不连续 | 该窗口**不成立**；不产生记录 | **否** | 用更早的读数拉长窗口充数 |
| **X-7** | **设备身份变化** | `sourceDeviceId` 与上一次不同 | 该窗口**不成立**；**不得跨设备相减** | **否** | 把两台设备的读数相减 |
| **X-8** | **采集失败 / 通道中断** | 两次采样之间有拉取失败或通道中断 | 该窗口**不成立**；不产生记录 | **否** | 用失败前后的读数相减 |
| **X-9** | **连续性不可确定** | 无法判定计数在窗口内是否连续（连续性标记缺失、端点不可比） | **不采纳该读数**（A 层保留备查） | **否** | 把两端读数当作可比端点直接相减 |
| **X-10** | **来源不可靠**（前置条件类） | 多来源混采、计数归属的设备不明 | **不采纳**该读数 | **否** | 把多来源计数相加或取最大 |
| **X-11** | **计数器语义未通过 N6 实验**（前置条件类） | N6 未通过 | **不产出任何可用数值**；只保留原始读数供取证 | **否** | 写入生产数据 |

> **X-1 ~ X-9 即 GPT v2.2 点名的九类异常**（Δ 与 E1 矛盾 / 重置 / 回绕 / 重启 / 采样间隔过长 / 采样缺失 / 设备身份变化 / 采集失败 / 连续性不可确定）；X-10 与 X-11 是另加的两类**前置条件**（来源不可靠 / N6 未通过），它们不是「异常」而是「本来就还不具备取值资格」。

> **降级的统一原则**：**任何不确定情形下的默认动作都是「不产出可用数值」，而不是「产出可疑数值」。**
> **特别强调（GPT v2.2 · R11-02）**：**「标记 UNKNOWN」本身不是免责**。若一个 Δ 被判为不可信，它**必须被挡在统计与展示之外**，而不是打上 UNKNOWN 标签后继续流入日均、排行或窗口级汇总。

### 4.1.4 W1 与 E2 的定位：不可替代、不可升级（GPT v2.2 · R11-01）

**两条证据各自解决什么问题**：

| | **E2 独立可证状态区间** | **W1 窗口级累计增量** |
|---|---|---|
| 解决的问题 | 「**某连续区间内屏幕持续亮**」 | 「**某采样窗口内累计亮了多久**」 |
| 输出形态 | 连续区间 [t1,t2] | 窗口总量 Δ（**无时间分布**） |
| 能否定位「什么时候亮」 | ✅ 能（区间内全程亮） | ❌ **不能**（只知道总量，不知道分布） |
| 能否进入 `screen_session` / 精确 UNION | ✅ 能 | ❌ **不能**（W-3 / W-4） |
| 能否作为某一天的精确亮屏时长 | ✅ 能（区间归属日） | ❌ **不能**（W-7；跨日窗口更不能） |
| 与对方的关系 | —— | **不是替代关系，也不能互相升级** |

**七条统一规则（GPT v2.2 · R11-01）**：

| 编号 | 规则 |
|---|---|
| **G-1** | **N6 通过** → 允许**评估**接入 W1 窗口级累计增量（接入与否还取决于 D2 的证据表字段定稿） |
| **G-2** | **N6 不通过** → **不产出可用 W1 数值**（原始读数可留作诊断） |
| **G-3** | **无论 N6 是否通过，W1 永远不能升级为 E2** |
| **G-4** | **W1 不得生成连续亮屏会话**（不得写 `screen_session`） |
| **G-5** | **W1 不得进入精确 session 区间或精确 UNION** |
| **G-6** | **W1 不得直接生成某一天的精确亮屏时长** |
| **G-7** | **W1 与 E2 必须在证据模型、字段语义、统计用途和展示说明中严格区分**（见 §4.1.6 与 §6.3 的 `evidenceType` 取值） |

> **G-3 是硬约束**：即使将来出现「计数器 + 其它证据」的新组合，只要那个组合**不能证明连续区间**，它就仍然**不是 E2**。E2 的定义（§4.1）不因 W1 的验证结果而改变。

### 4.1.5 W1 数据的三层语义：原始读数 / 计算结果 / 可用数值（GPT v2.2 · R11-02）

**当前设计对「计数器与 E1 矛盾时到底留什么」存在歧义。本节把它拆成三层，各层的保存与消费规则不同。**

```text
  A 层 · 原始读数（Raw）           ← 无条件保留，只用于诊断与取证
      采样时刻 t0 / t1
      设备累计计数器原始值 C(t0) / C(t1)
      设备身份（sourceDeviceId）
      本次采集是否成功
      重启 / 重置 / 回绕等识别信息
      ↓（做差 + 可信度校验）
  B 层 · 计算结果（Derived）        ← 可保留，但未通过校验前不得使用
      原始差值 Δ = C(t1) − C(t0)
      差值计算方法
      计算是否成立（端点是否可比、是否同设备、是否连续）
      是否存在反常变化或与 E1 的证据冲突
      ↓（可信度校验全部通过）
  C 层 · 可用窗口级数值（Usable）  ← 唯一允许进入展示与统计的层
      是否通过可信度校验
      是否允许进入窗口级数据展示
      是否允许进入任何统计汇总
      是否只能用于诊断
```

**三层规则表**：

| 层 | 存什么 | 什么时候产生 | 能否进统计 | 能否进展示 | 失效时的处理 |
|---|---|---|---|---|---|
| **A 原始读数** | 时刻、原始值、设备身份、采集状态、连续性识别信息 | **每次采样都产生**，无条件 | **否** | **否**（仅诊断页 / 取证包） | —— 永远保留 |
| **B 计算结果** | Δ、计算方法、是否成立、冲突标记 | 两个**可比**读数之间 | **否**（未过校验） | **否** | 不成立即**丢弃 Δ**，只留 A 层 |
| **C 可用数值** | 通过校验的窗口级 Δ | B 层通过**全部**校验项 | **仅限窗口级口径**（§4.1.6） | **是**（且必须带「窗口级 / 无法按日拆分」说明） | 不通过即**不产生 C 层** |

**B → C 的校验项（全部通过才算可用）**：

| 编号 | 校验 | 不通过的后果 |
|---|---|---|
| **V-1** | 两次采样**同设备**（`sourceDeviceId` 相同） | 不产生 Δ |
| **V-2** | 两次采样**之间无采集失败** | 不产生 Δ |
| **V-3** | 计数器**连续性可确定**（无重启 / 重置 / 回绕） | 不产生 Δ |
| **V-4** | Δ ≥ 0 且 Δ 与采样间隔**相容**（不得大于间隔时长） | 不产生 Δ |
| **V-5** | 与同窗口的 E1 证据**不矛盾** | **不产生 C 层**（可保留 B 层供诊断） |
| **V-6** | N6 **已通过**（语义已知） | 不产生 C 层 |

> **V-5 的特别说明**：Δ 与 E1 矛盾时，**B 层保留**（原始差值与冲突标记留作取证），但**不产生 C 层** —— 即该 Δ **不进入任何统计与展示**。这正是「不得仅通过标记 UNKNOWN 就让不可信数值继续流入统计」的实现方式。

### 4.1.6 W1 的消费边界（逐场景，GPT v2.2 · R11-03）

**总原则**：W1 **只提供窗口级增量**。凡是需要「某一天 / 某一小时 / 某个排名」的精确口径，W1 **一律不参与**；凡是需要「窗口级补充说明」的地方，W1 **可以出现，但必须带窗口起止与「无法按日拆分」**。

| # | 场景 | 是否消费 W1 | 展示形态 | 是否参与总量统计 | 是否需要「部分数据 / 估算」提示 | 是否可能与 E1/E2 重复计算 |
|---|---|---|---|---|---|---|
| **W-S1** | **首页今日亮屏时长** | **不消费**（亮屏数值不取自 W1） | 不出现 | **否** | 不需要（该数值与 W1 无关） | **否** |
| **W-S2** | **日历每日亮屏时长** | **不消费**（不落到任何一格） | 不出现 | **否** | 不需要 | **否** |
| **W-S3** | **应用排行** | **不消费**（W1 是屏幕级证据，不拆到包） | 不出现 | **否** | 不需要 | **否** |
| **W-S4** | **应用详情** | **不消费** | 不出现 | **否** | 不需要 | **否** |
| **W-S5** | **周 / 月 / 年周期总结** | **不消费**（不参与周期统计） | 不出现 | **否** | 不需要 | **否** |
| **W-S6** | **跨设备 SUM** | **不消费**（不得跨设备相加） | 不出现 | **否** | 不需要 | **否** |
| **W-S7** | **占用时钟 UNION** | **不消费**（UNION 的输入必须是已证明的连续区间） | 不出现 | **否** | 不需要 | **否** |
| **W-S8** | **历史数据重建** | **不消费**（重建的输入是 `screen_session` 的 E1/E2 区间） | 不出现 | **否** | 不需要 | **否** |
| **W-S9** | **备份与恢复** | **可消费，但仅作记录** | 备份保留 A 层原始读数与（若存在）C 层窗口级数值；**恢复后仍是窗口级** | **否**（不得参与任何日聚合） | 恢复摘要显示「含 N 条窗口级累计记录」 | **否** |
| **W-S10** | **窗口级数据专区的「累计亮屏」提示行** | **可消费 C 层** | 「采样窗口 [t0,t1] 累计亮屏 N 分钟（无法按日拆分）」 | **否**（只作说明，不进任何汇总） | **必须**显示「无法按日拆分」 | **是（必须防重）** —— 见下 |

**防重复计算（W-S10 的硬约束）**：

> W1 的窗口级总量与 E1/E2 区间**可能覆盖同一段真实亮屏时间**。因此：
> ① W1 数值**永远不进入**任何与 E1/E2 相加的总量（**不做** `E1 合计 + W1 Δ`）；
> ② 若某窗口的 E1/E2 区间**已覆盖该窗口的全部**，W1 在该窗口**不展示**（避免「同一段时间被数两次」）；
> ③ 若 E1/E2 只覆盖了窗口的一部分，W1 **不得**用来「补齐差额」（那正是 W-7 禁止的按比例估算）—— 只作为**独立说明行**出现，**不参与任何加总**。
### 4.2 Activity 前台证据的重新界定（GPT §3.2）

#### 4.2.1 结论先行

> **Activity 前台区间只能作为辅助证据，不得直接等价于亮屏时间。**
> 在 N4（MIUI「息屏而 Activity 仍可见」的发生率）验证之前，**Activity 区间不得生成精确亮屏区间**（RL-11）。

#### 4.2.2 为什么不能直接等价

Android 的前台 Activity 可见性与屏幕亮灭**不是同一个状态**：

- Activity 可见时屏幕**可能**已经息屏（息屏但 Activity 仍在 resumed 状态，唤醒后立刻恢复画面）；
- MIUI 的 `totalTimeUsed` 明确把「前台服务、画中画、灭屏但可见的 Activity」计入（代码注释自述「实测米家 +6.5%、当天合计 +8.5%」），这本身就是「Activity 前台 ⊄ 亮屏」的**已知反例**；
- 因此 `ACTIVITY_RESUMED` 配对区间是「**应用在前台**」的证据，不是「**屏幕亮着**」的证据。

#### 4.2.3 Activity 证据的合法用法

| 用法 | 允许？ | 说明 |
|---|---|---|
| 作为**应用时长**的证据 | ✅ | 这是它本来就证明的东西 |
| 作为**亮屏区间的唯一依据** | ❌ | 违反 RL-11 |
| 作为 E2 的**组成部分**（与独立系统状态联合） | ⚠️ 待验证 | 需 **§4.2.4** 与 **§13 的 N2、N4** 结论支撑（**§4.3 的计数器不参与**：它只给窗口总量、无时间分布，不能与 Activity 事件联合证明连续区间 —— §4.1.4 G-3） |
| 作为「该时段有前台活动」的**辅助标记** | ✅ | 可用于解释「为什么亮屏证据缺失」，但**不产生时长** |

### 4.3 W1 候选证据源：`screen-interactive` 累计计数器（v2 新发现；**v2.1 由「E2 候选」改为「W1 候选」**）

> **v2.1 更正（GPT R11-1）**：本节标题原为「E2 候选证据源」，**不准确**。累计计数器**不属于 E2** —— 它只给窗口总量，不给连续区间。证据等级见 §4.1.3（W1）。

#### 4.3.1 事实

明文 dump 的 `event aggregations` 段含如下行（归档明文 dump 第 1643 / 3387 / 4339 / 4389 / 4481 行）：

```text
  In-memory daily stats
  timeRange="2026/11/23 09:23–10:40"
    …
    event aggregations
      screen-interactive: 36x for "128:30:30"
      screen-non-interactive: 36x for "4:13:29"
```

其它块还有 `14832x for "1612:19:59"`、`30x for "69:58:00"`、`103x for "207:52:02"`、`9182x for "979:17:35"`。

**App 目前捕获了这个值，但从未使用**：

```kotlin
// UsageDumpParser.kt:108
private val SCREEN_CHECKIN = Regex("""screen-interactive: (\d+)x for (\d+)""")
// UsageDumpParser.kt:201
screenMatch != null -> current?.screenAggMs = screenMatch.groupValues[2].toLong()
```

`screenAggMs` 的写入是 `UsageDumpParser.kt:201`，**全仓库没有任何读取点** —— 这是一条**被捕获后丢弃**的证据线索。

#### 4.3.2 为什么它可能重要

若该计数器衡量的是「**屏幕处于 interactive 状态的总时长**」，那么**两次采样之间的增量**就是一个**独立的、窗口级的亮屏时长测量**：

- 它**不是**「假设一直亮着」的推断（这正是 RL-1 禁止的做法）；
- 它**不依赖事件缓冲** —— 计数器不受滚动窗口影响 → **正好命中线 1 的缺口**；
- 它**只能给出窗口级总量**，无法拆分到日 / 小时 → **正好对应方案甲的粒度**（§4.4）。

#### 4.3.3 语义未定 —— 登记为 N6，必须先验证

当前**无法确定**该计数器的确切语义：

| 疑点 | 观察到的数据 | 两种可能的解释 |
|---|---|---|
| 数值远超其 `timeRange` 长度 | `In-memory daily stats` 的 timeRange 是 `2026/11/23 09:23–10:40`（约 1h17m），但计数是 `36x for "128:30:30"`（约 128.5 小时） | (a) 计数是**自某起点累计**的，块的 timeRange 只描述包统计、不描述聚合；(b) 计数与该 timeRange 无关 |
| 与 `screen-non-interactive` 配对 | `36x for "4:13:29"` | 与 (a) 一致：若累计窗口很长，非交互时长 4 小时远小于交互 128 小时 → 符合「长期亮屏」 |
| 量级序列 | 36 / 14832 / 30 / 103 / 9182 | 不同块有各自的计数 → 更像**各自分段内的聚合**，而非单一全局累计 |
| 单位 | `HH:MM:SS`，小时数可 > 24 | 与 `128:30:30` = 128h30m30s 一致 |

**两种解释导向完全相反的结论**：

- 若是**累计增量** → 可用（差值 = 窗口亮屏时长）；
- 若是**窗口内聚合** → 128.5 小时落在 1h17m 窗口内**物理不可能** → 说明我们读错了块与行的配对关系 → 该计数器不可用。

#### 4.3.4 判定实验协议（N6，可执行、不改生产代码）

```text
  对照实验：两次 dump 采样之间，人为控制屏幕状态

  实验 A（灭屏对照）
    t0  亮屏，dump 一次，记 C0（screen-interactive 计数）
    t0+1 分钟  息屏（关闭「插着数据线不休眠」或按电源键）
    t0+31 分钟  保持息屏
    t0+32 分钟  dump 一次，记 C1
    期望：若计数器测「亮屏时长」 → C1 - C0 ≈ 0 分钟
          若计数器测「经过时长」 → C1 - C0 ≈ 31 分钟  ⇒ 不可用

  实验 B（亮屏对照）
    t0  息屏，dump 一次，记 C0
    t0+1 分钟  亮屏并保持 10 分钟
    t0+12 分钟 dump 一次，记 C1
    期望：若计数器测「亮屏时长」 → C1 - C0 ≈ 10 分钟

  实验 C（重启对照）
    重启设备后再采样，确认计数器是否归零 → 决定增量算法要不要处理「计数器回绕 / 归零」

  判定：A 与 B 同时成立 → 语义为「累计亮屏时长」，**归入 W1 窗口级证据（不是 E2 —— 见 §4.1.3）**；
        A 不成立       → 语义为「经过时长」或配对关系读错，该源作废（N6 关闭为「不可用」）；
        任一实验无法复现 → 保持 N6 开放，不写入设计结论。
```

### 4.4 线 2 候选方案：「保留窗口级聚合」vs「允许估算但标记估算」

**D1 已定方向：方案甲。** 本节保留两案的完整对比，供后续复核与回退决策。

#### 方案甲 · 保留窗口级聚合（D1 方向）

- 数据层：跨日滚动窗口**不拆到各自然日**，而是作为**窗口级记录**保留；
- 聚合层：**不**把窗口时长计入任何单日的 `app_usage.minutes`；
- 展示层：
  - 应用排行页：跨日窗口的包**单独成行**，标注「11-21 09:2x → 11-22 09:2x（跨日窗口）」，时长是**窗口总量**，不假装属于某一天；
  - 「应用构成」卡：**只统计可归属到单日的时间**；窗口级部分单列说明；
  - 日 / 夜条：**分母只含有归属明确的时间**，窗口级不参与；
  - 单日趋势（统计页 / 日历页）：该日**可能为空**，需明确「无单日归属数据」而不是 0。

**优点**：零伪造；不触碰 CR-28 冻结口径；备份兼容最简；不依赖任何「每格挂标记」的纪律。

**缺点**：用户看到的信息变少；单日趋势出现空洞；需要新增「窗口级」的展示语言。

#### 方案乙 · 允许估算但显式标记估算

- 把跨日窗口按**自然日重叠比例**切到各天，每个被切分的格子带 `ESTIMATED` 标记；
- 标记必须贯穿：解析层 → 入库层 → 聚合层 → ViewModel → UI → 统计分母 → 导出 → 备份。

**优点**：单日视图连续；给出有用的近似。

**缺点**：**标记一旦在某端丢失就退化成假精确**（最大风险）；分母口径含混；备份 / 合并 / 跨设备三处都要处理标记，CR-28 的取大规则需扩展。

#### 对比结论

| 维度 | 方案甲（D1 已定方向） | 方案乙 |
|---|---|---|
| 是否伪造精确日数据 | 否 | 否（前提：标记全链路保真） |
| 标记丢失风险 | 无标记需求 | **高** |
| 对 CR-28 的冲击 | 小 | 中 |
| 备份格式冲击 | 小 | **大**（schema 6 → 7，旧读取器 `ignoreUnknownKeys` 会静默丢标记） |
| 实现复杂度 | 中 | 高（7 层） |
| 单日连续性 | 差（有空洞） | 好 |
| **长期可维护性** | **高** | 中 |

**与 D4 的关系**：D4「估算值不进入默认日均分母」**与选甲或选乙都兼容** —— 方案甲根本没有估算值，方案乙有估算值但被排除在默认分母外。

### 4.5 门禁：为什么不能把 `> 1440` 改成 `>= 1440`

1. **会丢掉真实数据**：长亮屏下 1440 分钟是真实值；
2. **会误伤真实整天使用的用户**（游戏挂机、导航常驻）；
3. **把归属错误掩盖成丢弃问题** —— 真 bug 是「24h 窗口整段记到一天」；
4. **门禁会失去本职**：`> 1440` 是「物理上不可能」的硬判据，`>=` 之后变成「可疑值检测器」。

**替代方案：按「采集状态 × 数据质量」两维度判定（§5.2）**，而不是靠单一阈值：

```text
  单日应用合计 = 1440 分钟时，区分：
    采集状态 = FAILED / UNAVAILABLE  → 失败路径，本来就不该入库
    数据质量 = EXACT                  → 放行（真实整日使用）
    数据质量 = WINDOW                 → 窗口级数据，不进单日合计（方案甲下不成立）
    数据质量 = PARTIAL                → 放行但标记，界面上标注「不完整」
    数据质量 = UNKNOWN（legacy）      → 只读，不改写（CR-28）
```

## 5. 数据模型变更建议

### 5.1 为什么必须拆成两个维度（GPT §3.3）

v1 用单一 `DataQuality` 枚举，把两件事混在一起：

| 例子 | 「采集状态」 | 「数据质量」 | 合并成单枚举的后果 |
|---|---|---|---|
| 长亮屏第 2 天 | 采集**成功** | 该日亮屏**无法证明完整** | 会被标成「缺失 / 失败」→ UI 显示「采集失败」，**误导用户去查权限** |
| Shizuku 未启动 | 采集**失败** | 没有新数据入库（沿用旧值） | 会被标成「部分缺失」→ 把**通道问题**说成**数据问题** |
| 正常的一天 | 采集成功 | 精确 | —— |
| legacy 历史行 | 采集状态**不适用**（不是本次采集产生的） | **来源未知** | 无法表达 |

**结论**：两维度**正交**。采集状态回答「**这次采集过程发生了什么**」；数据质量回答「**已经入库的这行数据能被证明到什么程度**」。

### 5.2 维度一 · 采集状态（`CollectionStatus`）

**作用域：一次拉取（`pull_log` 的一条）。**

| 值 | 语义 | 判定点 | 消费点 |
|---|---|---|---|
| `OK` | 采集完成，且有可用数据 | 两路 dump 至少一路形态可用且解析成功 | 正常入库 |
| `EMPTY` | 采集完成，但**该时段没有事件**（合法为空） | 解析成功但结果为空 | 正常入库（可能无行）；UI 显示「暂无记录」而非「失败」 |
| `PARTIAL` | 采集完成，但**只覆盖部分时段** | 明文主导（checkin 无数据）/ 工具只吐元信息 / 事件缓冲已滚出 | 入库但**打质量标记**；UI 显示「数据不完整」 |
| `FAILED` | 采集过程**明确失败** | shell 执行失败 / 看门狗截断（`checkedOutput`）/ 解析抛异常 | **不写新数据**，保留旧值；UI 显示「采集失败」 |
| `UNAVAILABLE` | 通道**不可用** | Shizuku 未运行 / 降级通道无权限 | 同 `FAILED`，但文案区分（用户该去开 Shizuku） |

**采集状态落点**：扩展 `pull_log.note` 的结构化形式（新增可空列 `collectionStatus`），**不改** `pull_log` 既有列语义（CR-01 红线）。

### 5.2.1 `EMPTY` 的判定边界（GPT R11-2 · v2.1 新增）

**核心原则（不可违反）**：

> **没有采集到事件，不等于证明该时间段没有使用。**
> `EMPTY` 只能表达「**本次采集没有拿到任何记录**」，**永远不能**表达「该时间段用户没有使用手机」。

#### 5.2.1.1 四类情形的区分

| 情形 | 含义 | 可否判 `EMPTY` | 正确表示 |
|---|---|---|---|
| **① 真实空数据** | 采集成功、采样窗口**完整且可信**、窗口内系统**确实没有产生**任何相关事件 | **可以**，但须同时满足 §5.2.1.2 的四个前提 | 采集状态 `EMPTY` + UI「暂无记录」 |
| **② 暂无证据** | 采集成功，但**无法证明窗口内事件完整**（缓冲可能滚出 / 来源不产该类事件 / 解析未匹配） | **不可以** | 降级为 `PARTIAL`（能定位部分时段时）或数据质量 `UNKNOWN` |
| **③ 采集失败** | 采集过程明确失败（shell 失败 / 看门狗截断 / 解析抛异常） | **不可以** | 采集状态 `FAILED`，**不写新数据**，保留旧值 + 「采集失败」提示 |
| **④ 通道不可用** | Shizuku 未运行 / 未授权 / 降级通道无权限 | **不可以** | 采集状态 `UNAVAILABLE`，**不写新数据** + 「请开启 Shizuku」提示 |

#### 5.2.1.2 「真实空数据」的四个必要前提（缺一即不得判 `EMPTY`）

| 前提 | 要求 | 当前可满足性 |
|---|---|---|
| **P-1 采集成功** | 两路 dump 至少一路形态可用且解析成功 | ✅ 可判定 |
| **P-2 窗口完整** | 能证明采样窗口内**没有事件被滚动丢弃** | ❌ **当前无法证明** —— MIUI 缓冲滚动正是线 1 的同一机制 |
| **P-3 来源可信** | 该窗口内该类事件的**产出规则稳定**（不是某些机型 / ROM 版本根本不产出该类事件） | ❌ **未验证** —— §2.3 的差异矩阵里「通知事件」一行已有同类先例 |
| **P-4 覆盖目标时段** | 采样窗口**确实覆盖**被判定为空的那一天 / 时段 | ✅ 可判定（用 dump 内 `timeRange` / 锚点） |

> **由 P-2 与 P-3 当前均无法证明得出的结论**：
> **在现有能力下，`EMPTY` 只能以「弱 EMPTY」形式出现**，语义仅为「本次采集没有拿到任何记录」。
> **不得**用它做任何「该时段未使用」的断言，**不得**用它把某日排除在「有记录日」之外再据此抬高日均。

#### 5.2.1.3 逐项回答「能否使用 `EMPTY`」

| 问题 | 回答 |
|---|---|
| 系统事件缓冲区可能滚动丢失历史事件时，能否使用 `EMPTY`？ | **不能**。滚动丢失本身就是证据缺失，必须降级为 `PARTIAL` / `UNKNOWN`（P-2 不满足） |
| 采集成功但解析结果为空，是否足以认定 `EMPTY`？ | **不足够**。空结果可能是解析器未匹配 / dump 形态退化 / 只拿到元信息 —— 都属于「暂无证据」，必须降级（P-2 / P-3 不满足） |
| 采集失败怎么表示？ | 采集状态 `FAILED`；**不写新数据**；既有行质量不变；UI「采集失败」 |
| 权限缺失怎么表示？ | 采集状态 `UNAVAILABLE`（Shizuku 未运行 / 未授权）；文案与 `FAILED` 区分（引导用户去开 Shizuku） |
| 部分缺失怎么表示？ | 采集状态 `PARTIAL` + 对应指标数据质量 `PARTIAL`；数值可展示，但**不进日均分母、不参与极值**（§5.9） |
| 来源未知怎么表示？ | 数据质量 `UNKNOWN`（legacy / 恢复后旧行）；保留原值 + 「来源未知」标记 |
| `EMPTY` 是否需要额外的完整性证据或可信采样窗口？ | **需要**，即 P-2 与 P-3。当前**没有**这样的探测手段 → 只能弱化使用（见上） |

#### 5.2.1.4 三件事必须能区分

```text
  「没有记录」  ≠  「记录为 0」  ≠  「该时段没有使用」

  没有记录        → 采集状态 EMPTY（弱语义：本次没拿到记录）+ 无行
  记录为 0        → 有行，且该指标的数据质量 = EXACT（证据完整且证明为零）
  该时段没有使用  → 本 App **无法证明**，**永远不得**显示为 0
```

#### 5.2.1.5 一条红线

> **禁止**将事件缺失、缓冲区滚动、解析失败或证据不足伪装成真实零值（**RL-14** / RL-9）。
> 一旦某日只能得到「没有记录」，该日在所有统计口径中都必须**按缺数据处理**，而不是按 0 处理 —— 尤其**不得**因此把该日计入日均分母。

### 5.3 维度二 · 数据质量（`DataQuality`）

**作用域：单个指标，而不是整行。** 这是 v2 的一处重要澄清：

| 指标 | 证据来源 | 可能的质量取值 |
|---|---|---|
| `day_summary.screenMin` / `screenUnlockMin` / `longestSessionMin` | **屏幕事件** | `EXACT` / `PARTIAL` / `UNKNOWN` |
| `hour_usage.minutes` | **屏幕事件** | `EXACT` / `PARTIAL` / `UNKNOWN` |
| `app_usage.minutes` | **应用事件**（区间 / In-memory / 事件流） | `EXACT` / `PARTIAL` / `UNKNOWN` |
| `screen_session` 行 | **屏幕事件** | `EXACT`（E1/E2）/ `ANCHOR_ONLY`（E3） |
| 窗口级记录（D2 证据表） | **窗口聚合** | `WINDOW` |

> **为什么按指标分**：`app_usage` 的 1440 分钟是**应用时长**（有精确证据），`day_summary.screenMin` 的 0 是**亮屏时长**（无证据）。给整行打一个标签会把这两种事实搅在一起 —— 正是 v1 的缺陷。

| 值 | 语义 | 能否产生时长 |
|---|---|---|
| `EXACT` | 精确值，证据完整（E1 或 E2） | 是 |
| `WINDOW` | 窗口级聚合，**不归属任何单日** | 是，但**属于窗口不属于日** |
| `ANCHOR_ONLY` | 只有状态锚点（E3），**无时长** | **否** |
| `PARTIAL` | 有数据，但**无法证明完整** | 是，但数值只是**已观测部分** |
| `UNKNOWN` | 来源或质量**不可知**（历史 / legacy 默认态） | 是（保留原值），但不可证明 |

**已删除的取值**：`UPPER_BOUND`（上界）与 `LOWER_BOUND`（下界）**整体删除** —— 区间不等式不是证据类型（RL-10）。

> **W1 与 `screen_session` 的硬边界（v2.2 · R11-01）**：`WINDOW`（W1）质量取值**只允许出现在窗口级记录**（D2 的 `screen_evidence` / `usage_window` 方向）。
> **W1 永不写入 `screen_session`、永不参与 `SessionUnion.union`、永不进入 `day_summary.screenMin` / `hour_usage` 的日聚合。**
> 依据：§4.1.4（G-3 / G-5）与 §4.1.6（防重复计算三条硬约束）。

### 5.4 两维度的组合与互斥

| 采集状态 \ 数据质量 | `EXACT` | `PARTIAL` | `ANCHOR_ONLY` | `WINDOW` | `UNKNOWN` |
|---|---|---|---|---|---|
| `OK` | 常见 | 缓冲滚出 / 明文主导 | 有锚点无区间 | 跨日窗口 | legacy 行 |
| `EMPTY` | —— | —— | —— | —— | —— |
| `PARTIAL` | 部分区间精确 | 部分区间精确 | —— | —— | —— |
| `FAILED` | —— | —— | —— | —— | —— |
| `UNAVAILABLE` | —— | —— | —— | —— | —— |

**互斥关系**：

- 同一**指标**在同一时刻只能有一个质量取值；
- `ANCHOR_ONLY` 与任何「产生时长」的取值**互斥**；
- `WINDOW` 与单日取值**互斥**（窗口级记录不落到日）；
- 采集状态 `FAILED` / `UNAVAILABLE` 时**不产生新的质量取值**（沿用既有行）；
- 采集状态 `EMPTY` 时**不产生行**，也不产生质量取值 —— 「没有记录」与「记录为 0」是不同的事。

### 5.5 状态转换规则

```text
  每次拉取：
    采集状态 = 判定（OK / EMPTY / PARTIAL / FAILED / UNAVAILABLE）
        │
        ├─ FAILED / UNAVAILABLE → 不写新数据；既有行质量不变
        ├─ EMPTY                → 不写行；（清理过期行属独立议题，本轮不做）
        └─ OK / PARTIAL         → 写入数据，并逐指标标注质量

  写入时（逐指标）：
    屏幕指标：
      有 E1/E2 区间           → 该部分 EXACT
      只有 E3 锚点            → 该部分 ANCHOR_ONLY（不写 screen_session）
      有区间但覆盖不全        → PARTIAL
    应用指标：
      区间 / In-memory 命中   → EXACT
      只有事件流推导出        → PARTIAL（事件流会系统性低估）
    合并既有行时（D7）：
      数值取大 + 质量随行整体取（同一次写入的数值与标记不拆开）
      legacy 行 → 永远 UNKNOWN，只读
```

### 5.6 三层传递（数据层 → ViewModel → UI）

```text
  数据层
    · day_summary 增可空列 screenQuality   （屏幕类指标）
    · hour_usage  增可空列 quality         （屏幕类指标）
    · app_usage   增可空列 minutesQuality  （应用类指标）
    · screen_session 不改（D2：新增独立证据表，见 §6.3）
```

### 5.7 旧备份缺少质量字段时的兼容

| 情形 | 处理 |
|---|---|
| 旧备份（schemaVersion ≤ 6）**没有**质量字段 | 反序列化时字段缺省为 `null`；`null` 在语义上**等同 `UNKNOWN`**（不可证明），**不得**默认为 `EXACT` |
| 恢复后旧行的质量 | 一律 `UNKNOWN`；UI 按「来源未知」呈现（§10.2） |
| 备份 schemaVersion | 按 D7 / §7 决定是否升到 7；**升版时新字段必须可空**，保证旧备份仍可读 |
| `collectionStatus` 缺失 | 视为 `UNKNOWN`（不是 `OK`，也不是 `FAILED`）—— **不得**反推 |

**不追溯回填**：Room 迁移只改结构，新列对旧行留空（§6.4）。

### 5.8 历史 legacy 数据的处理

| 项 | 规则 |
|---|---|
| 质量取值 | 恒为 `UNKNOWN`（`__legacy__` 行） |
| 来源身份 | **不得**强分配（RL-7 / CR-28 F2） |
| 数值 | **保留原值**，不改写 |
| 是否参与日均分母 | **不计入**（`UNKNOWN` 不进分母） |
| 是否参与排行 | 可显示，但**必须**带「来源未知」标记；**不参与**百分比分母 |
| 是否参与极值 | **不参与** |
| 备份往返 | 质量标记原样保留，**不得**在导入时被「补齐」 |

### 5.9 哪些状态不能进入日均分母、排行与极值（GPT §3.3 要求）

| 计算 | 允许进入 | 排除 | 理由 |
|---|---|---|---|
| **日均分母**（`recordedDays`） | 仅 `EXACT` 的日 | `PARTIAL` / `WINDOW` / `ANCHOR_ONLY` / `UNKNOWN` 的日 | 分母要求「完整的一天」；混入不完整日会放大日均 |
| **日均分子** | 仅 `EXACT` 日的数值 | 同上 | 分子分母必须同源同口径 |
| **单日排行** | `EXACT` 的应用时长正常显示 | `WINDOW`（无单日归属）**不进单日排行**；`PARTIAL` / `UNKNOWN` 的行可显示但**带标记**且**不参与百分比分母** | 百分比必须有可信分母 |
| **最长连续 / 极值** | 仅 `EXACT` | `PARTIAL` / `UNKNOWN` 的极值**不参与**最大/最小比较 | 「不完整的最大值」会误导 |
| **日 / 夜条百分比** | 仅 `EXACT` 且分母 > 0 | 分母为 0 或含非 `EXACT` → **不显示百分比** | RL-9 |
| **周期总结（日 / 周 / 月）** | 窗口级记录单列 | 窗口级**不混入**默认统计 | D1 / D4 |

**注意 `PARTIAL` 的双重处理**：它的**已观测数值**可以展示（用户有权看到「已经观测到多少」），但**不计入任何需要「完整日」的分母或极值**。这与 v1 的「标记取弱」不同，v2 明确了「展示」与「统计」是两件事。

### 5.10 逐表建议

| 表 | 建议 | 依赖 |
|---|---|---|
| `screen_session` | **不改表结构**（D2 方向：新证据另立表）。**只存 E1 / E2 的精确区间**；**W1 永不写入此表**（§4.1.4 G-3 / §4.1.6） | D2 |
| `day_summary` | 新增可空列 `screenQuality: String?`（默认 `null` = `UNKNOWN` 语义，**不回填**） | D7 / D8 |
| `hour_usage` | 新增可空列 `quality: String?` | D7 / D8 |
| `app_usage` | 新增可空列 `minutesQuality: String?` | D7 / D8 |
| `pull_log` | 新增可空列 `collectionStatus: String?` | D2 |
| 新表 `screen_evidence` | D2 的独立证据表（§6.3） | D2 |
| 新表 `usage_window` | 方案甲的窗口级记录（§4.4）；**是否与 `screen_evidence` 合表待定**。只承载**窗口级**数值（W1 的 C 层可入，A / B 层不入） | D1 |

## 6. Room migration 方案

### 6.1 现状与版本号

- 数据库结构版本：**`version = 8`**（`ScreenTraceDatabase.kt`）；
- 备份文件 `schemaVersion`：**`6`**（`BackupCodec.SCHEMA_VERSION`，`BackupModels.kt:172`）——**两套版本号，不要混**；
- 导出的 schema JSON 目录：`app/schemas`。

### 6.2 D8：增量迁移、禁止破坏性

| 纪律 | 说明 |
|---|---|
| **绝不使用 `fallbackToDestructiveMigration`** | 它会**清库**重建，直接违反 RL-7；本项目当前也未启用它，**不得引入** |
| **只增不改** | 既有列不改名、不改类型、不改语义（CR-01 红线） |
| **不追溯回填** | 新列对旧行留空（语义 = `UNKNOWN`），**不得**用「看起来更整齐」的理由回填成 `EXACT`（RL-7） |
| **schema JSON 必须入库** | `app/schemas/<version>.json` 随迁移一起提交，供 `MigrationTestHelper` 校验 |
| **索引声明逐字一致** | `Entities.kt` 的 `indices` 必须与 migration 建的索引名逐字一致（CR-28 真机踩过：迁移建了索引、实体没声明 → Room schema 校验炸、App 起不来） |
| **迁移不重算历史** | 迁移**只改结构**；历史重算是独立动作，须走 §9 且单独审批（RL-7 / D6 暂不清理） |

### 6.3 D2：独立证据表 `screen_evidence`

#### 6.3.1 设计原则

> **独立证据表只保存「可追溯的证据」，不得把未经证明的区间伪装成真实会话区间。**

| 原则 | 落地 |
|---|---|
| 不参与精确会话并集 | `screen_evidence` 的行**不进** `SessionUnion.union`，**不进** `screen_session` |
| 不参与日聚合重算 | 不参与 `day_summary.screenMin` / `hour_usage` 的重算 |
| 不产生单日归属 | 表内**不存自然日字段**；只存绝对时刻 |
| 跨来源不合并 | 带 `sourceDeviceId`，同来源内按来源规则处理，**跨来源永不合并**（CR-28 F4） |
| 可追溯 | 每行能指认它的来源 dump 与采集时刻 |

#### 6.3.2 候选字段

```text
CREATE TABLE IF NOT EXISTS `screen_evidence` (
    `startMs`      INTEGER NOT NULL,   -- 观测时刻（锚点时刻 / 区间起点）
    `endMs`        INTEGER,            -- 仅 E2 区间有；纯锚点为 NULL
    `kind`         TEXT NOT NULL,      -- SCREEN / KEYGUARD
    `evidenceType` TEXT NOT NULL,      -- EXACT(E1) / PROVEN(E2) / ANCHOR(E3) / WINDOW(W1 窗口级累计增量)
    `quality`      TEXT NOT NULL,      -- 冗余的质量取值，便于查询；与 evidenceType 一一对应
    `measuredMs`   INTEGER,            -- 窗口级测量值（如计数器增量），仅 WINDOW 使用
    `sourceDumpAt` INTEGER NOT NULL,   -- 产生该证据的 dump 采集时刻（可追溯）
    `sourceDeviceId` TEXT NOT NULL,    -- 来源维度
    PRIMARY KEY(`startMs`, `kind`, `evidenceType`, `sourceDeviceId`)
)
```

#### 6.3.3 字段说明与待确认项

| 字段 | 含义 | 待确认 |
|---|---|---|
| `endMs` | E2 区间的结束时刻；纯锚点为 `NULL` | 是否允许 `NULL`（Room 需要可空声明） |
| `evidenceType` | 证据类别（**4 个值互斥**：E1 / E2 / E3 三者互不等价，`WINDOW` 只属 W1） | 是否就用 4 个值，够不够 |
| `quality` | 与 `evidenceType` 一一对应 | **冗余**（避免两处语义漂移），还是只留一个 |
| `measuredMs` | 窗口级计数器增量（**W1 专属**） | 只在 N6 通过后启用；否则该列不使用。**落库必须是 C 层**（§4.1.5）：A 层原始读数与未通过 V-1~V-6 校验的 B 层 Δ **不得**作为可用数值入库 |
| `sourceDumpAt` | dump 采集时刻 | 是否还需要存 dump 的哈希以便复核 |

#### 6.3.4 主键为什么带 `evidenceType`

同一段时刻可以同时存在「精确观测」与「仅锚点」两种证据 —— 主键必须能区分，否则后写覆盖先写。

### 6.4 迁移脚本骨架

```kotlin
val MIGRATION_8_9 = object : Migration(8, 9) {
    override fun migrate(db: SupportSQLiteDatabase) {
        // ① 元数据列：可空 + 无默认值 ⇒ 旧行留空 ⇒ 语义为 UNKNOWN
        db.execSQL("ALTER TABLE `day_summary` ADD COLUMN `screenQuality` TEXT");
        db.execSQL("ALTER TABLE `hour_usage` ADD COLUMN `quality` TEXT");
        db.execSQL("ALTER TABLE `app_usage` ADD COLUMN `minutesQuality` TEXT");
        db.execSQL("ALTER TABLE `pull_log` ADD COLUMN `collectionStatus` TEXT");

        // ② D2 的独立证据表
        db.execSQL("""
            CREATE TABLE IF NOT EXISTS `screen_evidence` (
                `startMs` INTEGER NOT NULL,
                `endMs` INTEGER,
                `kind` TEXT NOT NULL,
                `evidenceType` TEXT NOT NULL,
                `quality` TEXT NOT NULL,
                `measuredMs` INTEGER,
                `sourceDumpAt` INTEGER NOT NULL,
                `sourceDeviceId` TEXT NOT NULL DEFAULT '__local__',
                PRIMARY KEY(`startMs`, `kind`, `evidenceType`, `sourceDeviceId`)
            )
            """.trimIndent()
        )
        db.execSQL("CREATE INDEX IF NOT EXISTS `index_screen_evidence_endMs` ON `screen_evidence` (`endMs`)");
        db.execSQL("CREATE INDEX IF NOT EXISTS `index_screen_evidence_sourceDeviceId` ON `screen_evidence` (`sourceDeviceId`)");
    }
}
```

**注意**：四个元数据列**不给 DEFAULT**。给 `DEFAULT 'EXACT'` 会把旧行谎称为精确（RL-7 / §5.7）。

### 6.5 方案甲的窗口级表（是否与 `screen_evidence` 合表待定）

| 方案 | 说明 | 待确认 |
|---|---|---|
| 合表 | `screen_evidence` 增设 `pkg` / `minutes` / `launches` 列，窗口级应用时长也放进去 | **混了两种语义**（屏幕证据 vs 应用窗口聚合），查询时容易误用 |
| 分表 | `screen_evidence`（屏幕证据）+ `usage_window`（窗口级应用聚合） | 表更多，但语义清晰、**误用风险低** |

**本文档倾向分表**，理由与 §8 一致：**降低「新证据绕过 CR-28 冻结约束」的风险**。

## 7. 备份兼容

### 7.1 现状

- 备份 `schemaVersion = 6`；
- `BackupFile` 顶层六表 = **备份导出设备**自己的分量，`sources[]` = 其他来源分量（含 `'__legacy__'`）；
- 所有列表给默认空值（`= emptyList()`），旧备份缺键 → 视为「不含此表」→ `BackupSummary.missingTables` 逐条提示；
- 兼容检查在 `BackupModels.kt:223-226`：`schemaVersion < 2/3/4/5` 逐条给出「该备份不含哪些内容」；
- 旧读取器 `ignoreUnknownKeys` → **能解析、能展示（只见顶层）、不能正常导入**（三层兼容）。

### 7.2 变更与备份处理

| 变更 | 备份处理 |
|---|---|
| `day_summary.screenQuality` | DTO 加可空字段 `screenQuality: String? = null`；旧备份缺 → `null` → 语义 `UNKNOWN`（§5.7） |
| `hour_usage.quality` | 同上 |
| `app_usage.minutesQuality` | 同上 |
| `pull_log.collectionStatus` | DTO 加可空字段；`BackupSource` **不含** `pull_log`（本机流水不随来源搬运），故只在顶层 |

| **`screen_session`** | **不改**（D2 方向）→ 备份的 `ScreenSessionDto` **不动** |

### 7.3 备份的四条硬约束

1. **备份里出现非 `EXACT` 的值时，必须同时出现标记**。绝不允许「备份里有 1440 分钟但没有说明它是窗口级 / 部分缺失 / 来源未知」；
2. **恢复时不得把非 `EXACT` 转成 `EXACT`**：`overwrite` 与 `merge` 两条路径都要保留标记；
3. **legacy 分量的标记原样保留**：CR-28 规定 legacy 只读，恢复时不得改写、不得强分配身份、不得补齐成 `EXACT`；
4. **`screen_evidence` 的恢复不得改变其性质**：它是「证据」，不是「会话」。恢复后它**仍然不参与** `screen_session` 并集与日聚合（否则备份往返会让证据变成会话 → 违反 D2 的核心约束）。

### 7.4 schema 6 备份语义（CR-28 冻结项，必须原样保持）

| 项 | 要求 |
|---|---|
| 顶层 = 导出设备分量 | **不得**改成「导出时把所有来源合并成一份」 |
| `sources[]` = 其他来源分量 | **不得**省略或扁平化 |
| 事件条目带 `seq` | 保持 |
| 旧读取器的三层兼容（能解析 / 能展示只见顶层 / 不能正常导入） | **不得**因为新增字段而变成「静默导入错误数据」 |

### 7.5 是否升到 schemaVersion 7

| 情形 | 决定 |
|---|---|
| 只加**可空**元数据列 | **技术上不升版也行**（可空 + 默认值向后兼容）；但升到 7 可让 UI 提示「该备份含质量标记」 |
| 加**新表**（`screen_evidence` / `usage_window`） | 建议**升到 7**（新表是可空列表，旧备份读不到 → 空，不报错） |

**本轮不拍板**：升版与否属 D 系列之外的实施细节，留待 GPT 在实施前确认。

## 8. CR-28 兼容分析

### 8.1 CR-28 冻结口径清单（逐条，本设计不得改动）

来源：`docs/需求文档-屏幕使用时间App.md` 头部 CR-28 登记（2026-11-17 负责人三项口径裁决 + 二审六条修订，设计审查 R2 通过）。

| 编号 | 冻结口径 |
|---|---|
| **F1** | **跨来源行为指标 SUM**：总使用时长 / 解锁 / 启动 / 应用排行 / 小时分布跨来源 **SUM**（两台各用 1h，对外合计 2h，但各自分量可追溯） |
| **F2** | **占用时钟区间 UNION**：「占用时钟时长」= 会话区间跨来源 **UNION**（**永不合并**跨来源区间），只计 SCREEN 会话；同日恒有 `UNION ≤ SUM`，`SUM − UNION` = 跨设备重叠时长；跨午夜会话按自然日裁剪 |
| **F3** | **`longestSessionMin` 跨来源 MAX**（**不许相加**） |
| **F4** | **legacy 来源身份**：`'__legacy__'` 行**只读保护** —— 普通拉取 / 合并 / 重算**不得**取大、覆盖或累加它；**禁止**根据当前设备 ID 猜测历史来源 |
| **F5** | **冻结日规则**：R1 的「冻结日跳过该日所有写入」方案**已被二审废除** —— 不得丢独立来源的原始事件；来源明确的新数据**照常独立写入**各自分量 |
| **F6** | **schema 6 备份语义**：顶层 = 导出设备分量（身份与导入设备无关）、`sources[]` = 其他来源分量、≤5 可导入、无 `device.id` 归 `'__legacy__'`、旧版本三层判定（能解析 / 能展示 / **不能正常导入**） |
| **F7** | **来源未知历史不得强行归属**：重建工具只写「有原始备份直接证明」的来源分量，`'__legacy__'` 只保留无法解释的剩余，剩余为 0 才删行 |
| **F8** | 写路径一律「同来源取大 / 覆盖」，**跨来源求和只发生在读取聚合** |
| **F9** | `screen_session` 是**日聚合的唯一重算输入**；会话扫线并集**按来源隔离** |

### 8.2 本设计的每一处改动 → 对 CR-28 的逐条影响

| 本设计的改动 | 触及的冻结口径 | 结论 |
|---|---|---|
| `day_summary.screenQuality` / `hour_usage.quality` / `app_usage.minutesQuality`（**可空元数据列**） | F1 / F3 / F8 | **不触及**：新列是元数据，不是数值；来源维度、合并语义、SUM / MAX 规则全不变 |
| `pull_log.collectionStatus`（可空） | F6 | **不触及**：`pull_log` 不进 `sources[]`（本机流水），备份只在顶层带 |
| D2 的 `screen_evidence` 新表 | F2 / F9 | **不触及**：该表**不进** `SessionUnion.union`、**不进** `screen_session`、**不参与**日聚合重算 → 不改变 UNION 与 SUM 的任何结果 |
| 方案甲的 `usage_window`（窗口级应用聚合） | F1 / F8 | **需谨慎**：窗口级记录**不写入**任何单日 `app_usage` → 不改变跨来源 SUM；若将来把它并进 `app_usage`，则**违反 F1** |
| 线 2 归属修正（D5，改 §2.2） | F1 | **不触及** SUM / MAX / UNION，但**会改变历史各日的应用数值** → 必须走 §9 与重建工具（F7） |
| `MergePolicy` 的元数据绑定（D7） | F8 | **不改变数值取大**，只是让标记随行整体取 → 需在重建工具同步（F7） |
| **不采用「冻结日跳过写入」** | F5 | **必须遵守**：legacy 日**照常**写入独立来源的新数据，只是 legacy 行本身只读 |

### 8.3 元数据与「同来源取大」的交互（D7）

CR-28 的合并规则是「同 (date, pkg) 取较大值」。引入质量元数据后有两种做法：

| 做法 | 说明 | 评价 |
|---|---|---|
| 元数据独立取弱 | 数值取大，标记另行取弱 | **不好**：会出现「数值取自新行、标记取自旧行」的错配 —— UI 会把一个精确值标成未知 |
| **元数据随行绑定（D7）** | 数值与标记**同行取**，取大时两者一起取 | **更好**：标记与它描述的数值始终同源 |

**本文档按 D7 方向**：元数据随行整体取。**仍待确认**：当新旧两行**数值不同**时，标记随「较大值那行」取，还是**另立规则**（例如只要任一行非 `EXACT` 就整体降级为 `PARTIAL`）——后者的保守性更强，但会掩盖「新的那行已经是精确值」的事实。

### 8.4 legacy 行的处理

- `'__legacy__'` 行的质量取值恒为 `UNKNOWN`；
- **只读**：普通拉取 / 合并 / 重算**不得**取大、覆盖或累加它（F4）；
- **不得**给 legacy 行分配来源身份（RL-7 / F4）；
- legacy 行的数值**一律保留原值**；
- 备份里 legacy 分量的质量标记**原样往返**，导入时**不得**补齐成 `EXACT`（§7.3）。

### 8.5 新证据表不得绕过 CR-28 约束（GPT §3.7 明确点名）

> 「新证据表不能绕过上述约束。」——这是 D2 最容易被绕过的地方，必须写成**可测试的断言**。

| 约束 | 断言（必须能变红） |
|---|---|
| 跨来源区间永不合并 | 向 `screen_evidence` 写入两个来源的**完全重叠**区间 → `SessionUnion` 结果**不变** |
| 证据不是会话 | `screen_evidence` 有行时，`screen_session` 行数与 `day_summary.screenMin` **不受影响** |
| 证据不参与日聚合 | `screen_evidence` 有 E2 区间时，`day_summary.screenMin` **不增加** |
| legacy 只读 | legacy 日 + 新来源数据 → legacy 原值**不变**，新数据独立成行 |
| 窗口级不进单日 | `usage_window` 有记录时，任何单日 `app_usage` **不出现**该窗口的分钟数 |
| 跨来源 SUM | 两来源同一天 → 展示层 SUM 正确；`longestSessionMin` 取 **MAX** 不相加 |
| 占用时钟 UNION | 两来源同一小时各 1h → UNION = 1h（不是 2h），SUM = 2h |
| W1 不进单日 | `screen_evidence` 有 `WINDOW`（W1）行时，`screen_session` **不新增**、`day_summary.screenMin` **不增加** |
| W1 不与 E1/E2 相加 | 同一窗口同时存在 E1/E2 区间与 W1 Δ → 展示层**不得**输出「E1 合计 + W1 Δ」，W1 **不得**用于补齐差额（§4.1.6） |
| W1 不可信即不出数 | 构造 Δ 与 E1 矛盾 / 计数器回绕 / 采样缺失 → C 层**不得**产生数值（§4.1.5 V-1~V-6） |

### 8.6 结论

**CR-28 的数据口径不需要修改。** 需要改的是「CR-28 的实现要同步支持新增的元数据」：

1. `MergePolicy` 的元数据绑定规则（§8.3）；
2. `SourceRebuild` 必须能重建出带标记的行（否则重建会把 `EXACT` 洗成 `UNKNOWN`）；
3. 备份的顶层与 `sources[]` 必须同时携带新元数据（§7.2）；
4. legacy 行的默认态是 `UNKNOWN`，且**只读**（F4）；
5. **不采用**「冻结日跳过写入」的路子（F5）；
6. 新证据表的 10 条断言必须进测试矩阵（§8.5，v2.2 补入 3 条 W1 硬边界断言）。

## 9. 历史数据处理原则

### 9.1 五条原则

1. **可从原始证据重建的才重建**；只能保留原值的保留并标记可信度；来源或日归属不可确认的一律**保留原记录 + 标记**，**不得为界面整齐伪造精确值**；
2. **不追溯改写**：Room 迁移只改结构，不改数值；质量列对旧行留空（= `UNKNOWN`）；
3. **不清库、不删备份**（RL-7）；历史上 `MIGRATION_2_3` / `MIGRATION_3_4` 清过 `app_usage` / `hour_usage`，那是当时有充分理由的特定事故修复，**不能当成常规手段**）；
4. **重算必须经批准**：历史重建是独立动作，走 `rebuild_log` 留痕，可回滚；
5. **D6：暂不清理历史数据** —— 本轮**不做**任何历史清理或重算。

### 9.3 一条必须写进实施说明的反面禁令

## 10. UI 展示口径

### 10.1 逐页梳理（GPT §3.6 要求：七处页面 + 标记一致性）

| 页面 | 数据来源 | 质量标记怎么呈现 | 窗口级数据怎么呈现 | 明确禁止 |
|---|---|---|---|---|
| **今日页** | `day_summary` + `hour_usage` + `app_usage`（当日） | 亮屏数值旁标「不完整」/「来源未知」角标；`dayPercent == null` → 日夜条**不显示百分比** | 「应用构成」卡下方单列「另有 N 小时来自跨日窗口（无法按日拆分）」 | 显示「0 分钟」表示未采集；显示「日间 0% / 夜间 100%」 |
| **统计页** | 多日聚合（`day_summary` + `hour_usage`） | 「日均」分母只计 `EXACT` 日；**并在卡片上写明**「日均按 N 个完整日计算」；被排除的日子在明细里标注 | 窗口级**不进默认统计**（D4）；若展示则单列，不混入时段分布 | 把窗口级分钟数摊进时段桶 |
| **日历页** | 月视图色阶 | `UsageCalculator.monthLevel` 现有口径 `!recorded || minutes <= 0 -> 0`（不着色）→ **保持**；`PARTIAL` / `UNKNOWN` 的格子**不着色**或用单独一档并在图例说明 | 窗口级不落到某格 | 给 `PARTIAL` 的格子按完整值着色 |
| **周期总结页** | `periods` / `extremes` / `topAppsPerDay` / `clockOccupied` | 极值（最长连续 / 最高单日）**只从 `EXACT` 取**；卡片注明「极值按 N 个完整日计算」 | 窗口级**单独一段**，不参与周期极值 | 用 `PARTIAL` 日的最大值当「最长连续」 |
| **应用排行** | `app_usage` | 行尾带来源未知 / 部分缺失标记；**百分比分母只含 `EXACT` 行** | 跨日窗口的包**单独成行**，标注窗口起止 | 在单日排行里把窗口级显示成 0 |
| **应用详情** | 与排行同源（§7-16） | 标记必须**与卡片同源**（§7-16 的「同源」同样适用于标记） | 同上 | 详情页不标、卡片标（不一致） |
| **备份与恢复** | `BackupFile` + `sources[]` | 恢复后旧行一律 `UNKNOWN`；备份摘要显示「含 N 条来源未知数据」 | 窗口级记录随备份往返，性质不变 | 恢复时把非 `EXACT` 洗成 `EXACT` |

### 10.2 状态 → 文案对照表（核心交付物）

| 采集状态 | 数据质量 | 亮屏时长 | 应用构成 | 日 / 夜条 | 排行 |
|---|---|---|---|---|---|
| `OK` | `EXACT` | 正常显示 | 正常显示 | 正常显示 | 正常 |
| `OK` / `PARTIAL` | `PARTIAL` | 显示**已观测数值** + 「不完整」角标 | 同左 + 角标 | 显示数值 + 角标（分母为 0 则不显示百分比） | 带角标，不进百分比分母 |
| `OK` | `ANCHOR_ONLY` | 「状态未知」 | 正常（应用侧另有其证据） | **不显示百分比**，显示「状态未知」 | 正常 |
| `OK` | `WINDOW` | 「见窗口级统计」 | 单列窗口级说明 | 不参与 | 窗口级单独成行 |
| — | `UNKNOWN` | 保留原值 + 「来源未知」 | 同左 | 不参与（不计入分母） | 带「来源未知」标记 |
| `EMPTY` | ——（无行） | 「暂无记录」 | 「暂无记录」 | **不显示百分比** | 空态 |
| `FAILED` | ——（无新数据） | 保留旧值 + 「采集失败」提示 | 同左 | 同左 | 同左 |
| `UNAVAILABLE` | ——（无新数据） | 保留旧值 + 「Shizuku 未运行」提示 | 同左 | 同左 | 同左 |

### 10.3 四条硬性要求

1. **缺分母时，日 / 夜条不得渲染成两个百分比。** `total == 0` 时**不显示百分比数字**，改为「暂无记录」/「状态未知」或整块隐藏。当前实现的 `right = 100 - left` 在 `left = 0` 时必然产出「夜间 100%」，这是**结构性错误**；
2. **「0 分钟」与「暂无记录」必须能区分。** 现在两者都是 0，需要质量标记来区分，而不是靠 UI 猜；
3. **不得出现任何区间不等式表述**（「≥ N 分钟」「≤ N 分钟」）—— D3 暂不允许，且 E3 也推不出下界（§4.1.1）；
4. **标记必须在数字旁边**，不是藏在说明文字里；建议精确值用常规样式，`PARTIAL` / `UNKNOWN` 加弱化角标。

### 10.4 实现要点

- `TodayData.dayPercent: Int` → `Int?`（`null` = 无分母），这是**类型层面的诚实化**；
- `DayNightBar` 入参从 `Int` 改为 `Int?`：`null` 时不渲染两个百分比；
- **不要**用「夜间补 100%」或任何补集计算来凑出两个数 —— 补集的前提是分母存在且已知；
- 日历页 `monthLevel` 的「不着色」口径**保持不变**（`!recorded || minutes <= 0 -> 0`），只需额外把 `PARTIAL` / `UNKNOWN` 也归入不着色；
- 周期总结页的「最长连续」「日均」「极值」若分母被排除过，卡片上必须写明「按 N 个完整日计算」；
- 排名百分比分母必须与排除规则一致，否则用户看到的百分比与自己看到的数字对不上。

### 10.6 窗口级跨日数据在各场景的处理规则（GPT R11-3 · v2.1 新增）

> **五条原则不变**（GPT 明确要求保留）：① 跨日窗口**不强行归属某个自然日**；② **不按比例估算**后伪装成精确数据；③ 窗口级数据**不混入单日精确应用排行**；④ **不完整日期不得默认进入日均统计分母**；⑤ 日间 / 夜间比例**没有可信分母时不得显示虚假百分比**。
> 本节把这五条**逐场景落到「展示 / 排除 / 提示」三类动作**上。§10.1 是速查表，**本节是权威规则**，两者冲突以本节为准。

| # | 场景 | 是否展示窗口级 | 展示形态 | 是否排除出该场景口径 | 提示文案 | 明确禁止 |
|---|---|---|---|---|---|---|
| **S-1** | **首页今日统计**（今日页主卡 + 日夜条 + 应用构成卡） | **部分展示** | 亮屏主卡**下方单列一行**：「另有 N 小时来自跨日窗口（无法按日拆分）」。**主卡的亮屏数值不包含 N** | 窗口级**不进**主卡亮屏数值、**不进**日夜条分母、**不进**应用构成卡占比、**不进**「最长连续」 | 「无法按日拆分」+「不计入今日亮屏」 | ① 把 N 加进主卡数值；② 用 N 反推日间 / 夜间比例；③ 用 N 抬高今日「最长连续」 |
| **S-2** | **日历日统计**（月视图色阶 + 日详情） | **不展示为日数据** | 日详情里若该日被窗口覆盖，**只标注**：「该日有跨日窗口数据，未计入」 | 窗口级**不落到任何一格**、**不参与着色**、**不参与该日任何数值** | 「该日有跨日窗口数据，未计入」 | ① 把窗口摊到 11-21 / 11-22 两格；② 让窗口级影响某格色阶深浅 |
| **S-3** | **应用排行**（单日排行） | **单独成行展示** | 跨日窗口涉及的包**单独成行**，行内标「跨日窗口 11-21 09:2x → 11-22 09:2x」，时长是**窗口总量**；与单日行**视觉区分**（独立分组标题或独立区块） | 窗口级**不进单日排行的名次与百分比分母** | 行内直接写「跨日窗口（无法归属到某一天）」 | ① 把窗口总量当成某一天的应用时长参与排名；② 与单日行混排导致用户误读名次 |
| **S-4** | **应用详情**（单应用的时段分布 / 解锁 / 通知） | **不展示为该日数据** | 若该应用有窗口级记录，详情页**单独一行**提示：「该应用在跨日窗口内使用 N 小时（11-21 → 11-22）」 | 窗口级**不进**该应用的时段分布、**不进**该应用的日均、**不进**该应用的解锁 / 通知统计 | 同 S-3 | ① 把窗口总量并入某一天的小时柱；② 详情页不提示而卡片提示（违反 §7-16 同源） |
| **S-5** | **周 / 月 / 年总结** | **单独一段展示** | 周期总结页**独立区块**：「跨日窗口记录（N 条，共 X 小时，无法按日拆分）」，**放在周期统计之外** | 窗口级**不进**周期日均分母、**不进**周期极值（最长连续 / 最高单日）、**不进**时段分布 | 区块标题即含「无法按日拆分」 | ① 用窗口级抬高周期日均；② 把窗口级当作某一天参与「最高单日」评选 |
| **S-6** | **数据导出与备份恢复** | **原样保留** | 导出 JSON 中窗口级记录**带类型标记与窗口起止**；恢复后**性质不变**（仍是窗口级） | 恢复**不得**把窗口级洗成单日行、**不得**把窗口级折算成任何单日分钟 | 恢复摘要显示「含 N 条窗口级记录」 | ① 恢复时把窗口级按比例摊到各日；② 恢复时把窗口级当 `EXACT` 单日数据参与日均 |

**贯穿 S-1 / S-2 / S-5 的「不完整日期」处理**：

| 项 | 规则 |
|---|---|
| 进入日均分母的日 | **只有 `EXACT` 的日**（§5.9） |
| 排除在日均分母外的日 | `PARTIAL` / `ANCHOR_ONLY` / `UNKNOWN` / `WINDOW` 的日，**一律排除** |
| 卡片说明 | 分母被排除过时，卡片必须写明「日均按 N 个完整日计算」 |
| 区间内**没有任何 `EXACT` 日** | **不显示日均值**，显示「无可用完整日」，**不得**用 `PARTIAL` 日凑一个日均 |
| 极值 | 「最长连续」「最高单日」**只从 `EXACT` 取**；被排除的日在明细里标注 |

**一条跨场景的底线**：

> 窗口级数据在**任何场景**都**只能以「窗口总量 + 窗口起止 + 无法按日拆分」的形态出现**。
> 任何把它折算成日、小时、日均、名次、百分比的转换，都**不属于本设计**，且在实现阶段应视为缺陷。

## 12. 回滚方案

### 12.1 分级回滚

| 级别 | 对象 | 回滚方式 | 注意 |
|---|---|---|---|
| L1 | 单个提交 | `git revert <sha>`（**不要**用 `git checkout --`，项目纪律明令禁止） | 文档提交与实现提交分开 revert |
| L2 | 一批实现（文档 / 实现 / 真机收口三笔） | revert 实现笔，保留文档笔 | 文档保留「已回滚」记录，不删 |
| L3 | Room schema 变更 | **Room 不支持降级迁移** → 旧 APK 在新 schema 上必然失配 | 见 §12.2 |
| L4 | 备份格式变更（v6 → v7） | 旧版 App **无法读取 v7 备份**（`schemaVersion` 过高 → `DecodeResult.Invalid`） | 见 §12.3 |
| L5 | 历史重建 | `rebuild_log` 里有快照 → 可回滚到重建前 | 重建前必须已快照 |
| L6 | 真机 | 重装上一个 debug APK：`adb -s GAQOHMNFQWFUPBQO install -r app/build/outputs/apk/debug/app-debug.apk` | 卸载会丢数据，**优先 `-r` 覆盖安装** |

### 12.2 Room schema 的回滚策略（D8 的连带约束）

- **只要 Room schema 版本号变了，旧 APK 在新库上就会因 schema hash 校验失败而启动不了** —— 与是否只是加列**无关**；
- 因此 schema 变更**必须**与版本发布策略一起裁决（D8 的「仍待确认」项）；
- 回滚路径只有两条：
  1. **向前修复**：发布一个包含降级路径的过渡版本（Room 的降级需手工管理，成本高）；
  2. **数据回滚**：清库重装（**最后手段**，需用户明确同意，会丢本地数据，与 RL-7 的「不清库」精神冲突）；
- **降低风险的做法**：把 schema 变更**放在整批的最后一步**，且优先选择「只加可空列」（改动面最小、可测试性最好）。

### 12.3 备份格式的回滚策略

- v7 备份旧版 App 读不了（`schemaVersion` 过高 → `DecodeResult.Invalid`）→ 备份格式变更应**最后做**；
- 若必须提前发布，采用**双写**：v7 备份里同时保留 v6 可读的信息（新字段可空、旧字段照旧）；
- **任何情况下都不得**通过「删掉 v6 兼容分支」来「简化」实现。
